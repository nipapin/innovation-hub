# Инструмент «Новый элемент» — папка задачи в IN по требованиям ноды `checkFolder`

> **Слово одно на всё.** Сущность называется **элемент**: папка в `IN`, из
> которой соберётся один финальный ролик. Кнопка — «+ Новый элемент», папка —
> «папка элемента». В строках интерфейса держать только это слово; «сборка»,
> «задача», «ролик» как синонимы не заводить.

**Статус:** ✅ реализовано 2026-09-23. Дата написания — 2026-09-23.
**Сторона клиента готова:** нода `checkFolder` и контрол `folderRequirements` в
`fs.manager.tauri` сделаны и собраны.

Этот документ — задание на разработку. Он описывает, что именно строить, из каких
данных, и какие решения уже приняты, чтобы их не пересогласовывать по ходу.
Карта получившегося кода — [reference/09-tools.md](./reference/09-tools.md), часть V.

Чем реализация отличается от задания (решено при разработке 2026-09-23):

- **перенумерация делается пачкой.** В API появился батч-режим
  `POST /api/storage/v1/rename` с `items[]` (`writeRenameBatch` в
  `lib/storage/write-path.ts`). Открытый вопрос №1 из §13 этим закрыт, и не
  только ради журнала: перестановка двух соседей поштучно невыполнима вовсе —
  `01` ↔ `02` это цикл, и любое первое переименование упирается в занятое имя;
- **точек входа на строке две:** иконка при наведении, как в §3, и дублирующий
  пункт контекстного меню — иконку при наведении находят не все;
- **редактор текста — отдельный компонент** (`element/text-editor.tsx`), а не
  режим `markdown-editor.tsx`: у того свой формат и свой сериализатор, и заводить
  рядом второй прямо запрещено комментарием в его шапке;
- **удаление слота — у последнего в строке.** Убрать средний значит сдвинуть
  номера остальных, то есть та же перенумерация, только неочевидная для того,
  кто её вызвал;
- **свойства ноды `checkFolder` убраны из «Настроек» проекта.** У неё свой
  интерфейс, и второе поле для того же значения — это разъезжающиеся правки.
  Решено владельцем 2026-09-23: исключается нода целиком. Сайт смотрит в граф
  ровно на одно поле — `data.pluginId` ноды-владельца свойства; форма по-прежнему
  приезжает целиком из `onSiteFolderCheckForm.json`, в нём есть всё необходимое;
- **файл формы переименован.** `siteForm.json` → `onSiteFolderCheckForm.json`,
  имя сайдкара в API `site-form` → `on-site-folder-check-form`. Решено
  владельцем 2026-09-23, до того как имя где-либо закрепилось. Обе стороны
  меняются одновременно: пока десктоп пишет старое имя, сайт формы не находит;
- **форма — обычный файл проекта, а не канонический сайдкар.** Выяснилось при
  первом включении (2026-09-23): программа доставляет её **обычной
  синхронизацией папки** и отдельных команд записи не шлёт. Поэтому, во-первых,
  файл лежит по ключу `{uuid}-{имя}`, и искать его надо ПО ИМЕНИ в каталоге, а
  не по фиксированному адресу: GET `/sidecars` берёт ключ из строки каталога.
  Во-вторых, форму нельзя вносить в `CANONICAL_SIDECAR_NAMES` — этот список
  запрещает заливку мимо `PUT /sidecars`, и каждая синхронизация получала бы
  409, а байты удалялись бы как сиротские. Три настоящих сайдкара
  (`folderState.json`, `options.json`, `description.md`) в списке остаются: их
  пишет сайт;
- **папка заводится лениво — с первым файлом**, а не при открытии окна.
  Решено владельцем 2026-09-23: открыть окно и передумать это обычное дело, а
  пустые папки в `IN` человек потом удаляет руками. До первого файла существует
  только имя в шапке, и правится оно же. Структура подпапок появляется сразу
  вслед за папкой — граф ждёт объявленный состав целиком, а не по мере
  заполнения. Сохраняется всё само, подтверждения ждёт только запуск.

## 1. Зачем это

Обработка начинается с **одного** элемента в папке `IN`. Набор из нескольких
файлов поэтому собирают в папку, а чтобы её не утащило в работу недособранной —
имя начинают с дефиса: такие папки обе линии сборки пропускают.

Слабое место — наполнение. Сейчас оно ничем не проверяется: ни состав, ни
порядок, ни имена. А когда текстов несколько, каждому нужно строго определённое
имя, и ошибиться в нём нечем помешать — при том что дальше этот набор уезжает в
After Effects, где имя файла и есть способ его найти.

Нода `checkFolder` превращает «как договорились» в объявленное требование. Одно и
то же дерево читают двое: нода — чтобы проверить папку перед обработкой, этот
инструмент — чтобы **сгенерировать форму**, в которой человек собирает файлы по
местам и с правильными именами.

Отсюда главное свойство инструмента: **имена файлов даёт он, а не человек.**
Человек приносит файл, инструмент кладёт его под тем именем, которое ожидает граф.

## 2. Решение о месте: это НЕ инструмент из раздела «Инструменты»

`TOOLS_DEV_GUIDE.md §0` говорит прямо: инструмент «не запускает обработку и не
является нодой конвейера; он правит то, что обработка уже положила в папку», и
`defaults.sourceRoot` у обоих существующих инструментов — `OUT`.

Сборка делает ровно обратное: работает в `IN` **до** обработки и заканчивается
запуском обработки. Втискивать её в каталог инструментов значит нарушить
установленное правило раздела и завести экземпляр с источником, которого не
существует: подключать нечего, папка всегда одна — `IN` текущего проекта.

**Поэтому:** это **диалог рабочей области**, открываемый из файлового
дерева проекта, а не карточка в каталоге. Экземпляр в `user_tools` не заводится,
`source`/`settings` не нужны.

Что из гайда при этом всё равно обязательно:

- флаг в [lib/features.ts](../lib/features.ts) — иначе появится на всех площадках
  ([FEATURE_FLAGS.md](./FEATURE_FLAGS.md));
- строки **в оба словаря** [components/account/i18n.tsx](../components/account/i18n.tsx)
  (`npm run i18n:check` иначе упадёт);
- только токены `ws-*`, иконки только `lucide-react`, скроллятся панели, не
  страница ([UI_GUIDE.md](./UI_GUIDE.md));
- запись только через `writeNotifyUpload` с `actor.isUploader: false`;
- порог `editor` на любую запись, `viewer` на чтение.

Решено владельцем: именно так — кнопка в файловом дереве, как «+ новый проект» в
разделе проектов, а не карточка в каталоге инструментов.

## 3. Точки входа в интерфейсе

Обе — в файловом дереве проекта
([components/account/workspace/file-browser.tsx](../components/account/workspace/file-browser.tsx)).

| ситуация | что показываем |
| --- | --- |
| человек внутри папки `IN` проекта, в графе есть нода `checkFolder` | строка-кнопка **«+ Новый элемент»** в самом низу списка содержимого — по образцу «+ новый проект» в разделе проектов |
| наведение на папку-элемент внутри `IN` | иконка **«Править»** (`pencil`) на строке |

Кнопка показывается **только если граф работает с папками** — то есть в
`options.json` есть нода `checkFolder`. Нет ноды — нет и кнопки: собирать не по
чему.

Обе точки открывают один и тот же диалог: кнопка — на пустой папке, иконка — на
разобранном содержимом существующей.

**Как отличить папку элемента от обычной папки в `IN`.** По требованиям из ноды и
по имени: папка считается элементом, если её содержимое разбирается грамматикой
§6. Отдельной метки в хранилище не заводим — она стала бы вторым источником
правды и разъехалась бы с содержимым при первой же правке из десктопа.

> **Открытый вопрос №2.** Если в графе несколько нод `checkFolder`, непонятно, по
> какой строить форму. Предлагаемое умолчание: берём первую ноду типа
> `checkFolder`, у которой вход подключён к `mainSearch`; если таких несколько —
> показываем выбор перед открытием диалога.

## 4. Откуда берутся данные

### 4.1. `options/onSiteFolderCheckForm.json` — готовая форма, а не граф

Читается через `GET /api/storage/v1/sidecars?name=on-site-folder-check-form` (порог `viewer`).

**`options.json` сайт для этого НЕ разбирает.** `options.json` — это граф: ноды,
рёбра, координаты, свойства всех плагинов. Доставать оттуда форму значило бы знать
внутреннее устройство редактора нод (как называется `controlType`, где лежит
`value`, чем динамическое свойство отличается от статического) — то есть завести
второго читателя модели нод, который ломается молча при любой правке редактора.

Вместо этого десктоп при сохранении графа компилирует готовый ответ.

⚠️ **Поправка 2026-09-23.** Здесь раньше стояло «тот же приём, что у
`postSources.json` и `tgSearch.json`». Это неверно, и путаница стоила времени
при первом включении. Те сайдкары в облако **не синхронизируются** — они
локальные build-артефакты, — и поэтому сайт читает там сам граф
(`lib/posting/routes.ts`). Форма же в проект синхронизируется, и читать её надо
из файла. Совпадает только то, что оба файла компилирует программа при
сохранении графа; дальше судьба у них разная.
Код — `src/NODE_WIN/utils/syncSiteFormSidecar.ts` в клиентском репозитории,
вызывается из единой точки сохранения `saveFlow.ts`.

```jsonc
{
  "version": 1,                        // формат; чужую версию не читаем
  "element": {
    "nodeType": "checkFolder",
    "folderNameTemplate": "$YYYY-$MM-$DD $HH.$mm",
    "nodeLabel": "Check Folder",       // запасное имя, если шаблон пуст
    "rows": [ /* дерево требований, см. §5 */ ]
  },
  "fileTypes": {                       // тип → расширения, уже нормализовано
    "video": ["mp4", "mov"],
    "text":  ["txt", "srt"]
  }
}
```

Три следствия, на которых держится инструмент:

- **нет файла — нет кнопки.** Отсутствие `onSiteFolderCheckForm.json` значит «проект не
  собирается папками»: ноды `checkFolder` в графе нет либо она выключена. Десктоп
  в этом случае файл удаляет, а не оставляет пустым;
- **`fileTypes` едет здесь же** — отдельно из `options.json` его читать не нужно;
- **`version` сверяем.** Не совпала — инструмент не открывается и говорит, что
  проект сохранён более новой версией программы. Догадываться о формате нельзя.

### 4.2. Галочку «на сайте» игнорируем

У строки требования есть поле `exposed`. **В этом инструменте оно не смотрится:
показываются все строки.** Решение владельца: папку собирает человек, значит он
должен видеть весь состав, иначе «Запустить» будет недоступно по причине, которой
не видно на экране.

## 5. Модель требования

Каждая строка дерева `rows[]` из §4.1. Это полный список полей — других у строки нет:

| поле | смысл |
| --- | --- |
| `id` | уникален внутри дерева |
| `label` | имя поля формы — **оно же попадает в имя файла** |
| `tooltip` | подсказка (Markdown) |
| `type` | имя типа файла из словаря, либо `folder` |
| `op` | `">="` или `"="` |
| `count` | сколько штук, всегда ≥ 1 |
| `children` | требования к содержимому подпапки, только при `type: "folder"` |

Правила разворачивания в форму:

- **`op: "="`** → ровно `count` слотов, кнопки «добавить» нет (не рисуем вовсе, а
  не показываем выключенной);
- **`op: ">="`** → сразу `count` слотов плюс кнопка «добавить ещё такой же»;
- слоты нумеруются с `01` **всегда**, даже когда слот один: структура имён должна
  быть единой, иначе парсер обратно (§6) получает два случая вместо одного;
- строки одного уровня соединяются **И**.

**Ограничение: `label` должны быть уникальны внутри одного уровня.** Иначе имена
файлов совпадут и разобрать папку обратно будет нечем. Инструмент проверяет это
при открытии и, если дубли есть, **отказывается открываться** с внятным текстом —
чинить надо в графе, а не здесь.

## 6. Имена: грамматика, которую обязаны знать обе стороны

Имя — единственная связь между слотом формы и файлом на диске. Отдельного
манифеста в папке нет **намеренно**: он стал бы вторым источником правды, а
правки из десктопа его не обновляют.

```
папка элемента  -<имя по шаблону>            «-Ролик 2026-09-23 14.05»
файл в слоте    NN <label> - <исходное имя>  «01 Ведущий - clip.mp4»
файл без исходного имени   NN <label>        «01 Ведущий.txt»
подпапка        NN <label>                   «01 Сцена»
```

- `NN` — два знака, с ведущим нулём, порядковый номер слота внутри строки;
- разделитель между `label` и исходным именем — ` - ` (пробел, дефис, пробел);
- у подпапок дефиса в начале **нет**: дефис помечает только сам элемент, и только
  на верхнем уровне.

**Разбор обратно.** Не регуляркой «до первого ` - `»: `label` сам может содержать
дефис. Порядок такой: отрезать `NN `, затем найти среди `label` этого уровня тот,
с которого имя начинается (при нескольких совпадениях — самый длинный), остаток
после ` - ` считать исходным именем. Поэтому же `label` обязаны быть уникальны.

Файлы, которые не разобрались ни в один слот, показываем отдельной группой
«лишние» с возможностью удалить. Молча прятать нельзя: нода их посчитает, и
условие `=` из-за них не сойдётся.

### 6.1. Нумерация всегда подряд

Номера — это позиция в списке, а не идентификатор. Отсюда три правила:

- **начинается с `01`**, не с нуля;
- **дыр не бывает.** Удалили второй из трёх — оставшиеся перенумеровываются, то
  есть третий становится вторым и файл переименовывается. Иначе после `01`, `03`
  следующее добавление снова просится в `03` и упирается в занятое имя;
- **меняется только номер.** Имя компонента и исходное имя файла остаются как
  были: перенумерация — не повод трогать остальное.

**Порядок меняется перетаскиванием.** Слоты внутри одной строки требования можно
переставлять мышью; после перестановки номера пересчитываются по новому порядку и
файлы переименовываются. Это единственный способ поменять порядок — удалять и
заливать заново ради этого человек не должен.

**Удалить ниже минимума нельзя.** Если строка требует `>= 2`, последние два слота
не удаляются: кнопка удаления у них не показывается. При `=` не удаляется ни
один — их ровно столько, сколько объявлено. Удаление, после которого условие
заведомо не сойдётся, — это не свобода, а ловушка: человек получил бы форму,
которую нельзя запустить, и без объяснения почему.

Перенумерация — это переименование файлов в хранилище. Делать его надо **одной
пачкой после подтверждения удаления**, а не по файлу на каждый чих: каждое
переименование это `move`-событие в журнале.

### 7.1. Шапка: имя и запуск

**Имя папки** слева. При создании генерируется из `folderNameTemplate` ноды.
Поддерживаются **только временные маски** — `$YYYY`, `$MM`, `$DD`, `$HH`, `$mm`,
`$ss` — и `$random(N)`. Остальные маски движка зависят от обрабатываемого файла, а
его в момент создания папки ещё нет.

Подробности, без которых подстановка разойдётся с программой:

- **регистр значим**: `$MM` — месяц, `$mm` — минуты;
- **`$random` без числа** (`$random` или `$random()`) — это **10** символов, не одна
  и не «сколько получится». В программе он реализован через `nanoid`, алфавит
  url-safe (`A-Za-z0-9_-`); сайту точная копия алфавита не нужна (значение всё равно
  случайное), а вот **длина по умолчанию обязана совпадать** — имена элементов читают
  люди, и «10 знаков у меня и 21 у них» замечают сразу;
- время берётся **локальное для сервера**, не UTC: имя читает человек, и «вчера» у
  него своё.

⚠️ **Реализации масок на сайте нет.** Единственный движок — `src/Utils/masks.ts` в
клиентском репозитории, и он завязан на Node. Эти шесть подстановок придётся
написать на сайте заново; переиспользовать нечего. Шаблон пустой → берём
`data.label` ноды.

Имя правится двойным кликом; при наведении под ним появляется подчёркивание —
признак, что его можно менять. В поле человек пишет имя **без дефиса**, дефис
инструмент держит сам.

Если имя занято (шаблон дал ту же дату дважды) — дописываем ` (2)`, ` (3)`.

**Кнопка «Запустить»** справа. Единственное, что она делает — **снимает дефис с
имени папки**. Это `move`-событие внутри `IN`, и событийная линия заводит задачу
за секунды.

Кнопка неактивна, пока не собраны все слоты. Рядом — текст, чего не хватает:
человек должен видеть причину, а не упираться в серую кнопку.

### 7.2. Обычный файл

- под именем слота — ожидаемый тип (когда пусто, это и есть подсказка «что сюда»);
- справа кнопка выбора файла; сверх того зона принимает **перетаскивание извне
  браузера**;
- при наведении файлом проверяем расширение по словарю типов: подходит — зона
  зелёная, не подходит — красная, и **файл не принимается**;
- принятый файл заливается в папку элемента и сразу получает имя по §6;
- заполненный слот показывает итоговое имя, кнопку удаления и просмотр.

Заливка — штатная: `POST /api/storage/v1/presign {method:"PUT"}` → `PUT` в R2 →
`POST /api/storage/v1/notify`. Для крупных — multipart.

### 7.3. Текст — особый случай

Текстовый слот заполняется **двумя способами**: файлом или прямо на сайте.

- поле показывает первую строку, остальное свёрнуто;
- слева от «Выбрать» — кнопка **«Редактор»**, открывающая редактор §8;
- перетащенный или выбранный `.txt` **не заливается как файл**. Его читают,
  содержимое кладут в поле, а исходное имя запоминают — чтобы итоговый файл
  назывался `01 Текст ролика - исходное.txt`. Имени нет → `01 Текст ролика.txt`.

Итог всегда один: **новый `.txt`, записанный инструментом.** Так у двух разных
текстов никогда не совпадут имена.

### 7.4. Подпапка

Строка с `type: "folder"` разворачивается во вложенный блок: внутри — та же форма
по `children`, визуально вложенная (отступ + левая линия, как в редакторе ноды).

При `op: ">="` — кнопка «добавить», создающая **ещё одну папку** с той же
внутренней структурой и следующим номером. Имена подпапок — `NN <label>`, без
дефиса. Вложенность рекурсивна на любую глубину.

## 8. Редактор текста и формат разметки

### 8.1. Редактор

Берём существующий Tiptap-редактор
([components/markdown/markdown-editor.tsx](../components/markdown/markdown-editor.tsx)),
но **сильно урезанный**. Правило отбора жёсткое:

> Чего нельзя сделать скриптом в After Effects — того в редакторе быть не должно.

Оставляем: жирный, курсив, цвет, комментарий-тег, переносы строк.
Убираем: заголовки, списки, таблицы, картинки, ссылки, цитаты, код, **подчёркивание**.

Цвет — отдельный контрол: палитра плюс ряд ячеек «уже использованные», который
пополняется при выборе нового цвета. Клик по ячейке — применить её цвет.

### 8.2. Формат файла

Файл — обычный `.txt`, UTF-8. Не HTML и не Markdown: переносы строк и любые
символы допустимы как есть. Размеченный фрагмент выглядит так:

```
Обычный текст, <этот кусок>[Bold, #FF3B30, x1.5, "произносить медленно"] и дальше.
```

Грамматика:

```
<фрагмент текста>[свойство, свойство, …]
```

Свойства распознаются **по форме**, без ключей — так парсеру в ES3 не нужен JSON:

| форма | что значит | пример |
| --- | --- | --- |
| зарезервированное слово | начертание | `Bold`, `Italic` |
| начинается с `#` | цвет | `#FF3B30` |
| начинается с `x` | множитель размера | `x1.5`, `x0.5` |
| в двойных кавычках | комментарий-тег | `"произносить медленно"` |

**Размер — множитель, а не кегль.** Какой кегль окажется в композиции, заранее
неизвестно; `x1.5` значит «в полтора раза больше того, что есть».

**Как это применяется в After Effects.** Свежие версии умеют стилизовать текст
экспрешенами по **диапазону символов** — у `TextStyle` почти каждый сеттер
принимает `startIndex` и `numOfCharacters`:

```
setFillColor(value[, startIndex, numOfCharacters])
setFontSize(value[, startIndex, numOfCharacters])
setFauxBold(value[, startIndex, numOfCharacters])
setFauxItalic(value[, startIndex, numOfCharacters])
setStrokeColor / setStrokeWidth / setApplyStroke / setTracking / setBaselineShift
```

Поэтому разбор устроен так: парсер снимает разметку, отдаёт **чистый текст** и
список диапазонов (`от символа`, `длина`, свойства), а скрипт вешает экспрешен,
который зовёт нужные сеттеры на эти диапазоны. Из этого следует требование к
формату, уже заложенное выше: вложенность запрещена, значит диапазоны не
пересекаются и ложатся в вызовы один к одному.

**Подчёркивания в формате нет, и это решение, а не пробел.** В `TextStyle` его не
существует вообще: ни `setUnderline`, ни атрибута. Реализовать пришлось бы рисованием
— то есть механизмом, не имеющим ничего общего с «поставить свойство символа», — и
ради начертания, которое в титрах почти не нужно. Решено владельцем 2026-09-23:
не заводим.

То же касается **плашки под текстом** (фон за фрагментом): она тоже не свойство
символа, а геометрия, зависящая от границ отрисованного текста. Если понадобится,
формат к этому готов — правило «неизвестное свойство игнорируется, текст
сохраняется» позволяет добавить её позже, не ломая уже написанные файлы.

**Смена шрифта в формате не предусмотрена намеренно** — решение владельца, хотя
`TextStyle` это и умеет.

Правила, без которых парсер разойдётся с редактором:

- **вложенность запрещена.** Пересекающееся оформление при сохранении
  раскладывается в соседние фрагменты;
- **экранирование** — обратный слеш перед `<`, `>`, `[`, `]`, `\`;
- порядок свойств внутри `[…]` произволен, разделитель — запятая с пробелом;
- фрагмент без свойств (`<текст>[]`) не пишем вовсе — пишем просто текст;
- неизвестное свойство при чтении **игнорируется, а текст сохраняется**: формат
  будет расширяться, и старый скрипт не должен терять содержимое.

> **Открытый вопрос №3.** Этот формат читает ещё и скрипт After Effects в
> клиентском репозитории (`jsx/`). Канонический текст грамматики — здесь; когда
> появится парсер в `jsx/`, он должен ссылаться на этот раздел, а не пересказывать
> его. Второй полный текст об одном и том же разъезжается молча.

## 9. Запрет переименования внутри элемента

Имена держит инструмент, значит переименование мимо него ломает связь слота с
файлом.

**Решение: прячем пункт в интерфейсе**, жёсткой проверки в API не ставим.

Область запрета:

- сама папка элемента и **всё её содержимое на любой глубине** — пункт
  «Переименовать» не показывается;
- **файл, лежащий прямо в `IN`** (не в элементе), переименовывается как раньше:
  это обычный одиночный исходник, инструмент к нему отношения не имеет.

Место правки — [context-menu.tsx](../components/account/workspace/context-menu.tsx),
пункт `ws.renameItem(file)`.

Образец жёсткого запрета, если позже решим усилить, — `assertSidecarPlaceIsStable`
в [lib/storage/write-path.ts](../lib/storage/write-path.ts): там защита стоит **на
уровне операции**, а не в `validateLogicalName`, и это осознанный принцип
(см. комментарий в [lib/storage/file-names.ts](../lib/storage/file-names.ts)).

## 10. Открытие уже собранной папки

1. читаем дерево папки (`GET /api/storage/v1/tree`);
2. разбираем имена по §6, раскладываем файлы по слотам;
3. текстовые слоты — читаем содержимое файла и разбираем разметку §8 обратно в
   документ редактора;
4. лишние файлы — в группу «лишние»;
5. недостающие слоты — пустые.

Заполненные слоты показывают имя, дают посмотреть файл и удалить его.

### Важно: дефис — общий канал

Дефисом помечается не только «ещё собираем». Тем же дефисом помечается **брак**:
и десктоп (`markSkippedWithDash`), и сайт (`quarantineTaskSource`) так помечают
исходник упавшей задачи. По имени эти состояния не различаются вообще.

Различитель — **задача**:

| состояние | как узнать | что показывать |
| --- | --- | --- |
| собираем | задачи по этой папке нет | форму элемента |
| упало | есть задача `status = 'failed'`, `quarantined_at` | сначала ошибку, форму — по явному действию |

Открыть форму элемента на упавшей папке, не сказав об ошибке, — значит предложить
человеку «дособрать» то, что на самом деле сломалось.

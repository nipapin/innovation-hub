# UI-настройки в браузере — реестр

Мелкие предпочтения интерфейса, которые браузер запоминает между визитами:
свёрнутая панель, выбранная вкладка, режим списка, размер колонки. Это
оформление, а не данные аккаунта: в базу они не едут, синхронизации между
устройствами нет — на двух машинах человек волен смотреть по-разному.

Документ — реестр: **новая настройка сначала попадает сюда**, потом в код.
Иначе через полгода никто не вспомнит, что где хранится, и одно и то же
начнут сохранять дважды под разными ключами.

## Куда писать

**Новые настройки — в куки** через `lib/ui-prefs.ts` (`readUiPref` /
`writeUiPref`, решение 2026-09-17). Куку, в отличие от `localStorage`, **может
прочитать и серверный компонент** — через `cookies()` из `next/headers`, и
тогда первый кадр приходит уже с учётом выбора (так работает тема).

Но `readUiPref` этого не делает: он читает `document.cookie`, то есть на
сервере всегда возвращает `null`. Серверное чтение — отдельная работа, значение
надо протащить пропом до нужного компонента. Само по себе хранение в куке
первый кадр не чинит.

Плата: значения ездят с каждым запросом к серверу. Поэтому правила:

- значение — короткая строка (`"1"`, `"settings"`), никаких JSON-структур;
- ничего чувствительного — кука не httpOnly, её видит любой скрипт страницы;
- имя куки с префиксом `ui-`, короткое: оно тоже ездит в каждом запросе.

Старые настройки остаются в `localStorage` и живут как живут — переносить их
в куки ради переноса не нужно; таблица ниже фиксирует, что где лежит.

## Правила добавления новой настройки

1. **Строка в реестре ниже** — ключ, значение по умолчанию, где используется.
2. **Одна точка записи.** Запись прячем в сеттер состояния (как `setBottomTab`
   в `workspace-context.tsx`), а не размазываем по местам вызова: иначе часть
   путей будет сохранять, часть — нет.
3. **Чтение с валидацией.** При чтении значение проверяется по списку
   допустимых; мусор и отсутствие — это «по умолчанию», а не причина упасть.
4. **Когда читать — по тому, есть ли компонент в серверном кадре.**
   - Компонент **рисуется сервером** (обычный случай: клиентский компонент в
     App Router всё равно попадает в серверный HTML) — читаем в `useEffect`
     после монтирования, как плотность и вид рабочей области. Ленивый
     инициализатор здесь даёт расхождение гидратации: сервер нарисует значение
     по умолчанию, клиент — сохранённое, и React об этом пожалуется.
   - Компонента **в серверном кадре нет** (родитель до ответа API возвращает
     `null` — так живёт «пульт» на странице конвейера) — можно ленивым
     инициализатором `useState(() => ...)`: расходиться не с чем, зато секция
     не моргнёт развёрнутой.
   - Нужен **правильный первый кадр у серверного компонента** — читаем куку
     через `cookies()` и передаём пропом; `readUiPref` для этого не годится.
5. **Без `try/catch` не падаем, но и не обязаны.** Запись в куку через
   `writeUiPref` безопасна сама по себе; на сервере (нет `document`) оба
   хелпера молча возвращают `null` / ничего не делают.

## Куки (текущий способ)

| Ключ | Что хранит | Значения | По умолчанию | Где |
| --- | --- | --- | --- | --- |
| `theme` | тема оформления | `system` / `light` / `dark` | `system` | `lib/theme.ts`, `theme-switch.tsx` — читается и серверным layout |
| `ui-pipeline-areas-open` | свёртка «Пульта» (таблица всех конвейеров) на `/admin/pipeline` | `1` / `0` | `1` (развёрнут) | `areas-content.tsx` → `Section storageKey` |
| `ui-ws-bottom-tab` | вкладка нижней панели проекта | `preview` / `desc` / `settings` / `chat` | `desc` | `workspace-context.tsx` (`setBottomTab`) |

# Производство: пайплайн ролика по шагам

**Для кого.** Для того, кто будет это реализовывать и кто принимает решения по
продукту: из каких сущностей состоит производство ролика, как шаг связан с папками
и людьми, как проходит проверка и как файл на выходе связывается с исходником. Плюс
порядок работ и вопросы, без ответа на которые дальше не двинуться.

Дата сверки с кодом: **2026-09-28**. Статус: **план, не начато.** Рабочее название
«Производство» (§1) пока не утверждено.

Основа: [COMPANY_ACCOUNTS_PLAN.md §8 и §12](./COMPANY_ACCOUNTS_PLAN.md). Там уже
записано, что назначение в пайплайне делает человека участником проекта, что шаги
связываются по id проекта, а не по имени, и что чат компании живёт отдельным
каналом, а не в `project_chat_messages`. Этот документ те решения не пересматривает,
а раскладывает на реализацию.

Смежные документы: [PIPELINE.md](./PIPELINE.md) (очередь обработки на машинах),
[PROJECT_CHAINS_PLAN.md](./PROJECT_CHAINS_PLAN.md) (цепочки внутри одного владельца),
[TOOLS_DEV_GUIDE.md](./TOOLS_DEV_GUIDE.md) (как подключить инструмент),
[FEATURE_FLAGS.md](./FEATURE_FLAGS.md) (выключатели разделов).

## 0. Одной фразой

**Шаблон** описывает шаги производства и связи между ними. Кнопка «Новый ролик»
создаёт по шаблону **запуск**: на каждый шаг заводится свой проект с папками, своими
людьми и своим чатом. Шаг берут в работу, сдают на проверку, проверяющий смотрит
результат с покадровыми пометками и либо принимает (результат замораживается и
уходит в следующие шаги), либо возвращает на доработку. Каждое действие попадает в
журнал: кто и когда.

## 1. Название

### 1.1. Что занято

«Конвейер» / `pipeline` — это очередь **автоматической обработки**: сайт замечает
новое в `IN`, собирает задачу, машина парка её выполняет
([lib/pipeline/](../lib/pipeline/), `/admin/pipeline`, таблица `tasks`, контракт с
`fs.manager.tauri` в [PIPELINE.md](./PIPELINE.md)). В интерфейсе слово «конвейер»
встречается в ~15 строках словаря ([components/account/i18n.tsx](../components/account/i18n.tsx)),
в справке и в статистике.

### 1.2. Предложение

| что | название |
| --- | --- |
| Новый раздел | **«Производство»** |
| Ключ в коде, таблицы, роуты | `production` (`lib/production/`, `production_*`, `/api/production/*`) |
| Шаблон | «Шаблон производства» |
| Запуск по шаблону | «Ролик» (в коде `run`) |
| Шаг | «Этап» (в коде `step`) |

Существующий «Конвейер» **не переименовываем**. Слово `pipeline` вшито в контракт с
десктопом, в имена экшенов и в документацию, которую читает другая команда. Выигрыша
от переименования нет, если новое называется иначе. Путаница возможна только в
разговоре, поэтому в коде нового раздела слово `pipeline` не используется совсем.

Если новый раздел всё-таки должен называться «Пайплайн», дешёвый вариант такой:
переименовать **только подпись** существующего раздела на «Обработку». Это ~15 строк
словаря плюс справка, а код, таблицы и контракт с машинами остаются как есть.

Другие варианты названия нового раздела: «Продакшн», «Маршрут», «Техкарта».

## 2. Сущности

```
Шаблон (production_templates)          ← граф: этапы + связи, люди по умолчанию
   │  «Новый ролик»
   ▼
Ролик (production_runs)                ← снимок графа на момент запуска
   │
   ├── Этап (production_steps)         ← свой проект: папки, участники, чат
   │     ├── Элементы (production_items)          ← единицы работы: что пришло на вход
   │     ├── Сдачи (production_submissions)       ← v1, v2, … отправленное на проверку
   │     │     └── Файлы сдачи (…_submission_files) ← выход, привязанный к элементу
   │     │           └── Пометки (production_review_comments) ← кадр, рисунок, текст
   │     └── Чат (production_messages)
   └── Журнал (production_events)      ← взял, сдал, принял, вернул, пригласил
```

### 2.1. Шаблон и снимок

Шаблон можно править в любой момент. Ролик при запуске забирает **копию** графа
(`graph_snapshot`), поэтому правка шаблона не ломает ролики, которые уже в работе.
Правило то же, что у задачи конвейера: инструкция фиксируется в момент создания.

### 2.2. Этап = проект

**Каждый этап каждого ролика — отдельный проект.** Это главное решение плана, и
принимается оно ради того, что всё нужное уже работает на уровне проекта:

| что нужно этапу | что уже есть у проекта |
| --- | --- |
| своя папка-хранилище | проект и есть папка в R2 с каталогом `project_files` |
| раздать людям с правами | `project_members`, `viewer` / `editor` / `full`, диалог «Поделиться» |
| скачать всё разом | архив папки ([lib/storage/archive.ts](../lib/storage/archive.ts)) |
| залить вручную | заливка кабинета и десктоп-синхронизация |
| обработка на машине | конвейер следит за `IN` проекта и сам создаёт задачи |
| инструменты сайта | источник инструмента = проект + папка |
| кто платит | владелец проекта, «отдал доступ — платишь ты» |

Альтернатива «один проект на ролик, этап = подпапка» проигрывает: права на уровне
папки в хранилище не существуют. Пришлось бы переписывать авторизацию в
`lib/storage/auth.ts` и в `lib/project-access.ts`, то есть самые чувствительные
места сайта, а исполнитель этапа 3 увидел бы черновики этапа 1.

Следствия:

- **Все проекты ролика принадлежат владельцу шаблона** (в компании это служебный
  аккаунт кошелька, [COMPANY_ACCOUNTS_PLAN §7.3](./COMPANY_ACCOUNTS_PLAN.md)).
  Передача файлов между этапами идёт внутри одного владельца, поэтому ограничение
  цепочек «за пределы владельца нельзя» здесь не мешает.
- В общих списках проектов этапы не показываются. Им ставится
  `group_name = 'production'` (колонка без `CHECK`, миграция не нужна), и они
  видны только внутри раздела «Производство». Проект называется
  `<ролик> · <NN этап>`.
- Исполнитель следующего этапа **не получает доступа** к предыдущему: принятые
  файлы копируются ему во вход (§4.4).

### 2.3. Раскладка папок этапа

```
<ролик> · 02 Анимация/
  IN/                ← входы: принятое с прошлых этапов + ручные заливки
    <слот>/…         ← по папке на входной слот, если слотов несколько
  OUT/               ← результаты: сюда кладёт машина, сюда же ручная заливка
  _review/
    v1/…             ← замороженная сдача, не редактируется
    v2/…
  options/           ← как у любого проекта (граф обработки, если этап автоматический)
```

`_review/vN` пишет только сайт. Замороженная копия нужна затем, чтобы принятое
нельзя было тихо поменять правкой файла в `OUT` после одобрения. Копия делается
внутри R2 ([lib/storage/copy.ts](../lib/storage/copy.ts)), байты через сайт не идут.

## 3. Ноды

### 3.1. Чем ноды производства отличаются от нод обработки

В программе нода — это операция над файлом, а граф исполняется машиной. Здесь нода —
**этап работы людей или машины**, а граф задаёт порядок и то, что передаётся дальше.
Исполняет его не движок, а сайт, по событиям «этап принят».

[PROJECT_OPTIONS_PANEL.md §1](./PROJECT_OPTIONS_PANEL.md) закрыло вопрос редактора
**графов обработки** на сайте. Здесь другой граф, и то решение он не отменяет: графы
обработки по-прежнему правятся только в программе.

### 3.2. Типы нод

| нода | что делает | вход → выход |
| --- | --- | --- |
| **Старт** | откуда берутся исходники ролика: заливка при создании или папка | — → слоты |
| **Этап** (ручной) | работа людей: скачали, сделали, залили | слоты → слоты |
| **Этап обработки** | работа машины по графу в `options.json` этапа (ffmpeg, AE, Moho через программу) | слоты → слоты |
| **Этап с инструментом** | работа в инструменте сайта (титры, озвучка), источник подключён к этапу | слоты → слоты |
| **Финал** | куда кладётся принятый результат ролика: папка выдачи, позже постинг | слоты → — |

Проверка — **не отдельная нода, а свойство этапа**: у любого этапа есть галка «нужна
проверка» и список проверяющих. У этапа обработки проверку можно выключить, тогда
результат машины уходит дальше сам.

### 3.3. Слоты и связи

У этапа есть именованные входные и выходные **слоты** («Раскадровка», «Озвучка»,
«Анимация»), у слота есть фильтр типов из общих словарей (видео, картинка, аудио,
текст, папка). Связь соединяет выходной слот одного этапа с входным слотом другого.

- **Разветвление:** один выход идёт в несколько этапов (озвучка и анимация параллельно).
- **Слияние:** этап становится доступным, когда приняты **все** этапы, которые в него
  входят.
- **Циклов в графе нет.** Возврат на доработку — это действие над этапом (§4.3), а не
  ребро.

### 3.4. Свойства этапа в шаблоне

| свойство | зачем |
| --- | --- |
| исполнители по умолчанию | получают `editor` на проект этапа |
| проверяющие | получают `commenter` (§6.2) и право принять или вернуть |
| наблюдатели | `viewer` |
| правило приёмки | достаточно одного проверяющего или нужны все |
| срок (часов от старта этапа) | подсветка просрочки, позже |
| граф обработки | только у этапа обработки: какой `options.json` положить в проект |
| инструмент | только у этапа с инструментом: `tool_key` и настройки |

При запуске ролика людей можно переназначить. В ролик идут изменённые, шаблон не
меняется.

### 3.5. Чем рисовать граф

`@xyflow/react`, та же библиотека, что в программе: у неё знакомое поведение, слоты
ложатся на handles, а этапов в шаблоне единицы и десятки, то есть объём небольшой.
Хранится граф JSON-ом в `production_templates.graph` с `revision` и оптимистической
блокировкой, как общие словари (`UPDATE … WHERE revision = $base`, иначе 409).
Общего кода с редактором программы нет и не будет: стек сайта Tailwind + Radix, а в
программе MUI (см. то же §1 PROJECT_OPTIONS_PANEL).

На странице ролика тот же граф показывается только для чтения, с цветом статуса на
каждом этапе.

## 4. Жизненный цикл

### 4.1. Статусы этапа

```
waiting ──► ready ──► in_progress ──► in_review ──► approved
 (ждёт        (входы     (взят в        │   ▲
 входов)      пришли)    работу)        ▼   │
                                   changes_requested
```

| переход | кто | что фиксируется |
| --- | --- | --- |
| `waiting → ready` | сайт: приняты все входящие этапы | входы скопированы в `IN` |
| `ready → in_progress` | исполнитель: кнопка **«Взять в работу»** | кто и когда |
| `in_progress → in_review` | исполнитель: **«Отправить на проверку»** | версия `vN`, кто, когда, состав |
| `in_review → approved` | проверяющий: **«Принять»** | кто, когда; запускает передачу дальше |
| `in_review → changes_requested` | проверяющий: **«Вернуть»** с комментарием | кто, когда, пометки |
| `changes_requested → in_review` | исполнитель: сдаёт `v(N+1)` | как при сдаче |

«Взять в работу» — единственное обязательное действие для отметки старта. Ничего
включать не нужно, это просто кнопка. Если исполнитель забыл её нажать и сразу
залил результат или сдал, старт фиксируется по первой заливке в `OUT` с пометкой
«неявно». Время всё равно известно, и статистика по этапам не дырявая.

### 4.2. Единица работы — элемент входа

Правило то же, что у конвейера ([reference/08-pipeline.md §3](./reference/08-pipeline.md)):
**один элемент верхнего уровня в `IN`, файл или папка, — одна единица работы.**
На этапе может быть один элемент (весь ролик) или двадцать (двадцать шотов).

Проверка идёт по элементам, как в Frame.io по ассетам: у каждого элемента в сдаче
своё «принято» или «на доработку». Этап принят, когда приняты все его элементы.
Доработка касается только возвращённых элементов, и следующая сдача несёт только их.
В первой версии можно упростить до «принять или вернуть всю сдачу целиком» (§13,
вопрос 1).

### 4.3. Возврат на более ранний этап

Проверяющий этапа 4 видит, что проблема в раскадровке с этапа 2. Нужно действие
«Переоткрыть этап 2»: этап 2 возвращается в `changes_requested`, зависящие от него
этапы уходят обратно в `waiting`, а их текущая работа сохраняется как есть. Правило
для того, что уже сделано на этапах 3–4, — открытый вопрос (§13, вопрос 2).

### 4.4. Передача дальше

При приёмке сайт копирует файлы принятой сдачи из `_review/vN/` в `IN/<слот>/`
каждого следующего этапа и записывает, откуда каждый файл пришёл (§5). Копия, а не
ссылка, по трём причинам:

- у каждого этапа своя граница доступа, и ссылка на чужой проект её пробила бы;
- конвейер и десктоп-синхронизация работают с файлами в своём проекте, ссылку они не
  поймут;
- в R2 копия дешёвая: `CopyObject` на сервере, без трафика через сайт.

Место под копии учитывается в объёме владельца. Сколько хранить старые `vN` —
вопрос 6 в §13.

## 5. Как выход связывается с входом

Это ядро всей конструкции: «вот этот файл в `OUT` получен вот из этого исходника».
Путей три, и для каждого связь своя.

### 5.1. Обработка на нашей машине — связь уже есть

Задача конвейера хранит `source_key` (элемент `IN`), `taskDone` дописывает в неё
`outFiles`, а id задачи сквозной до архива статистики
([PIPELINE.md §11.5 и §15](./PIPELINE.md)). Нужен только крючок: если проект задачи —
этап производства, то `taskDone` создаёт записи выхода для элемента с
`origin = 'machine'` и `task_id`. Угадывать по именам не нужно.

Сюда же относятся AE и Moho, если их запускает программа по графу этапа: для сайта
это та же задача с тем же отчётом.

### 5.2. Работа в инструменте сайта — связь по источнику

Инструмент подключён к папке элемента, поэтому его экспорт кладётся с привязкой к
элементу, `origin = 'tool'`.

### 5.3. Ручная работа — связь по действию, а не по имени

Человек скачал входы, поработал у себя в AE и заливает результат. Два способа, оба
нужны:

1. **Через карточку элемента** (основной). На странице этапа у каждого элемента
   есть «Залить результат» и зона перетаскивания. Связь задаётся тем, куда человек
   положил файл, и ошибиться тут нельзя.
2. **Прямо в `OUT`** (кабинетом, десктоп-синхронизацией). Сайт сопоставляет по
   имени: элемент верхнего уровня в `OUT`, чьё имя совпадает с именем элемента входа
   или начинается с него (`shot_012.mov` → `shot_012_v2_final.mp4`). Машина строит
   имена результатов из `$curItemName`, поэтому правило согласовано с тем, как уже
   называются файлы. Всё, что не сопоставилось, показывается на этапе как
   **«непривязанные»**, и человек разносит их по элементам вручную. Сдать этап с
   непривязанными файлами нельзя.

### 5.4. Цепочка происхождения

У элемента хранится `upstream_file_id`, то есть файл сдачи предыдущего этапа, из
которого он пришёл. У файла сдачи хранится элемент. Отсюда «откуда взялся финальный
ролик» — это проход по ссылкам назад до исходника, без отдельной таблицы.

## 6. Люди и права

### 6.1. Как человек попадает в этап

Это пути из [COMPANY_ACCOUNTS_PLAN §8.1](./COMPANY_ACCOUNTS_PLAN.md):

| путь | роль в проекте этапа | `project_members.via` |
| --- | --- | --- |
| назначен исполнителем | `editor` | `production` |
| назначен проверяющим | `commenter` | `production` |
| назначен наблюдателем | `viewer` | `production` |
| тегнули в чате этапа | `commenter` | `mention` |
| расшарили вручную | как выбрали | `share` |

Колонка `via` добавляется этим планом (в §8.4 плана компаний она названа
`pipeline`, здесь используется `production`, чтобы не путать с конвейером). Выход из
чата снимает участие `mention`, но не `production`: иначе этап молча теряет
исполнителя.

Правило «тегнуть — значит пригласить» подчиняется тем же правам, что «Поделиться»:
звать может `full` и владелец. У `editor` тег не-участника превращается в запрос
владельцу.

### 6.2. Новая ступень `commenter`

Между `viewer` и `editor`: читает всё, пишет в чат и ставит пометки, файлы не
трогает. Сейчас `writeChat` и `writeFiles` открываются одной ступенью
([lib/project-roles.ts](../lib/project-roles.ts)), и развести их нужно в первую
очередь. Правка мелкая, но касается матрицы, которую импортирует и интерфейс.

### 6.3. Право принимать — не роль в проекте

«Принять» и «Вернуть» может тот, кто записан проверяющим **этого этапа**
(`production_step_people.role = 'reviewer'`), независимо от роли в проекте.
Владелец шаблона может всё. Если зашить приёмку в лестницу ролей, `full` смог бы
принимать собственную работу.

## 7. Чат этапа

Отдельный канал, как решено в [COMPANY_ACCOUNTS_PLAN §12.2](./COMPANY_ACCOUNTS_PLAN.md):
`project_chat_messages` уезжает в YouGile к нашей поддержке, и внутренняя переписка
компании туда попадать не должна.

- **Участники чата = участники проекта этапа.** Одного списка достаточно, второй
  однажды разошёлся бы с доступом к файлам.
- **Прочтение отмечается на каждого человека** (`production_reads(step_id, user_id,
  last_read_id)`), а не «прочитал один — прочитали все», как в поддержке.
- **Системные сообщения** о действиях из журнала: «Анна взяла в работу», «Отправлено
  на проверку v2 (3 элемента)», «Принято», «Возвращено: 4 пометки». Уведомление
  проверяющему — это и есть такое сообщение плюс web push (он уже есть,
  `lib/push.ts`).
- **Пометка ревью в чате** выглядит как карточка с кадром-миниатюрой и таймкодом, по
  клику открывается ревью на этом кадре.
- **Упоминания** `@имя`: для участника это уведомление, для не-участника приглашение
  (§6.1).
- Доставка: сначала опрос, как в текущем чате, плюс push. Отдельного канала вроде SSE
  или WebSocket на сайте сейчас нет, его стоит добавить позже, одним каналом на все
  чаты пользователя. Процесс долгоживущий под pm2, SSE он выдержит.

«Мои задачи» — входящие этапы, где человек исполнитель или проверяющий и от него
ждут действия. Непрочитанные чаты там же.

## 8. Ревью: инструмент по типу Frame.io

### 8.1. Видео (первая очередь)

- Плеер: кадр вперёд и назад, `J/K/L`, таймкод `HH:MM:SS:FF`, скорость.
  Покадровая точность держится на `requestVideoFrameCallback` и fps файла.
- **Пометка = комментарий + момент + рисунок.** На паузе поверх кадра рисуются
  перо, стрелка, прямоугольник, овал и текст. Рисунок хранится вектором (SVG) в
  **нормированных координатах 0..1**, поэтому он совпадает на любом размере экрана и
  на прокси другого разрешения.
- Комментарий можно привязать к диапазону (от–до), а не только к кадру.
- Маркеры пометок на таймлайне, список пометок сбоку, ответы в ветке, галка
  «исправлено».
- **Версии:** переключатель `v1 / v2 / …` у элемента. Пометки остаются на своей
  версии. Сравнение рядом или шторкой — позже.

### 8.2. Картинки (первая очередь)

То же без времени: рисунок и комментарий на изображении, зум и панорама.

### 8.3. Прокси

Браузер не играет ProRes, DNxHD и большинство `.mov` из AE, а многогигабайтный
оригинал на ревью не нужен. Нужна лёгкая копия H.264 MP4 с известным fps.

- **Первая версия:** играем то, что браузер умеет. Если не умеет, показываем
  «нужно прокси» и ссылку на скачивание.
- **Затем:** при сдаче сайт ставит задачу конвейера «сделать прокси» (ffmpeg на
  машине парка) и кладёт результат в `_review/vN/.proxy/`. Там же `ffprobe` отдаёт
  fps и длительность. Новой инфраструктуры для этого не нужно, это обычная задача
  очереди.

### 8.4. Аудио и текст (потом, держим в голове)

- **Аудио:** выделить участок на волне и написать комментарий. Разбор пиков и
  отрисовка волны уже есть в редакторе титров (`lib/tools/dialog/peaks.ts`,
  `timeline.ts`).
- **Текст:** выделить фрагмент и поставить тег или комментарий. Разметка
  `<фрагмент>[…, "тег"]` уже описана в [TOOLS_FOLDER_ASSEMBLY_PLAN.md](./TOOLS_FOLDER_ASSEMBLY_PLAN.md).

Модель пометки общая для всех видов: `anchor` (время, диапазон, область, фрагмент
текста) + `shapes` + текст. Новый вид файла добавляет новый вид якоря, а не новую
таблицу.

## 9. Где это живёт в интерфейсе

### 9.1. Отдельное рабочее место, а не вкладка

В кабинете появляется переключатель верхнего уровня: **«Проекты» | «Производство»**.

- **Проекты** остаются как есть: личные и расшаренные проекты, инструменты, архив,
  корзина. Проекты этапов сюда **не попадают** (`group_name = 'production'`
  отфильтровывается), поэтому двадцать роликов по шесть этапов не засыпают список.
- **Производство** — отдельный маршрут `/account/production` со своей раскладкой.
  Вкладкой рядом с «Инструментами» (`ProjectTab` в
  [workspace-context.tsx](../components/account/workspace/workspace-context.tsx))
  его делать не стоит: рабочее пространство проектов построено вокруг файлового
  браузера, а здесь центр — чат и ревью.

Раскладка «Производства»:

```
┌──────────────────┬───────────────────────────────┬──────────────────┐
│ Мои задачи    3  │  Ролик «Промо 12» › Анимация  │  Чат этапа       │
│ Ролики           │  ┌─────────────────────────┐  │                  │
│  Промо 12        │  │  плеер / картинка       │  │  Анна: взяла     │
│   ● Сценарий  ✓  │  │  + пометки поверх       │  │  ▸ v2 на проверке│
│   ● Анимация  ◐  │  └─────────────────────────┘  │  [кадр 00:12:04] │
│   ○ Монтаж       │  элементы: shot_01 ✓ shot_02 ✗│                  │
│  Промо 13        │  [Скачать входы] [Сдать]      │  @Иван посмотри  │
│ Шаблоны          │  граф ролика (свернуть)       │  ________________│
└──────────────────┴───────────────────────────────┴──────────────────┘
```

Слева — «Мои задачи» (этапы, где от меня ждут действия) и ролики с этапами и
счётчиками непрочитанного, как список чатов в мессенджере. В центре — этап: файлы,
ревью, кнопки действий. Справа — чат этапа. На телефоне три колонки становятся
тремя экранами, как в [mobile-view.tsx](../components/account/workspace/mobile-view.tsx).

Инструменты (титры, озвучка) открываются **внутри этапа**, подключённые к его
папке, а не через раздел «Инструменты».

### 9.2. Связь с переключателем профилей

[MULTI_COMPANY_PROFILES_PLAN.md](./MULTI_COMPANY_PROFILES_PLAN.md) добавляет в шапку
переключатель профиля (Личное / компания). Он и переключатель «Проекты |
Производство» независимы: профиль выбирает, **чьё** рабочее место, а переключатель —
**какое**. В каждом профиле своё производство.

## 10. Технологии и библиотеки

### 10.1. Новые зависимости

| библиотека | зачем | почему она |
| --- | --- | --- |
| `@xyflow/react` | редактор шаблона и граф ролика | та же, что в программе; ноды со слотами (handles) из коробки |

### 10.2. Что сознательно не берём

| не берём | чем заменяем |
| --- | --- |
| video.js, Plyr, react-player | нативный `<video>` + `requestVideoFrameCallback`: нужны покадровый шаг и свой слой поверх кадра, а обёртки плееров в этом только мешают |
| Konva, Fabric.js | SVG-слой поверх кадра: фигур немного, их нужно хранить вектором в 0..1, а canvas-движок добавил бы ещё одну модель сцены |
| HLS, DASH | прогрессивный MP4-прокси: R2 отдаёт `Range`, перемотка работает сразу |
| socket.io, Pusher, Ably | SSE обычным роутом Next + `LISTEN/NOTIFY` Postgres через уже подключённый `pg`; процесс один и долгоживущий |
| wavesurfer.js (на будущее, аудио) | свои `peaks.ts` / `timeline.ts` из редактора титров |
| редактор с упоминаниями (Tiptap и т. п.) | `textarea` + выпадающий список по `@` |

## 12. Модель данных

Черновик. Колонки уточняются на этапе реализации, но форма такая.

```sql
production_templates (
  id, owner_user_id, name, graph JSONB, revision INT,
  created_at, updated_at, deleted_at
)

production_runs (
  id, template_id, owner_user_id, name,
  graph_snapshot JSONB,                -- копия графа на момент запуска
  status  -- active | done | cancelled
  created_by, created_at, finished_at
)

production_steps (
  id, run_id, node_id,                 -- node_id из графа
  project_id → projects,               -- проект этапа
  status  -- waiting | ready | in_progress | in_review | changes_requested | approved
  started_by, started_at, started_implicitly BOOL,
  approved_at
)

production_step_people (
  step_id, user_id,
  role  -- executor | reviewer | watcher
  PRIMARY KEY (step_id, user_id, role)
)

production_items (
  id, step_id, name,                   -- элемент верхнего уровня IN
  source_file_id,                      -- строка каталога во входе этапа
  upstream_file_id,                    -- файл сдачи предыдущего этапа (NULL для ручной заливки)
  status  -- pending | in_review | changes_requested | approved
)

production_submissions (
  id, step_id, version INT,            -- v1, v2, …
  submitted_by, submitted_at, note,
  decided_by, decided_at,
  status  -- pending | approved | changes_requested | superseded
)

production_submission_files (
  id, submission_id, item_id,
  file_id,                             -- замороженная копия в _review/vN
  proxy_file_id,                       -- NULL, пока прокси нет
  origin  -- machine | tool | manual
  task_id,                             -- для origin = machine
  item_status  -- pending | approved | changes_requested
)

production_review_comments (
  id, submission_file_id, parent_id,   -- ветка ответов
  author_id, body,
  anchor JSONB,                        -- { t, frame, tEnd } | { region } | { text range }
  shapes JSONB,                        -- вектор, координаты 0..1
  resolved_by, resolved_at, created_at
)

production_messages (
  id BIGSERIAL, step_id, author_id,
  kind  -- text | system | review_ref
  body, payload JSONB, created_at, edited_at, deleted_at
)

production_reads (step_id, user_id, last_read_id)

production_events (
  id BIGSERIAL, run_id, step_id, actor_user_id,
  kind  -- step_started | submitted | approved | changes_requested | reopened | assigned | invited …
  payload JSONB, at
)

-- правка существующего
ALTER TABLE project_members ADD COLUMN via TEXT NOT NULL DEFAULT 'share';  -- share | production | mention
-- project_members_role_check: + 'commenter'
```

Замечания:

- `company_id` в таблицах **нет**: компания выводится через владельца, как везде
  ([COMPANY_ACCOUNTS_PLAN §16](./COMPANY_ACCOUNTS_PLAN.md)).
- `production_events` пишется из одной функции на каждый переход статуса, в одной
  транзакции с самим переходом. Системное сообщение в чат строится из события, а не
  пишется отдельно.
- Код, который читает новые таблицы, и миграция выкатываются вместе: dev-сервер
  работает на боевой базе, и чтение несуществующей таблицы кладёт страницу.

## 13. Открытые вопросы

Нужны ответы до начала соответствующего этапа работ, поэтому у каждого вопроса стоит
номер этапа.

1. **Приёмка по элементам или всей сдачей?** По элементам удобнее для шотов, всей
   сдачей проще сделать. Предлагаю в этапе 1 делать приёмку всей сдачей, а таблицы
   сразу завести под элементы. *(этап 1)*
2. **Переоткрытие раннего этапа.** Что происходит с уже принятыми этапами после
   него: они сбрасываются в `waiting` целиком или только их затронутые элементы?
   *(этап 1)*
3. **Кто может править граф ролика, который уже идёт** (добавить этап, поменять
   проверяющего)? Людей менять можно наверняка. А структуру? *(этап 1)*
4. **Внешний проверяющий без аккаунта** (заказчик по ссылке, как в Frame.io)?
   Потребуется гостевой доступ к одной сдаче по токену. Это новая граница
   безопасности. *(этап 3)*
5. **Раздел только для компаний или для всех?** Технически разницы нет, это
   выключатель. *(этап 0)*
6. **Сколько хранить старые версии `_review/vN`** и копии входов? Это прямой объём
   R2 у владельца. *(этап 2)*
7. **Нужны ли сроки и просрочки** в первой версии? *(этап 5)*
8. **Проверка у этапа обработки:** по умолчанию включена или выключена? *(этап 4)*

## 14. Порядок работ

Каждый этап даёт то, чем уже можно пользоваться. Раздел закрыт выключателем
`production` до конца этапа 3.

### Этап 0. Решения и заготовки

- Утвердить название (§1) и ответить на вопросы 1, 2, 3 и 5 из §13.
- Выключатель раздела ([FEATURE_FLAGS.md](./FEATURE_FLAGS.md)).
- Ступень `commenter` и колонка `project_members.via`. Выход из чужого проекта для
  любой роли ([COMPANY_ACCOUNTS_PLAN §8.3](./COMPANY_ACCOUNTS_PLAN.md)) — полезно
  уже сейчас, независимо от производства.

### Этап 1. Каркас: шаблон → ролик → этапы, ручной путь

- Таблицы §12 без комментариев ревью и без чата.
- Редактор шаблона на `@xyflow/react`: ноды «Старт», «Этап», «Финал», слоты, связи,
  люди на этапе.
- «Новый ролик»: заводит проекты этапов (`group_name = 'production'`), папки,
  участников, заливку исходников в «Старт».
- Страница этапа: входы, выходы, «Скачать входы» (архивом), заливка результата в
  карточку элемента, «непривязанные».
- Кнопки «Взять в работу», «Отправить на проверку», «Принять», «Вернуть» с
  комментарием. Заморозка в `_review/vN`, передача в следующие этапы, журнал.
- Доска роликов: строки — ролики, столбцы — этапы, в ячейке статус и кто взял.

### Этап 2. Чат этапа и уведомления

- Сообщения, прочтение на человека, системные сообщения из журнала.
- Упоминания и приглашение по тегу.
- Web push проверяющему при сдаче и исполнителю при возврате.
- «Мои задачи».

### Этап 3. Ревью видео и картинок

- Плеер с покадровой навигацией, пометки с рисунком, ветки, «исправлено».
- Картинки: те же пометки без времени.
- Версии у элемента, карточка пометки в чате.
- Первая версия без прокси (§8.3).

### Этап 4. Машины и инструменты

- Этап обработки: `options.json` из шаблона в проект этапа, слежение включено.
  Крючок в `taskDone` создаёт выходы (§5.1).
- Прокси для ревью задачей конвейера.
- Этап с инструментом: экземпляр инструмента, подключённый к этапу.

### Этап 5. Дальше

- Статистика по этапам: время в работе, время на проверке, число возвратов, кто.
  Всё это есть в `production_events`.
- Сроки, просрочки, напоминания.
- Сравнение версий, ревью аудио, теги в тексте.
- Внешний проверяющий по ссылке.
- «Финал» → постинг ([SOCIAL_POSTING_PLAN.md](./SOCIAL_POSTING_PLAN.md)).

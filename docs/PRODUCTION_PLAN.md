## 0. Одной фразой

Автор настраивает **пайплайн** — рельсы производства: этапы, связи между ними,
исполнителей и проверяющих. На каждый этап один раз заводится папка-проект и
расшаривается нужным людям. Кнопка **«Новый ролик»** запускает производство по этим
рельсам: в папке каждого этапа появляется подпапка ролика, а у каждого этапа —
новый чат. Человек видит в разделе **«Производство»** только свои этапы ролика и
общую схему — на каком этапе сейчас производство. Этап берут в работу, сдают на
проверку, проверяющий принимает или возвращает. Принятое ложится в финальную папку
этапа и уходит дальше, когда следующему этапу собрано всё нужное. Готовый ролик
уходит в архив вместе с чатами.

## 1. Названия

| что                                   | в интерфейсе                                   | в коде                            |
| ------------------------------------- | ---------------------------------------------- | --------------------------------- |
| Закладка в кабинете                   | **«Производство»** (рядом с «Проектами»)       | маршрут `/account/production`     |
| Рельсы: этапы, связи, люди            | **«Пайплайн»**                                 | `production_pipelines`            |
| Запуск пайплайна под конкретный ролик | **«Ролик»**                                    | `production_runs` (`run`)         |
| Узел пайплайна                        | **«Этап»**                                     | `node` в графе, `step` в таблицах |
| Этап конкретного ролика               | «Этап ролика» — то, что человек видит в списке | `production_run_steps`            |

**Код нового инструмента живёт в пространстве `production`** (`lib/production/`,
`production_*`, `/api/production/*`), а не `pipeline`. Слово `pipeline` в коде уже
принадлежит очереди автообработки ([lib/pipeline/](../lib/pipeline/), `tasks`,
контракт с `fs.manager.tauri` в [PIPELINE.md](./PIPELINE.md)), и два разных
`pipeline` в одном репозитории гарантированно перепутаются.

Существующий раздел называется в интерфейсе «Конвейер», и по-русски это то же
слово, что «пайплайн». Чтобы у людей не было двух синонимов для разных вещей,
подпись «Конвейер» меняется на **«Обработка»**. Это около 15 строк словаря
([components/account/i18n.tsx](../components/account/i18n.tsx)) и справка. Код,
таблицы и контракт с машинами не меняются.

## 2. Уровни и папки

### 2.1. Три уровня в данных, два в интерфейсе

```
Пайплайн (рельсы)               production_pipelines      ← настраивается один раз
  ├─ этап пайплайна             production_pipeline_steps ← один проект-папка на этап, расшарен людям этапа
  └─ версия структуры           production_pipeline_versions ← v1, v2…: фиксируется при изменении структуры
Ролик                           production_runs           ← «Новый ролик» по текущей версии, привязан к ней навсегда
  └─ этап ролика                production_run_steps      ← подпапка ролика в проекте этапа + свой чат
```

Человек, который работает, пайплайн как отдельный уровень не видит. У него в
«Производстве» список роликов, под каждым роликом — только его этапы (эскиз, §9).
Пайплайны как отдельный список видят только те, кто их настраивает и запускает.

### 2.2. Этап пайплайна = проект, ролик = подпапка

**Проект заводится на этап пайплайна, а не на этап каждого ролика.** Папки
создаются и расшариваются один раз, при активации пайплайна. Новый ролик новых
проектов не заводит, он кладёт свою подпапку в каждый проект этапа.

Почему этап — это проект: всё нужное уже работает на уровне проекта.

| что нужно этапу         | что уже есть у проекта                                            |
| ----------------------- | ----------------------------------------------------------------- |
| своя папка-хранилище    | проект и есть папка в R2 с каталогом `project_files`              |
| раздать людям с правами | `project_members`, «Поделиться»                                   |
| скачать всё разом       | архив папки ([lib/storage/archive.ts](../lib/storage/archive.ts)) |
| залить вручную          | заливка кабинета и десктоп-синхронизация                          |
| обработка на машине     | конвейер следит за `IN` проекта и сам создаёт задачи              |
| инструменты сайта       | источник инструмента = проект + папка                             |
| кто платит              | владелец проекта, «отдал доступ — платишь ты»                     |

Права на подпапки в хранилище не существуют, и заводить их не нужно. Исполнители
этапа — это одни и те же люди для всех роликов, поэтому доступ к проекту этапа
целиком им и нужен. Гость, позванный в чат одного ролика, получает доступ **только к
файлам этого ролика на этом этапе** через участие в чате, а не через проект (§6.1).

Следствия:

- **Все проекты пайплайна принадлежат его автору.** В личном кабинете это сам
  человек, в компании — тоже сам автор. У разных людей одной компании разные
  пайплайны. Передача файлов между этапами идёт внутри одного владельца, поэтому
  ограничение цепочек «за пределы владельца нельзя» здесь не мешает.
- Проекты этапов **не показываются в «Проектах»** (`group_name = 'production'`,
  колонка без `CHECK`). Они видны только через «Производство».
- Проект называется `<пайплайн> · <NN этап>`.

### 2.3. Три папки этапа (решено 2026-09-30)

У каждого этапа три папки, и пайплайн выставляет их сам — по маскам ноды (§3.4б):

| папка                  | что в ней                                                                                                                                | кто пишет                          |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------- |
| **исходники**          | FINAL предыдущих этапов этого ролика — по ссылке, не копия (§4.4). У первого этапа — то, что загрузили при запуске ролика. Может не быть | никто: только смотреть и скачивать |
| **рабочая (варианты)** | правки и варианты: то, что присылают в чат, и то, что инструмент сохраняет сам при каждом изменении                                      | исполнитель, инструмент, чат       |
| **финальная**          | принятый результат этапа — его и видят следующие этапы                                                                                   | только сайт, при «Принято»         |

Оригинал не трогается никогда: инструмент читает исходники, а изменения пишет в
рабочую папку. Вариант — это и есть содержимое рабочей папки; сохранять его
отдельно не нужно. Экспорт инструмента — отдельная вещь: он скачивает материал
на компьютер человека и к папкам этапа отношения не имеет.

В панели файлов этапа это три вкладки: исходники, «Из чата» (рабочая) и FINAL.
Исходники и FINAL — только для чтения.

**Машинный этап — исключение:** машина работает с `IN/<ролик>`, поэтому исходники
туда **копируются** (обработка может удалить исходник), а результат машины
(`taskDone`, §5.1) ложится в рабочую папку и приходит в чат вариантом.

Все копии делаются внутри R2 ([lib/storage/copy.ts](../lib/storage/copy.ts)),
байты через сайт не идут. Копия в `IN` собирается в `IN/-<ролик>`, и `-`
снимается одним переименованием, когда скопировано всё: машина не возьмёт
полусобранную папку.

## 3. Ноды

### 3.0. Типы нод и папки — решено 2026-09-30 (версия 4)

**Правки 2026-10-01 (схема графа 3), главнее текста ниже, где расходятся:**
ноды «Финал» нет — ролик сдан, когда приняты все последние этапы (без исходящих
связей); этап без входов — первый и открывается при запуске; у «Старта» нет связей
и шаблона названия ролика — только люди, сроки и описание (оно видно в окне
запуска); нормы часов нет. Папка этапа — **свой** проект владельца: выбирается из
списка, вводится новым именем или (только в черновике) `$pipelineName`; проект
заводится и расшаривается **при активации**, id пишется в граф. Форма — дерево
строк как у `checkFolder` и сбора элемента на сайте (`lib/tools/element`): название
(префикс имени файла), тип из словаря типов установки, `≥`/`=`, число; подпапка —
строки внутри; файлы в этапе кладутся по слотам с именами `01 Титры - clip.srt`.
Шапки нод цветные, ноды растягиваются по ширине; ввод путей — как автокомплит
программы (история поля в браузере).

Код: `lib/production/graph.ts` (схема графа 2, перевод схемы 1 — `upgradeGraph`),
`masks.ts`, `flow.ts`, `form.ts`, `retention.ts`; редактор — `components/account/production/editor/`.

**Связи.** У каждой ноды один вход слева и один выход справа, связей в каждом
сколько угодно. На вход приходит просто массив файлов — финалы всех предыдущих
этапов; от типов файлов связь не зависит. Этап открывается, когда приняты все входы.

**Общее у этапов.** Шапка — название этапа (по умолчанию — тип ноды, правится).
Строка людей: исполнитель и проверяющий — поиск по кругу людей (§6.1). Папка —
проект владельца пайплайна по имени (по умолчанию `$pipelineName`): есть — берётся,
нет — создаётся при первом запуске ролика; несколько этапов могут писать в одну
папку. Внутри — три пути масками:

- **входная** — пусто: вход по ссылке на финалы предыдущих; задана — финалы
  **копируются** сюда. Структура сохраняется: от пути отрезается всё до финальной
  папки источника (`…/этап1/final/123/4.mp4` → `IN/123/4.mp4`). Файл один — прямо
  в папку; несколько — в подпапку ролика (`IN/<ролик>/123/4.mp4`);
- **версии** — сюда ложатся файлы из чата; временная, чистится по сроку;
- **Final** — только принятый результат, он уходит дальше.

Пути считаются в момент открытия этапа и замораживаются в `production_run_steps.paths`
(там же `projectId`, выбранный при запуске).

**Типы:**

| Тип        | Люди                                                                      | Что происходит                                                                                                                          | Что уходит в Final                                                 |
| ---------- | ------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| Старт      | запускающие (кнопка «Новый ролик»), редакторы (правят всё, включая архив) | описание; шаблон названия ролика; сроки хранения вариантов и промежуточных финалов, 0–30 дней слайдером или вручную, 0 — не удалять     | —                                                                  |
| Инструмент | исполнители, проверяющие                                                  | выбор инструмента вставляет его название в шапку (дальше не связано); в этапе кнопка «Открыть в инструменте»                            | выбранный вариант                                                  |
| Форма      | исполнители, проверяющие                                                  | строки: «файлы» — папка, имя по умолчанию (маски), тип, `≥`/`=`, число; «папка» — путь, заводится сам. У строки своя загрузка           | вся рабочая папка со структурой, только когда выполнены все строки |
| Автоматика | исполнитель — машина; проверяющий — люди или автоматика                   | открывается сама, вход копируется во входную (по умолчанию `IN`); без людей чата нет; у проверяющего «Ещё раз» — вход копируется заново | весь результат (по умолчанию `OUT`) со структурой                  |
| Действие   | нет, чата нет                                                             | пока одно — «скопировать»: финалы предыдущих в свою Final, этап принимается сам                                                         | копия входа                                                        |
| Финал      | —                                                                         | принят вход — ролик сдан                                                                                                                | —                                                                  |

Обработку на машинах и готовность результата автоматики сайт пока не отслеживает
(этап 4): результат принимает проверяющий. Автоматика с проверяющим «автоматика»
до этапа 4 сама не закроется.

**Маски** (`lib/production/masks.ts`; место определяет, что доступно):
`$pipelineName`, `$runName`, `$runTime` (`ММ.ДД-ЧЧ.мм` запуска ролика),
`$stageName`, `$stageNum` (`01`, порядок в пайплайне), `$stageTime` (открытие
этапа), `$prevStageName` (только входная папка и имя файла), `$user` (запустивший;
в имени файла — загрузивший), `$fileName` (только имя файла; расширение всегда
исходное), `$random` / `$random(n)` (по умолчанию 10 символов), `$YYYY $MM $DD $HH
$mm $ss` — момент запуска ролика, по поясу запустившего. В имени папки-проекта —
только `$pipelineName` и `$random`. Папка без `$runName`, `$runTime` или `$random`
— предупреждение: файлы разных роликов смешаются.

**Срок хранения** — от сдачи ролика, одна точка отсчёта для обоих сроков. Не сдан —
не удаляется ничего. Удаление штатное, в корзину. Финал этапов, ведущих в «Финал»,
не удаляется никогда. Сроки — настройка на месте (из черновика).

**Рабочее место.** Вторая колонка — ролики как папки: название, тусклым —
пайплайн, зелёная полоса прогресса; клик раскрывает этапы (не начатые тусклые,
готовые с галочкой). Переключатель «В работе / Готовые, поиск по ролику и
пайплайну. «Новый ролик» — пайплайны тегами, название подставляется по шаблону.
Пайплайны — вкладки «Активные / Архив».

**Доступ к папкам** при запуске только добавляется: папку могут делить несколько
этапов и пайплайнов, поэтому снятие человека с этапа доступ к папке не отзывает.

### 3.1. Чем ноды пайплайна отличаются от нод обработки

В программе нода — это операция над файлом, граф исполняет машина. Здесь нода — это
**этап работы людей или машины**, граф задаёт порядок и то, что передаётся дальше, а
исполняет его сайт по событиям «этап принят».

[PROJECT_OPTIONS_PANEL.md §1](./PROJECT_OPTIONS_PANEL.md) закрыло вопрос редактора
**графов обработки** на сайте. Это другой граф, и то решение он не отменяет: графы
обработки по-прежнему правятся только в программе. Ноды пайплайна придумываются и
рисуются заново, в дизайне сайта.

### 3.2. Нода этапа — две части (решено 2026-09-30)

```
            ┌────────────────────────────────────────────────────┐
 ● вход 1 ─▶│ Анимация                                    ✎      │
 ● вход 2 ─▶│ Исполнители: Анна, Олег │ Проверяющие: Иван        │  ВЕРХ: кто работает
 ⊕ добавить │ Папка: [$pipeline]/[$run]/[animation]               │  и где лежат данные
            │ Исполняет: человек │ машина   Принимает: человек │ авто│
            ├────────────────────────────────────────────────────┤
            │ Инструмент: SRT-редактор                            │  НИЗ: чем работаем
            │   язык ▾   перевод: [метка сервиса] ▾   …           │  и с какими настройками
            │ ☐ копировать вход в папку этапа                     │
            └────────────────────────────────────────────── ● выход (массив файлов)
```

**Верх — кто работает и где хранится.**

- **Название этапа** правится прямо на ноде, как в программе.
- **Исполнители и проверяющие** в одной строке — люди по умолчанию. На них
  расшаривается папка этапа, им приходят уведомления.
- **Папка этапа** — любой путь с вложенностью, собранный масками (§3.4). Это не
  IN: всё, что лежит в IN, забирает конвейер, и ручные этапы забивали бы очередь.
  От выбранной папки дальше считаются все пути этапа. В интерфейсе этапа
  показывается именно она.
- **Исполняет:** человек или машина. «Машина» — не конкретный компьютер, а общая
  очередь обработки: задачу берёт любая свободная машина парка. Тогда папка этапа
  — `IN/<ролик>` принудительно: конвейер следит только за IN.
- **Принимает:** человек (проверяющий, §4.1) или автоматически — результат сразу
  становится финальным и уходит дальше.

**Низ — инструмент и его настройки.**

- Инструмент сайта (SRT-редактор первым) и **пресет**: значения тех настроек,
  которые инструмент разрешил задавать из пайплайна. Какие это настройки, решает
  сам инструмент — у каждого своя схема пресета в реестре (`lib/tools/registry.ts`);
  сейчас её нет ни у одного, добавляется вместе с этапом 1.
- Сервис для инструмента (например, перевода) выбирается **по метке** учётки
  вендора. Отдельного поля «назначение» у сервисов не заводим: в метке пишется
  необходимый минимум.
- У машинного этапа инструмента нет: настройки обработки живут в `options.json`
  папки этапа, как у любого проекта.

### 3.3. Входы и выход — как в программе

Принцип редактора программы (`fs.manager.tauri`: `InputHandle.tsx`,
`useConnection.tsx`, `AddNewPropertyButton.tsx`):

- **Входных хендлеров сколько нужно, в каждый — ровно одна связь.** Новый вход
  добавляется кнопкой «⊕» на ноде. Занятый хендлер новую связь не принимает.
- **Выход один** и несёт массив файлов — FINAL этапа.
- Циклов нет: связь, замыкающая круг, не принимается. Возврат на доработку живёт в
  чате, не в графе.
- **Слияние:** этап ждёт, пока приняты этапы на **всех** его входах.

Благодаря отдельным хендлерам следующий этап знает, какой вход от какого этапа, и
файлы разных источников не смешиваются.

### 3.4. Маски путей — в стиле программы

Пути и имена задаются масками на `$`, в том же стиле, что в программе, но **со
своим набором**: смысл у совпадающих имён тот же (`$fileName` — имя файла без
расширения), остальное — понятия производства.

| маска               | что значит               |
| ------------------- | ------------------------ |
| `$pipeline`         | название пайплайна       |
| `$run`              | название ролика          |
| `$stage`            | название этапа           |
| `$fileName`         | имя файла без расширения |
| `$YYYY` `$MM` `$DD` | дата запуска ролика      |

Набор уточняется; список живёт в одном месте, как `Utils/masks.ts` в программе.

Ввод — как в программе (`ChipAutocompleteProperty.tsx`): начинаешь печатать —
предлагаются варианты; **Tab** вставляет вариант, **Enter** фиксирует сегмент, и он
становится папкой. Путь — массив сегментов, **последний — имя файла**. Путь без
`$run` получает его сам: иначе файлы разных роликов смешаются в одной папке.

### 3.4а. Папки ноды

В верхней части ноды — три пути, собранные масками (§3.4):

- **исходники** — по умолчанию FINAL этапов на входах; менять не нужно;
- **рабочая** — по умолчанию `$pipeline/$run/$stage/work`;
- **финальная** — по умолчанию `$pipeline/$run/$stage/final`.

Пути считаются от папки этапа. Для каждой новой ноды пайплайн заполняет их сам;
правят их, только если проекту нужна своя раскладка. Правила для конкретного
инструмента (что именно он пишет в рабочую и что кладёт в финальную при
«Принято») вырабатываются для каждого инструмента отдельно — со временем.

### 3.4б. Схема ролика: автоматика обводкой

Жёлтая левая половина кружка — исполняет машина; жёлтая правая — принимается
автоматически; обе — этап полностью автоматический.

### 3.5. Жизнь пайплайна: версии вместо дублей

Пайплайн — это оригинал. Каждый ролик запускается по **версии** оригинала,
которая действовала в момент запуска, и живёт по ней до конца. Хранятся все
версии, по которым есть ролики.

- **Черновик.** Граф правится свободно, папки ещё не созданы.
- **Активация.** «Активировать» создаёт проекты этапов, расшаривает их людям этапов
  и фиксирует **версию 1**. По пайплайну можно запускать ролики.
- **Настройки правятся на месте**, новую версию они не создают: нормы сроков
  (§4.8), срок хранения версий файлов (§4.5), люди этапов (добавить или снять
  исполнителя, проверяющего, наблюдателя — доступ к папке этапа обновляется сразу).
  Правка действует и на ролики, которые уже идут.
- **Изменение структуры** (добавить или убрать этап, слот, связь) правится в том
  же оригинале. Сохранение фиксирует **новую версию**. Новые ролики идут по ней,
  уже запущенные — по своей старой версии, пока не закончатся или пока их не
  отменит проверяющий или автор (§4.7). Дублировать руками ничего не нужно.
- **Папки при смене версии:**
    - этап, который есть в обеих версиях, работает с той же папкой (id ноды
      сохраняется между версиями);
    - новый этап получает новую папку при сохранении версии;
    - убранный этап сохраняет папку, пока по старой версии идут ролики. Когда их не
      осталось, папку предлагается удалить отдельным шагом.
- **«Дублировать»** остаётся отдельным действием, когда нужен **другой** пайплайн
  на основе этого, например под другой тип ролика. У дубля свои папки и своя
  история версий.
- **Архив** убирает пайплайн из списка для «Нового ролика». Идущие ролики
  продолжаются.
- **Папки этапов уходят в архив вместе с пайплайном** (`projects.is_archived`), но
  не раньше, чем закончится последний его ролик. Архивный проект конвейер
  пропускает ([reference/08-pipeline.md §1](./reference/08-pipeline.md)), поэтому,
  если заархивировать папки сразу, этапы обработки у идущих роликов встанут. Пока
  ролики идут, у пайплайна статус «в архиве, доживает», и папки архивируются сами,
  когда последний ролик завершён или отменён. Возврат пайплайна из архива
  возвращает и папки. Удалить пайплайн, по которому ещё идут ролики, нельзя: сначала в
  архив, удаление — когда его ролики завершены или отменены.

### 3.6. Чем рисовать

`@xyflow/react` для редактора пайплайна и для схемы ролика только на чтение
(`@dagrejs/dagre` раскладывает её автоматически). Граф хранится JSON-ом с `revision`
и оптимистической блокировкой, как общие словари (`UPDATE … WHERE revision = $base`,
иначе 409). Общего кода с редактором программы нет (стек сайта — Tailwind + Radix,
программа на MUI, см. то же §1 PROJECT_OPTIONS_PANEL).

## 4. Жизненный цикл этапа ролика

### 4.1. Статусы и кнопки

**Решено 2026-09-29: кнопка одна — «Принято».** Вся работа над этапом идёт в
его чате (§7): исполнитель присылает варианты сообщениями с файлами, проверяющий
смотрит их там же и там же пишет, что поправить. Файлы из сообщений чата
складываются в рабочую папку этапа (§2.3) — отдельной заливки нет.

```
open ─► approved
```

- **Кнопки «Взять в работу», «Отказаться», «На проверку», «На доработку» убраны.**
  Цикл «сдал — вернули — сдал снова» живёт в чате, а не в статусах.
- **«Принято»** стоит в шапке этапа в одной строке с людьми, справа от списка
  проверяющих: это их кнопка. Нажать её может проверяющий этапа (§6.3); у
  остальных она видна, но погашена.
- **Исполнитель отмечает себя сам**: выбирает своё имя в выпадающем списке
  «Исполнители». Отметка — не «занял этап», а «я его делаю»: по ней человек
  числится исполнителем во всех отчётах. Отметиться могут несколько человек,
  снять отметку можно тем же пунктом. Отметить другого нельзя.
- Исполнители и проверяющие — выпадающие списки; по умолчанию их заполняет
  пайплайн, в каждый можно добавить человека.

**Решено 2026-09-30: версий как понятия нет — это просто файлы.** Исполнитель
кладёт результат как обычно — вложением в сообщение чата. У проверяющего лента
сообщений, и последний вариант он смотрит там же, с превью, при необходимости в
отдельном окне ревью (§8). Файл из сообщения ложится в папку этапа ролика, но
номеров v1, v2 у него нет: в панели файлов это вкладка «Из чата», файлы по
времени, с автором. Главное требование — превью в чате для видео и картинок.

**Решено 2026-09-30: что ложится в `FINAL`.** Выбирает проверяющий. «Принято» в
шапке этапа принимает последний присланный в чат вариант — его имя видно в
подсказке к кнопке. Принять более ранний — пунктом «Принять этот вариант» в меню
«⋯» у файла: во вкладке «Из чата» и у вложения в самом сообщении. Принятый файл
отмечен галочкой и лежит во вкладке FINAL.

Шапка этапа — схема, люди и «Принято» — закреплена: прокручиваются только
файлы и чат. На телефоне колонки роликов нет; выбор ролика там будет отдельным
экраном.

**Пересмотреть под это решение:** §4.2 (взять и отказаться — отпадает, остаётся
отметка исполнителя), §4.3 (сдача и возврат — теперь сообщения чата), §6.3
(право принимать — без «На доработку»), §7.1 (выход из чата «пока не нажмёт
«Отказаться»», системные сообщения), §9.1 (эскиз с тремя рядами кнопок), §12
(`taken_by` и статусы в модели данных). Ниже эти разделы пока в прежнем виде.

После «Принято» у следующего этапа загорается «Взять в работу», если ему собрано
всё (§3.3). Чат принятого этапа не закрывается: в него можно вернуться, задать
вопрос, продолжить обсуждение.

### 4.2. Взять в работу и отказаться

> ⚠ **Устарело** решениями 2026-09-29/30 (§4.1, §2.3): кнопки сведены к «Принято»,
> варианты идут через чат в рабочую папку. Оставлено до переписывания раздела.

- Как только этап готов (`ready`), **любой** его исполнитель может взять его в
  работу. Нажатие фиксирует, кто и когда взял. У остальных исполнителей кнопка
  становится «В работе · <имя>».
- **Остальным исполнителям отключаются уведомления и слежение** за этим этапом: из
  чата они не выходят, видят его, но не получают пушей и счётчиков. Включить обратно
  каждый может сам (§7.3).
- **«Отказаться»** возвращает этап в `ready`. Кнопка снова активна у всех
  исполнителей, всем им приходит уведомление, слежение включается обратно. Отказ
  тоже фиксируется. Отказаться может **взявший этап, автор пайплайна и суперадмин
  сайта**. Автору это нужно, чтобы снять этап с человека, который заболел или
  пропал. Отказ за другого пишется в журнал с именем того, кто его сделал.
- **Отказаться можно и после «На доработку».** Следующий исполнитель продолжает с
  того, что лежит в `OUT/<ролик>`. Что не лежит в `OUT` (исходники из AE, рабочие
  файлы), прежний исполнитель передаёт через чат, в том числе архивом (§7.1).
- **Исполнитель ушёл из компании или его аккаунт удалён.** Взятый им этап
  автоматически возвращается в `ready`, как при отказе. Остальным исполнителям
  приходит уведомление, в журнал пишется причина.
- **Автоматический старт.** Этап со стартом «автоматически» не ждёт кнопки: как
  только собраны входы, он переходит в `in_progress`, в журнал пишется «запущено
  автоматически». Этап обработки на этом шаге просто открывает `IN/<ролик>`, и
  конвейер сам ставит задачу машине.
- Если исполнитель забыл нажать «Взять в работу» и сразу залил результат, этап
  берётся им неявно при первой заливке, с пометкой в журнале.

### 4.3. На проверку, на доработку, принято

> ⚠ **Устарело** решениями 2026-09-29/30 (§4.1, §2.3): кнопки сведены к «Принято»,
> варианты идут через чат в рабочую папку. Оставлено до переписывания раздела.

- **«На проверку»**: содержимое `OUT/<ролик>` копируется в `VERSIONS/<ролик>/vN`,
  этап переходит в `in_review`, проверяющим приходит уведомление, в чат — системное
  сообщение с версией.
- **«На доработку»**: проверяющий пишет, что поправить (текстом в чате и пометками
  на файлах, §8). Этап возвращается к взявшему, следующая сдача будет `v(N+1)`.
- **«Принято»**: сдача принимается **целиком**. Принятая версия копируется в
  `FINAL/<ролик>`, этап решён, дальше работает передача (§4.4).
- **Фиксируется принятое решение, остальные версии тоже остаются**: v1, v2 и так
  далее вместе с пометками лежат в `VERSIONS` и в журнале, пока их не уберёт срок
  хранения (§4.5).

### 4.4. Передача дальше (решено 2026-09-30)

**По умолчанию — ссылка, а не копия.** Следующий этап показывает FINAL
предыдущих как свой вход: смотреть и скачивать можно, добавлять и удалять —
нет. Копий меньше, места тоже.

**Копия — только там, где файлы должны лежать физически в папке этапа:**

- у машинного этапа — всегда: машина работает с папкой `IN/<ролик>`, и обработка
  может удалить исходник;
- у остальных — галочкой «копировать вход в папку этапа» в нижней части ноды.

Копия собирается в `IN/-<ролик>`, и `-` снимается одним переименованием, когда
скопировано всё: машина не возьмёт полусобранную папку.

**Цена ссылки — производное право:** участник этапа ролика читает FINAL
непосредственно предыдущих этапов этого же ролика. Это правка медиапрокси и
выдачи списка файлов через таблицы производства, а не новые права на папки.

Когда приняты этапы на всех входах, этап становится доступным, исполнителям
приходит уведомление, в чат — системное сообщение «входы собраны».

**Открыто:** куда инструмент сохраняет варианты и финальный результат, если у
этапа указана своя папка, и как выглядит финальный результат при нескольких
файлах (галочки и главная кнопка — отложено).

### 4.5. Срок хранения версий

Настройка пайплайна «Промежуточные версии удалять»:

| вариант                                    | что происходит                                                    |
| ------------------------------------------ | ----------------------------------------------------------------- |
| **после завершения ролика** (по умолчанию) | когда принят Финал, рабочие папки ролика во всех этапах очищаются |
| через N дней после приёмки этапа           | удаляются версии этого этапа                                      |
| не удалять                                 | хранятся, пока их не удалят руками                                |

Удаляются только файлы непринятых версий. `FINAL` не трогается никогда: это
результат. Записи в базе (кто сдал, когда, решение, текст пометок) остаются
навсегда: у версии ставится отметка «файлы удалены по сроку», и в истории видно,
что она была и чем закончилась. Удаление идёт фоновой работой хранилища
(`storage_jobs`, вид `purge`) и попадает в корзину по её обычным правилам.

### 4.6. Новая ветка ролика

Бывает, что после приёмки результат на этапе K меняется, и новый вариант должен
пройти все следующие этапы заново. Это **ветка**, как в git:

- от ролика «Промо 12» с этапа K создаётся ролик-ветка «Промо 12 · ветка 2»;
- этапы **до K** в ветке не проходятся заново: их принятые результаты берутся из
  исходного ролика, галочки приёмки остаются как есть;
- этапы **с K и дальше** в ветке — новые, с новыми подпапками и новыми чатами;
- исходный ролик никуда не девается: он готов (или продолжает идти), и его приёмки
  не снимаются.

Первая версия обходится без веток (§14, этап 5). Таблицы сразу закладываются с
`parent_run_id`, чтобы ветки не потребовали переделки.

### 4.7. Архив и отмена

Когда принят Финал, ролик **уходит в архив** у всех участников вместе с чатами.
Ничего не удаляется, только скрывается из списка. Архив открывается фильтром, чаты
в нём читаются и пишутся, ролик можно вернуть из архива.

**Отменить ролик на полпути** может любой его проверяющий (любого этапа) и автор
пайплайна. Отменённый ролик уходит в архив как есть, со статусом «отменён»: папки,
версии, чаты и журнал остаются. Взятые этапы снимаются, машинные задачи по ролику,
которые ещё стоят в очереди, отменяются.

### 4.8. Сроки

Сроки мягкие: они ничего не блокируют, только показывают, где производство
отстаёт.

- В настройках этапа пайплайна задаётся **норма**: сколько часов этап обычно
  занимает. Можно не задавать.
- У этапа ролика срок **считается сам**: время, когда этап стал `ready`, плюс
  норма. Отдельно видно время в работе (от «Взять в работу») и время на проверке —
  они и так пишутся в журнал.
- **Срок ролика** — самый длинный путь по схеме от старта до финала по нормам
  этапов. Он пересчитывается сам на каждом событии: этап приняли раньше — срок
  ролика сдвинулся ближе, задержали — дальше.
- Показывается цветом на схеме и в списке: в норме / скоро / просрочено. Просрочка —
  повод для напоминания в чате этапа и взявшему (одно в сутки, не чаще).
- Руками срок у конкретного ролика не правится: это производная от норм и фактов.
  Если нормы неверные, их правят в настройках пайплайна (§3.5), и сроки
  незавершённых этапов во всех идущих роликах пересчитываются сразу.

## 5. Как выход связывается с входом

Связь не опирается на имена файлов.

### 5.1. Обработка на нашей машине — связь уже есть

Задача конвейера хранит `source_key` (элемент `IN`, то есть `IN/<ролик>`),
`taskDone` дописывает `outFiles`, а id задачи сквозной до архива статистики
([PIPELINE.md §11.5 и §15](./PIPELINE.md)). Нужен только крючок: если проект задачи —
этап пайплайна, `taskDone` создаёт сдачу с этими файлами (`origin = 'machine'`,
`task_id`). Куда именно машина положила результаты и как она их назвала, неважно:
список пришёл в отчёте задачи.

AE и Moho, запущенные программой по графу этапа, для сайта — та же задача с тем же
отчётом.

### 5.2. Ручная работа и инструменты — связь по папке

Всё, что лежит в рабочей папке этапа ролика (§2.3), — варианты этого этапа этого
ролика: вложения из чата и то, что инструмент сохраняет сам. Неважно, как файлы
туда попали. Принятый вариант копируется в финальную папку.

### 5.3. Цепочка происхождения

При каждой копии (приёмка → финальная, передача → `IN`
следующего этапа) пишется связь «из какого файла сделан какой»
(`production_file_links`). По ней от финального ролика можно пройти назад до
исходников, через все этапы и версии.

## 6. Люди и права

### 6.1. Как человек попадает в работу

| путь                        | что получает                                                                                                           | как записано                             |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------- | ---------------------------------------- |
| исполнитель этапа пайплайна | `editor` на проект этапа + участие во всех чатах этапа                                                                 | `project_members.via = 'production'`     |
| проверяющий                 | `commenter` на проект этапа + участие в чатах                                                                          | `via = 'production'`                     |
| наблюдатель                 | `viewer` + участие в чатах без уведомлений                                                                             | `via = 'production'`                     |
| позван в чат ролика         | участие **только в этом чате**: видит его сообщения и файлы этого ролика на этом этапе. Проектного доступа не получает | `production_chat_members.via = 'invite'` |

Звать в чат может любой участник, упоминанием `@имя`, как в мессенджерах и
таск-трекерах. Это не раздача всего проекта, а доступ к одному обсуждению, поэтому
правило мягче, чем у «Поделиться». Круг, из которого можно позвать, закрыт:

- в профиле компании — только люди этой компании;
- в личном профиле — только свои контакты (`share_contacts`), у которых уже есть
  аккаунт.

Позвать человека, которого на сайте нет, нельзя: упоминание не создаёт аккаунт и не
шлёт приглашение на почту. Так чат не превращается в способ раздать файлы кому
угодно.

### 6.2. Ступень `commenter`

Между `viewer` и `editor`: читает всё, пишет в чат и ставит пометки, файлы не
трогает. Сейчас `writeChat` и `writeFiles` открываются одной ступенью
([lib/project-roles.ts](../lib/project-roles.ts)), их нужно развести.

### 6.3. Право принимать — не роль в проекте

«Принято» и «На доработку» может нажать тот, кто записан проверяющим **этого
этапа**, независимо от роли в проекте. Приёмка не зашивается в лестницу ролей:
право принимать даёт назначение на этап, а не уровень доступа к папке.

- **Проверяющих может быть несколько, достаточно одного.** Кто именно проверяет эту
  сдачу, решается в момент проверки: кто первый нажал «Принято» или «На доработку»,
  тот и проверил. Договориться, кто смотрит, можно в чате (сообщением или
  реакцией). Это соглашение между людьми, сайт его не проверяет.
- **Один человек может быть и исполнителем, и проверяющим одного этапа** и
  принять собственную сдачу. В журнале это видно: сдал и принял один и тот же
  человек.

### 6.4. Кто заводит пайплайны

- **В компании** — только тот, кому выдан тег компании `production.manage`.
  Это первый **рабочий** тег (`COMPANY_WORKSPACE_CAPABILITIES` в
  [lib/company-capabilities.ts](../lib/company-capabilities.ts)): в отличие от
  консольных, он выдаётся и рядовому сотруднику, не только админу. Решено
  2026-09-28: пайплайны заводит продюсер, и делать его админом ради одного права
  значило бы открыть ему консоль и журнал. Консоль участнику по-прежнему
  закрыта. При смене роли в компании рабочие теги сохраняются, консольные
  снимаются.
- **В личном профиле** — сам человек, для себя: там раздавать теги некому.
- Раздел «Производство» — пункт в наборе разделов компании: компания может его
  выключить, по умолчанию он включён.

### 6.5. Кто что видит в «Производстве»

- В списке — ролики, где человек участник хотя бы одного чата этапа, и под каждым
  **только его этапы**.
- Схема ролика целиком (этапы, статусы, кто взял) видна всем участникам ролика,
  чтобы все знали, где сейчас производство. Зайти в чужой этап по схеме нельзя,
  если не позвали.
- Список пайплайнов и кнопка «Новый ролик» — у автора и у тех, кого нода «Старт»
  разрешает как запускающих (§9.2).

## 7. Чат этапа

### 7.1. Полноценный внутренний чат

**Два разных чата, их нельзя путать.**

|              | чат проекта                                                                                                                                  | чат этапа пайплайна                                                            |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| что это      | технический чат внутри проекта, в том числе в компаниях                                                                                      | рабочее обсуждение этапа конкретного ролика между исполнителями и проверяющими |
| где хранится | `project_chat_messages`                                                                                                                      | `production_messages`                                                          |
| YouGile      | зеркало включается и выключается компанией (`chatYouGileSync`, [lib/company-chat-gate.ts](../lib/company-chat-gate.ts)); сам чат есть всегда | никогда, выключатель компании на него не влияет                                |
| сколько      | один на проект                                                                                                                               | один на этап каждого ролика                                                    |

Чат проекта этот план не трогает. У проектов этапов он есть, как у любого проекта,
и подчиняется тому же выключателю. Выключатель читается по владельцу проекта, то
есть по компании автора пайплайна. В «Производстве» технический чат не
показывается: там только чат этапа ролика.

| что                          | как                                                                                                                                                                                                                                                                                                                             |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| кто в чате по умолчанию      | исполнители, проверяющие и наблюдатели этапа — автоматически при запуске ролика                                                                                                                                                                                                                                                 |
| добавить человека            | любой участник, через `@имя` в сообщении (§6.1)                                                                                                                                                                                                                                                                                 |
| выйти из чата                | исполнитель — **только когда этап взял в работу кто-то другой**; взявший выйти не может, пока не нажмёт «Отказаться». Гость и наблюдатель — в любой момент. Проверяющий — в любой момент, но **последний проверяющий этапа выйти не может**. Выход снимает только участие в чате; доступ к проекту этапа по назначению остаётся |
| имя отправителя              | имя из профиля, **без почты**                                                                                                                                                                                                                                                                                                   |
| время                        | у каждого сообщения                                                                                                                                                                                                                                                                                                             |
| галочки                      | ✓ отправлено (записано на сервере), ✓✓ прочитано. По наведению — **кто прочитал**                                                                                                                                                                                                                                               |
| реакции                      | эмодзи под сообщением, несколько от разных людей, со списком кто                                                                                                                                                                                                                                                                |
| ответ на сообщение           | цитата со ссылкой на исходное                                                                                                                                                                                                                                                                                                   |
| упоминание `@имя`            | участнику — уведомление; не-участнику — приглашение в чат. Подсказки по `@` — только из своей компании (в профиле компании) или из своих контактов (в личном). Позвать человека, у которого нет аккаунта, нельзя                                                                                                                |
| файлы и картинки в сообщении | любые файлы, **включая архивы** — например, рабочие исходники при передаче этапа другому исполнителю. Лежат в `CHAT/<ролик>` проекта этапа, видны всем участникам чата. Видео и картинки — с превью, по клику — ревью с рисованием (§8); архивы и прочее — скачать                                                              |
| системные сообщения          | «Анна взяла в работу», «Отправлено на проверку v2», «На доработку», «Принято», «Входы собраны» — строятся из журнала                                                                                                                                                                                                            |

### 7.2. Прочтение и доставка

На каждого участника хранится `last_read_message_id`. «Кто прочитал сообщение» —
это участники, у которых отметка не меньше id сообщения. Отдельной строки на пару
«сообщение × человек» нет, поэтому счёт не растёт с длиной переписки.

### 7.3. Уведомления и слежение

У участника три уровня: **все** / **только упоминания и мои кнопки** / **выкл**.
Отдельно — «следить»: выключенное слежение убирает этап из счётчиков непрочитанного.

- Когда этап взяли в работу, остальным исполнителям слежение выключается
  автоматически (§4.2), и каждый может включить его обратно.
- Проверяющему уведомление о сдаче приходит всегда, даже при «только упоминания»:
  это адресованное ему действие.
- Доставка: web push (он уже есть, `lib/push.ts`) и живое обновление открытого
  чата (§10).

## 8. Ревью: инструмент по типу Frame.io

Открывается из чата и из списка файлов этапа, смотрится поверх чата или рядом.

### 8.1. Видео (первая очередь)

- Плеер: кадр вперёд и назад, `J/K/L`, таймкод `HH:MM:SS:FF`, скорость. Покадровая
  точность — `requestVideoFrameCallback` и fps файла.
- **Пометка = комментарий + момент (или диапазон) + рисунок.** На паузе поверх
  кадра рисуются перо, стрелка, прямоугольник, овал и текст. Рисунок хранится
  вектором в **нормированных координатах 0..1**: совпадает на любом экране и на
  прокси другого разрешения.
- Маркеры пометок на таймлайне, список пометок, ответы в ветке, галка «исправлено».
- Пометка публикуется в чат карточкой с кадром и таймкодом. Клик по карточке
  открывает ревью на этом кадре.
- **Версии:** переключатель `v1 / v2 / …`, пометки остаются на своей версии.
  Сравнение рядом или шторкой — позже.

### 8.2. Картинки (первая очередь)

То же без времени: рисунок и комментарий на изображении, зум и панорама.

### 8.3. Прокси

Браузер не играет ProRes, DNxHD и большинство `.mov` из AE, а многогигабайтный
оригинал на ревью не нужен.

- **Первая версия:** играем то, что браузер умеет. Если не умеет, показываем
  «нужно прокси» и кнопку «Скачать».
- **Затем:** при сдаче сайт ставит задачу конвейера «сделать прокси» (ffmpeg на
  машине парка). Результат ложится рядом с версией, `ffprobe` отдаёт fps и
  длительность. Это обычная задача очереди, новой инфраструктуры не нужно.

### 8.4. Аудио и текст (потом, держим в голове)

- **Аудио:** выделить участок волны и написать комментарий. Пики и отрисовка волны
  уже есть в редакторе титров (`lib/tools/dialog/peaks.ts`, `timeline.ts`).
- **Текст:** выделить фрагмент и поставить тег. Разметка `<фрагмент>[…, "тег"]` уже
  описана в [TOOLS_FOLDER_ASSEMBLY_PLAN.md](./TOOLS_FOLDER_ASSEMBLY_PLAN.md).

Модель пометки общая для всех видов: `anchor` (время, диапазон, область, фрагмент
текста) + `shapes` + текст. Новый вид файла добавляет вид якоря, а не таблицу.

- **Переключатель «Проекты | Производство»** в шапке кабинета. «Проекты»
  остаются как есть; проекты этапов туда не попадают. Это отдельный маршрут
  `/account/production`, а не вкладка рядом с «Инструментами»
  ([workspace-context.tsx](../components/account/workspace/workspace-context.tsx)):
  рабочее пространство проектов построено вокруг файлового браузера, а здесь центр —
  этап и чат.
- **Слева** — ролики, под каждым только мои этапы, со счётчиками непрочитанного,
  как список чатов в мессенджере. Сверху фильтр по пайплайну и «Архив».
- **Справа сверху** — схема всего ролика, чтобы все видели, где производство.
- **Под схемой** — название этапа, **кто исполнители, кто взял в работу и с
  какого времени, кто проверяет**, и кнопки (§4.1). Люди стоят рядом с кнопками,
  чтобы сразу было видно, почему у тебя кнопка неактивна.
- **Ниже** — файлы этапа ролика, ещё ниже — чат. Уточнено 2026-09-29: панель
  файлов сворачивается до строки заголовка и тянется по высоте; в ней три папки —
  IN (исходники, может не быть), версии и FINAL. OUT не показывается. IN и FINAL
  только для чтения: их наполняет сайт.
- **Схема ролика** — узкая полоса из кружков без подписей: пустой — не принят,
  зелёный с галочкой — принят; название этапа в подсказке. Растянута на всю
  ширину, линии — горизонталь и вертикаль со скруглёнными поворотами.
  Сворачивается.
- На телефоне колонки становятся экранами, как в
  [mobile-view.tsx](../components/account/workspace/mobile-view.tsx).

### 9.2. Где настраиваются пайплайны и запускаются ролики

- **«Пайплайны»** — отдельный список в том же разделе. Его видит тот, у кого есть
  свои пайплайны или право их заводить (§6.4). Там «Новый пайплайн», редактор графа,
  «Активировать», «Сохранить новую версию», «Дублировать», «В архив».
  На карточке пайплайна — **сколько роликов по нему сейчас в производстве**, с
  разбивкой по версиям, если идут ролики по старым («5 в работе · 2 из них по v1»).
  Число считается выборкой по `production_runs` со статусом `active`, отдельно не
  хранится. Оно же объясняет, почему пайплайн пока нельзя удалить.
- **«Новый ролик»** — кнопка вверху списка роликов. Видна только тем, кого нода
  «Старт» хоть одного активного пайплайна называет запускающим. Открывает список
  доступных пайплайнов. После выбора — форма ноды «Старт»: название ролика и
  исходные файлы по слотам. «Запустить» создаёт подпапки и чаты у всех участников.

### 9.3. Связь с переключателем профилей

[MULTI_COMPANY_PROFILES_PLAN.md](./MULTI_COMPANY_PROFILES_PLAN.md) добавляет в шапку
переключатель профиля (Личное / компания). Он и «Проекты | Производство»
независимы: профиль выбирает, **чьё** рабочее место, закладка — **какое**.

Правила:

- `company_id` в таблицах **нет**: компания выводится через владельца, как везде

  и системное сообщение в чате. Системное сообщение строится из события, а не
  пишется отдельно.
- Взять в работу — `UPDATE … SET taken_by = $me WHERE id = $id AND status = 'ready'`.
  Двое нажали одновременно — выиграл один, второй получает «уже взял <имя>».
- Код, который читает новые таблицы, и миграция выкатываются вместе: dev-сервер
  работает на боевой базе, и чтение несуществующей таблицы кладёт страницу.

| Изменение пайплайна                    | настройки правятся на месте и действуют сразу; изменение структуры фиксирует новую версию — новые ролики идут по ней, начатые доживают по своей; дубль — только для отдельного пайплайна                                      |

| Готовый ролик                          | в архив со всеми чатами, не удаляется                                                                                                                                                                                         |

| Кто взял этап                          | виден в шапке этапа рядом с кнопками                                                                                                                                                                                          |
| «Отказаться»                           | взявший, автор пайплайна, суперадмин сайта; можно и после «На доработку»                                                                                                                                                      |
| Передача незавершённой работы          | через чат, вложения — любые файлы, включая архивы                                                                                                                                                                             |
| Выход проверяющего                     | в любой момент, но последний проверяющий этапа остаётся                                                                                                                                                                       |
| Проверяющих несколько                  | достаточно одного; кто проверяет, договариваются в чате                                                                                                                                                                       |
| Кто заводит пайплайны                  | в компании — по тегу `production.manage`; в личном — сам человек                                                                                                                                                              |

| Исполнитель и проверяющий в одном лице | разрешено, в том числе принять свою сдачу                                                                                                                                                                                     |

| Сроки                                  | мягкие: норма у этапа в пайплайне, сроки этапов и ролика считаются и пересчитываются сами                                                                                                                                     |

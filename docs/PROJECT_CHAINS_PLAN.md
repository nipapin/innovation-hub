**От кого:** десктоп-клиент (`fs.manager.tauri`).

## 0. Одной фразой

Проект перестаёт быть замкнутым. Результат обработки в одном проекте может лечь **в папку
другого проекта того же пользователя** и стать входом для его собственного, независимого
процесса — со своим триггером, расписанием и оплатой. Постинг — первый такой процесс, но не
единственный возможный.

---

## 1. Что такое цепочка и зачем она

Сегодняшняя картина: проект = `IN` → граф → `OUT`. Замкнутый цикл, всё внутри одной папки.

Картина с цепочками:

```
проект A (обработка)            проект B (постинг в YouTube)      проект C (постинг в VK)
IN → граф → OUT                 YT_post → Finder → Poster         VK_post → Finder → Poster
        └──→ B/YT_post ─────────────┘
        └──→ C/VK_post ──────────────────────────────────────────────┘
```

Зачем так, а не одним графом:

- **разные ритмы.** Обработка идёт когда есть файлы и свободная машина; постинг — по расписанию,
  каплей, в окно, с интервалом. Один граф этого не выражает без костылей.
- **разные исполнители.** Обработке нужна машина с AE и лицензиями; постингу — только сеть.
  После переноса постинга на сайт это буквально разные хосты.
- **разная настройка и разные люди.** Звено постинга настраивается один раз и живёт само;
  граф обработки переделывается под задачу.
- **несколько площадок = несколько звеньев.** Отдельная папка на площадку, у каждой своё
  расписание, свой аккаунт и свой дедуп.

Ключевое требование заказчика (владельца программы): **такая возможность должна быть**, а
конкретные имена папок и состав звеньев согласуются с клиентом в каждом случае.

## 2. Механика на нашей стороне (уже работает, писать не надо)

### 2.1. Как файл попадает в чужой проект

Нода `Copy File` с относительным путём вида `../<имя проекта>/<папка>`. Относительный путь
резолвится от папки проекта (`$projectPathGD`), не от локальной рабочей папки.

**В зеркале облака это работает даже прямее, чем локально.** Раскладка зеркала —
`<mirror>/<владелец>/<проект>/…` (`src-tauri/src/storage/layout.rs`), **уровня главной папки в
ней нет**. Значит `../` из проекта выводит сразу на уровень, где лежат все проекты этого
владельца. Копирование за пределы владельца невозможно по построению — путь просто не
разберётся, и заливать его будет некуда.

### 2.2. Что происходит дальше, без единой строки нового кода

1. `copy_from_mirror` создаёт папку назначения (`create_dir_all`) и копирует байты.
2. Вотчер зеркала (рекурсивный по всему корню) видит новый файл → очередь кандидатов.
3. По затишью — `presign` → PUT → **`/notify`**. Файл появляется у вас в каталоге, в проекте B.
4. Записи папки в каталоге заранее **не нужно**: строку создаёт сама заливка.

### 2.3. Проект-приёмник не обязан иметь `IN` и `OUT`

Папки заводятся по составу графа: `IN` — только если есть нода `mainSearch`, `OUT` — только если
есть `saveFileOnGD` (`src/NODE_WIN/utils/ensureProjectFolders.ts`). Проект из одних `finder` +
`Poster` не получит ни той, ни другой — и это правильно: ему они не нужны.

Папки-источники постинга создаются автоматически при сохранении графа, **через шов хранилища**, а
не обычным `mkdir` — то есть появляются в каталоге и видны сайту
(`src/NODE_WIN/utils/syncPostSourcesSidecar.ts`).

### 2.4. Несколько папок = несколько площадок

Внутри одного проекта может быть сколько угодно нод `finder`, у каждой своё:

| поле | смысл |
|---|---|
| `folder` | папка-источник (`VK_post`, `YT_post`, `TG_post`, допустим и абсолютный путь) |
| `searchType` | какие файлы искать |
| `order` | by Time / by Name / Random |
| `interval` | секунд между публикациями |
| `daysOfWeek`, `window` | дни недели и окно суток (секунды от полуночи) |
| `deleteAfter` | судьба исходника |
| `account` | аккаунт площадки |

Платформа отдельным полем **не хранится** — она выводится из того, какая `Poster`-нода стоит в
подграфе этого `finder`а (карта `POSTER_PLATFORM`, `src/PROCESSING/autoPost/posters.ts`). Это
ровно то, что уже написано в [SOCIAL_POSTING_PLAN §2](./SOCIAL_POSTING_PLAN.md), — здесь только
подтверждаем, что модель выдерживает несколько площадок в одном проекте.

Дедуп и тайминг у нас platform-aware (ключ `файл + площадка`), поэтому один файл, разложенный в
две папки под две площадки, сам себе не мешает.

## 3. Что из этого следует для сайта

### 3.1. Файл в папке проекта больше не значит «его положил человек»

Самое важное следствие. До цепочек появление файла в проекте означало действие пользователя.
Теперь источником может быть **другая задача**, выполненная машиной час назад.

Отсюда вопрос триггера: сайт должен уметь ставить работу **по появлению файла в наблюдаемой
папке проекта**. Два очевидных источника события — `/notify` при заливке и периодический обход
каталога. Для постинга это ваш планировщик из [SOCIAL_POSTING_PLAN §3.3](./SOCIAL_POSTING_PLAN.md);
для обработки, если она когда-нибудь тоже станет запускаться сайтом, — та же механика.

### 3.2. Один исходник порождает работу в нескольких проектах

Цепочка из трёх звеньев — это три отдельные работы в трёх проектах, у каждого свои оси
тарификации (`payBase` / `payMeter` в ноде `description`). Наше ожидание: клиент видит три
строки, потому что это три разные работы. Но решать вам — см. открытые вопросы.

### 3.3. Что считать финальным результатом (важно для биллинга)

У нас «финал» — **не тип ноды, а место в графе**: терминальный шаг = нода без исходящего ребра
(`src/PROCESSING/utils/createProcessQueue.ts:130`). `Save File on GD` ничем не привилегирован,
`Copy File` тоже может быть финалом — если к нему ничего не подключено дальше.

По терминальным шагам считается всё, что вы получаете в строке архива:

- `outSec` — **сумма** длительностей терминальных медиа-выходов;
- `out[]` — все терминальные выходы, включая не-медиа.

Три следствия, которые в цепочках выстреливают сразу:

1. **Передаточная копия не должна быть тарифицируемым финалом.** Если копия в чужой проект
   терминальна, её хронометраж войдёт в `outSec` проекта-отправителя, и клиент заплатит за один
   ролик дважды — как отправитель и как получатель. Лечится настройкой графа (не делать ветку
   терминальной) или выбором осей, кода не требует.
2. **Путь в `out[]` окажется абсолютным.** Пути режутся относительно корня своего проекта; файл,
   лежащий в чужом проекте, под этот корень не попадает и остаётся абсолютным
   (`src-tauri/src/commands/db_analytics.rs:104`). Правило чтения «корень из расположения `.jsonl`
   + `out[]`» на таких строках не работает.
3. **В режиме воркера такой файл в отчёт не попадёт вовсе** — мы намеренно выбрасываем из
   `taskDone` всё, что вне папки проекта, потому что в облаке этого нет
   (`src/PROCESSING/remoteWorker/runTask.ts:230`). Для цепочки это значит: **факт передачи в
   соседний проект в отчёте задачи не виден**, он виден только как появление файла в каталоге.

### 3.4. Постинг: настройка у нас, исполнение у вас

Разделение из [SOCIAL_POSTING_PLAN §1](./SOCIAL_POSTING_PLAN.md) остаётся в силе и цепочками не
меняется. Уточнение к нему: **сайдкар `options/postSources.json` вам действительно не нужен** —
он скомпилирован под наш движок (внутри лежит очередь исполнения `processItem`, наш рантайм-формат)
и платформу в явном виде не содержит. Источник истины — граф в `options.json`, как вы и
планировали.

## 4. Известные проблемы и грабли

Часть — наша зона, но вам их знать нужно: от них зависит, какие сценарии сегодня работают, а какие
только выглядят рабочими.

### 4.1. ⚠️ Загрузка файла на сайте не запускает локальную обработку

Гейт папки `IN` и листинг папки-источника постинга читают **диск** (`fs::read_dir`), а не каталог
(`src/PROCESSING/findFilesForSingleFolder.ts:62`, `src/PROCESSING/autoPost/index.ts:130`). Файл,
который существует только в облаке, локальному раннеру **невидим** — при том, что в колонках
программы он прекрасно виден (там листинг идёт через каталог с подмешиванием диска).

Следствия:

- клиент положил файл в `IN` через сайт → машина в режиме конвейера его не подхватит;
- машина A положила файл в проект B → машина B его не увидит, пока байты не окажутся у неё.

Пока доставка работы идёт **очередью задач** (файл достаётся по `file_id`), это неважно: скан не
участвует вовсе. Чинить у нас, решение известно (перевести оба гейта на зеркальный листинг),
работа небольшая. Приоритет зависит от вашего ответа на вопрос 1 в §5.

### 4.2. Переименование проекта ломает цепочки

Относительный путь в графе (`../newProj2/YT_post`) жёсткий, а имя папки в зеркале следует имени
проекта в каталоге. Переименовали проект у вас — звено цепочки молча перестаёт попадать куда надо.
Просьба иметь это в виду, если появится массовое переименование; в идеале — предупреждать
пользователя, что проект может быть целью чужой автоматизации.

### 4.3. Опечатка в имени проекта = тихий тупик

Копирование создаёт любую папку на диске без проверки, но заливка для пути, чей проектный
уровень не найден в каталоге, отвечает «заливать некуда» и молча пропускает файл
(`src-tauri/src/storage/service.rs:3710`). Ни ошибки, ни значка — файл лежит локально навсегда.
Чинить у нас (валидация в ноде), но это же и аргумент за то, чтобы **список проектов для выбора
приходил с сайта**, а не набирался руками.

### 4.4. Коллизии имён проектов

Два проекта с одинаковым именем у одного владельца разводятся суффиксом в раскладке зеркала.
Путь, написанный в графе по «человеческому» имени, тогда не совпадёт. Редко, но диагностируется
плохо.

### 4.5. Журнал постинга не помечен машиной

`options/_post/MM.YYYY.jsonl` — единственный источник дедупа и интервала у локального раннера, и,
в отличие от архива статистики, **метки машины в имени не имеет**. В объектном хранилище нет
дописывания: две машины, постящие один проект, затрут журнал друг друга при заливке, и файл уедет
на площадку второй раз. Это ещё один аргумент за то, что **журнал должен принадлежать тому, кто
постит** — то есть после переноса вам, в `post_ledger`.

### 4.6. Переходный период цепочки усугубляют

Запрет «два постинга по одному проекту» ([SOCIAL_POSTING_PLAN §9](./SOCIAL_POSTING_PLAN.md))
становится острее: звено-приёмник может быть включено раньше, чем выключен локальный раннер, и
заметить это некому — проект-приёмник человек в этот момент не открывает.

## 5. Открытые вопросы

1. **Кто ставит работу для звена-приёмника** — сайт по появлению файла в каталоге или машина по
   локальному скану? Наш ответ: сайт, раз исполняет сайт. От этого прямо зависит, чинить ли §4.1
   и когда.
2. **Нужен ли явный граф связей «A → B»?** Сейчас связь нигде не объявлена: она выводится из пути,
   написанного в ноде копирования. Сайт о ней не знает. Это достаточно для работы, но не хватит
   для UI «откуда пришёл этот файл» и для операции «остановить цепочку целиком». Заводить ли
   объявление связи — и если да, то на чьей стороне?
3. **Оплата цепочки.** N звеньев = N списаний и N строк у клиента? Резерв считается по звену или
   по цепочке целиком? Что показывать клиенту, чтобы три списания за один ролик не выглядели
   ошибкой?
4. **Кто владелец расписания постинга** — нода `finder` в графе (наш путь) или настройка проекта в
   вашей админке, которая его переопределяет? Два источника истины на расписание — известный
   способ получить публикацию в три ночи.
5. **Гранулярность переключателя «постит сайт»** — проект / клиент / глобально. Уже стоит у вас в
   [§10](./SOCIAL_POSTING_PLAN.md); повторяем, потому что для цепочек ответ важнее: звенья
   включаются по одному.
6. **Что делать с накоплением**, если звено-приёмник выключено или в архиве, а файлы в его папку
   продолжают падать: копить молча, предупреждать, считать ошибкой цепочки?
7. **Регламент имён папок-источников.** `VK_post` / `YT_post` / `TG_post` — свобода или словарь?
   Если сайт будет их показывать, создавать или предлагать, лучше согласованный словарь; и
   переименовывать их потом дорого (в зеркале это переезд файлов).
8. **Импорт локальных `_post/*.jsonl` в `post_ledger`** при переносе — уже стоит у вас в §10,
   здесь только подтверждаем: формат простой, отдадим по первой просьбе.

## 7. Что этот документ НЕ требует делать сейчас

Ничего. Механика цепочек на нашей стороне работает уже сегодня в пределах одной машины, а всё
остальное упирается в перенос постинга, у которого свой порядок работ
([SOCIAL_POSTING_PLAN §8](./SOCIAL_POSTING_PLAN.md)). Документ фиксирует решения, границы и
вопросы, чтобы к моменту реализации не восстанавливать рассуждения заново.

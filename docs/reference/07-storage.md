# 07 — Хранилище файлов

Cloudflare R2 (S3-совместимый API) для байтов, PostgreSQL для каталога и
журнала. Основные модули — `lib/storage/*`, ядро записи —
`lib/storage/write-path.ts` (~1300 строк).

---

## 1. Раскладка ключей в бакете

```
projects/{userId}/{projectId}/project-meta.json      ← метаданные проекта
projects/{userId}/{projectId}/options/folderState.json ← тумблер слежения
projects/{userId}/{projectId}/options/options.json     ← граф обработки
projects/{userId}/{projectId}/options/description.md   ← развёрнутое описание
projects/{userId}/{projectId}/{folderPath}/{uuid}-{name} ← файлы пользователя
projects/{userId}/user-meta.json                     ← метаданные пользователя
projects/{userId}/{projectId}/_catalog/               ← снимок каталога
projects/{userId}/{projectId}/{...}/_stats/*.jsonl    ← архив обработок машин
_site/stats/YYYY-MM.jsonl                            ← месячная копия архива
admin/…                                              ← медиа витрины
feature-suggestions/…                                ← вложения заявок
```

Ключ строится только через `lib/s3-config.ts`:
`projectObjectPrefix(userId, projectId)` и `buildProjectObjectKey(...)`.
Каждый сегмент проверяется `safeSegment` — ни `/`, ни `.`, ни `..`.

### Физическое и логическое имя

Presign минтит физическое имя `{uuid}-{name}`, чтобы два файла с одинаковым
именем не перетёрли друг друга в бакете. Каталог при этом хранит **логическое**
имя (`name` = то, что видит человек), а `logicalNameFromObjectKey()` умеет
срезать uuid-префикс при обратном разборе.

Отсюда возможны «двойники»: один файл под каноническим ключом
(`.../options/foo.json`) и под физическим (`.../options/{uuid}-foo.json`). В
каталоге место одно — держит уникальный индекс. Кто побеждает, решает
`preferCandidate` при переиндексации: **канонический ключ**, при прочих равных —
свежий по `originMtime`, при полном равенстве — лексикографически меньший ключ.

## 2. Каталог

`project_files` — плоский список: `folder_path` + `name`, папки тоже строки
(`is_folder = TRUE`, `s3_key IS NULL`, гарантировано `CHECK`).

Почему каталог, а не листинг бакета:

- листинг платный и медленный, а дерево нужно на каждом рендере;
- листинг не знает, кто залил файл (`uploaded_by`);
- листинг не даёт монотонного порядка событий, без которого нет инкрементальной
  синхронизации.

Имена уникальны **без учёта регистра** — как в Windows и macOS. Проверку делает
`assertNameFree` в транзакции, а ловит на всякий случай уникальный индекс.

### Правила имён — `lib/storage/file-names.ts`

| Запрет | Причина |
| --- | --- |
| пустое, `.`, `..` | очевидно |
| `\ / : * ? " < > \|` и управляющие 0x00–0x1f | пересечение запретов Windows и POSIX |
| заканчивается пробелом или точкой | Windows молча обрезает |
| `CON`, `PRN`, `AUX`, `NUL`, `COM1..9`, `LPT1..9` | зарезервированы Windows |
| > 180 байт UTF-8 в имени | предел |
| > 1000 байт UTF-8 в полном пути | предел |
| `_catalog` | зарезервировано (403) |

`options` намеренно **не** запрещён: служебная папка — обычная папка каталога.
Закреплены только три канонических имени внутри неё, и это проверяется на
уровне операции, а не имени.

---

## 3. Журнал изменений

`storage_changes` — единственный способ, которым клиент узнаёт об изменениях.
Пишется **в той же транзакции**, что строка каталога.

| Поле | Смысл |
| --- | --- |
| `seq BIGSERIAL` | монотонный курсор для всей базы |
| `op` | `put` \| `delete` \| `move` |
| `event_id` | уникальный, `ON CONFLICT DO NOTHING` — повтор идемпотентен |
| `actor_user_id` | кто совершил запись |
| `payload` | `name`, `folderPath`, `isFolder`, `fileId`, `contentType`, `from`/`to` |

### `GET /delta?since=`

Отдаёт до 5000 записей за раз. Если `since` старше окна хранения (90 дней),
приходит `truncated: true` — клиент обязан перечитать дерево целиком.

Сериализация (`lib/storage/delta-format.ts`) склеивает `from`/`to` в удобные
`name`/`folderPath` и, если передан контекст, добавляет
`displayPath` = `email владельца / имя проекта / путь / имя` — человекочитаемая
строка для логов и интерфейса.

## 4. Загрузка файла

```
браузер / машина                        сайт                      R2
      │                                  │                         │
      ├── POST /presign ────────────────► │                         │
      │   {projectId, method:"PUT",       │  проверка доступа       │
      │    folderPath, fileName,          │  (editor+)              │
      │    contentType}                   │  проверка MIME          │
      │                                   │  ключ {uuid}-{name}     │
      │ ◄─── {url, s3Key} ────────────────┤                         │
      │                                                             │
      ├── PUT {url} + байты ──────────────────────────────────────► │
      │                                                             │
      ├── POST /notify ────────────────►  │                         │
      │   {projectId, s3Key, folderPath,  │  HEAD объекта           │
      │    fileName, sizeBytes,           │  → размер, etag, hash   │
      │    contentHash, originMtime}      │  транзакция:            │
      │                                   │   строка каталога       │
      │                                   │   + запись в журнал     │
      │ ◄─── {file} ──────────────────────┤                         │
```

Байты **никогда не идут через сервер приложения** — кроме двух проксирующих
роутов витрины и сборки архива папки, где иначе нельзя
(см. [14](#14-скачивание-папки-архивом)).

### Что делает `notify` особенным

1. **Отказ заливки канонического сайдкара.** Если `folderPath`/`fileName`
   попадают на `options/{folderState.json|options.json|description.md}`, а ключ
   не канонический — 409 «пишется через `PUT /sidecars`, не через `/notify`».
   Иначе в бакете появился бы второй объект с тем же логическим именем: сайт
   читал бы свой, программа свой, и «какая версия новее» тут не помогает,
   потому что это два разных объекта.
2. **Уборка сирот.** Байты уже в бакете, строки ещё нет. Если операция упала
   отказом, который повтором не лечится (400 — плохое имя, 409 — занятое),
   объект удаляется: ссылок на него нет, а `delete` работает по `file_id`, то
   есть удалить его клиенту было бы нечем. Если ошибка неизвестная (упало
   соединение с базой) — объект **остаётся**: клиент повторит `notify` тем же
   ключом, и доехавшие гигабайты пригодятся.
3. **Создание отсутствующих папок** по пути заливки
   (`writeEnsureFolderPath`).

### Multipart

Четыре шага для больших файлов: `create` → `presign-part` (по одной на часть) →
`complete` → `abort`. Логика общая для REST и RPC —
`lib/storage/multipart.ts`.

## 5. Переименование и перемещение

`writeRename` — одна операция для обоих: **ключ в R2 не меняется**, меняются
`folder_path` и `name` в каталоге. Событие журнала — `op: "move"` с
`from`/`to`.

Это важно для конвейера: снятие `-` с начала имени папки приходит именно сюда,
и это событие готовности витка обработки. Кто его совершил, тот и становится
`description.contact` (см. [08](./08-pipeline.md#6-кто-становится-contact)).

Защиты: `isMoveIntoSelf` (папку нельзя переместить внутрь себя),
`assertNameFree`, запрет уводить канонические сайдкары и саму папку `options`.

## 6. Копирование

`POST /copy` — файлы и папки. Мало работы делается сразу, много — уходит в
фоновую задачу `storage_jobs` (`kind: "copy"`), и клиент следит через
`GET /jobs/:id`.

Конфликт имён решается суффиксом: `allocateUniqueName` подбирает
`имя (2)`, `имя (3)` … до 999.

## 7. Корзина

Две независимые корзины, обе мягкие.

| | файлы | проекты |
| --- | --- | --- |
| Поле | `project_files.deleted_at` | `projects.deleted_at` |
| Срок | 30 дней (`TRASH_RETENTION_DAYS`) | 30 дней |
| Список | `GET /trash?projectId=` | внутри `GET /api/projects` |
| Возврат | `POST /trash/restore` | `POST /project-restore` |
| Чистка | `purgeExpiredTrash()` | `purgeDeletedProjects()` |

Удалённая строка выпадает из уникального индекса — имя освобождается сразу. При
восстановлении, если имя уже занято, подбирается уникальное.

В интерфейсе кабинета раздел «Корзина» пока помечен как не подключённый
(`trashNotWired`), хотя бэкенд готов.

## 8. Фоновые работы

`storage_jobs` + `lib/storage/job-runner.ts`.

| `kind` | Что делает |
| --- | --- |
| `copy` | копирование по плану `buildCopyPlan` |
| `move` | перемещение |
| `purge` | чистка корзины файлов и проектов |
| `recatalog` | пересборка снимка каталога в `_catalog/` |

Жизненный цикл: `queued` → `claimJob` → `running` → `finishJob` →
`done`/`failed`. `requeueStaleRunningJobs()` возвращает подвисшие.
`event_id` уникальный — повторный запрос не создаёт вторую работу.

Разбор очереди: `scheduleJob(id)` сразу после создания и
`POST /api/cron/storage-jobs` как второй вход.

## 9. Переиндексация

`POST /reindex` — полная сверка: `LIST` по префиксу проекта против каталога.
Возвращает `{scanned, inserted, updated, removed, shadowed}`, где `shadowed` —
двойники, проигравшие канонику.

Дорогая операция, инструмент восстановления, а не рутина.

## 10. Снимок каталога `_catalog/`

`lib/storage/catalog.ts`: `catalog.json` (снимок) + `catalog.jsonl` (журнал
дописыванием), пересборка каждые `CATALOG_REBUILD_EVERY_N = 200` записей.

Фактически используется только `rebuildCatalogSnapshot` из работы
`recatalog`; чтение (`loadCatalogRows`) не вызывается нигде. Задел под
восстановление каталога без базы.

## 11. Три сайдкара

`GET`/`PUT /api/storage/v1/sidecars` — единственный законный канал записи.

| Файл | Кто владеет записью | Что внутри |
| --- | --- | --- |
| `options/folderState.json` | `lib/project-automation.ts#setProjectPaused` | `enabled` (= `NOT is_paused`), `updatedBy`, таймстемп |
| `options/options.json` | `lib/project-storage.ts#updateProjectExposedOptions` | граф обработки; сайт правит только `exposedToSite` |
| `options/description.md` | `writeProjectDescriptionMd` | markdown-описание проекта |

После каждой успешной записи вызывается `writeSidecarSync`: сайдкары попадают в
бакет по фиксированному ключу, минуя presign/notify, поэтому строку в
`project_files` им никто не создавал. Без строки файла не видно ни в дереве
кабинета, ни в `/tree` у клиента, а событие журнала приходит без `fileId` — то
есть применить его к своему индексу клиент не может и вынужден перечитывать
дерево целиком.

`writeSidecarSync` идемпотентна: строка ищется по логическому имени, поэтому
файл, попавший в каталог когда-то с uuid-ключом, здесь же переводится на
канонический ключ и **сохраняет свой `file_id`**.

## 12. Параметры обработки

`options.json` пишет редактор нод десктопа. Сайт видит только свойства,
помеченные `exposedToSite`.

Семь типов контролов (`lib/options/types.ts`): `checkbox`, `slider`, `timecode`,
`ddm`, `autocomplete`, `textedit`, `valueRange`. Всё остальное — тяжёлые контролы
с объектом в `value`; сайт их не рисует и не отдаёт.

| Файл | Роль |
| --- | --- |
| `lib/options/extract.ts` | граф → плоский список `ExposedOption` (путь, метка, тултип, значение, границы, варианты) |
| `lib/options/apply.ts` | правки клиента → граф, на месте, без обращений к R2 |
| `lib/options/numeric-format.ts` | таймкоды, float/integer, границы, шаг |

Проверка на сервере обязательна, хотя контрол в браузере уже зажимает ввод:
страница могла открыться до того, как автор поменял граф.

- **Числа зажимаются**, а не отвергаются: значение вне диапазона почти всегда
  означает устаревшую страницу, и отказ выглядел бы поломкой ползунка.
- **Списки — отказ**: подставлять «ближайший вариант» вместо выбранного нельзя.

Токены `#tgChannels`, `#vkGroups`, `#folders` в списках вариантов резолвит только
программа — у неё есть учётки и локальные папки. Свойство всё равно
показывается с `editable: false`: пользователю важно видеть, что параметр есть.

Подробно — `docs/PROJECT_OPTIONS_PANEL.md`.

## 13. Загрузка медиа витрины

Две стратегии, обе нужны:

| Роут | Как | Когда |
| --- | --- | --- |
| `POST /api/admin/upload` | браузер отправляет сырое тело (не multipart), сервер стримит в R2 через `@aws-sdk/lib-storage` | CORS на бакете не нужен, прогресс через `XHR.upload.onprogress`. `maxDuration: 300` |
| `POST /api/admin/upload/presign` | presigned PUT напрямую из браузера | быстрее и дешевле, но требует CORS (`pnpm s3:set-cors`) |

В presign **намеренно не подписывается** `ContentType`: иначе `Content-Type`
попадает в `SignedHeaders`, и браузер обязан прислать байт-в-байт тот же
заголовок — иначе `SignatureDoesNotMatch` **после** того, как тело уже
загрузилось (в XHR это выглядит как CORS-ошибка). R2 всё равно сохраняет тот
Content-Type, который прислал браузер.

По той же причине в `lib/s3-client.ts` отключены flexible checksums.

### Политики загрузки

| Модуль | Где применяется | Что разрешает |
| --- | --- | --- |
| `lib/s3-upload-policy.ts` | медиа витрины | 7 типов: jpeg, png, webp, gif, mp4, webm, quicktime. Лимит `ADMIN_UPLOAD_MAX_BYTES`, по умолчанию 250 МБ |
| `lib/project-upload-policy.ts` | файлы проектов | те же + аудио (mpeg, wav, ogg, webm, mp4/m4a, aac, opus, flac), текст, markdown, csv, субтитры (`text/vtt`, `application/x-subrip`), json, pdf, zip, `application/octet-stream` |
| `lib/public-upload-policy.ts` | вложения заявок | реэкспорт первого + свои лимиты: 25 МБ, до 5 файлов |

`safeBaseFileName()` чистит имя: только буквы, цифры, `.`, `_`, `-`; схлопывает
подчёркивания; обрезает до 180 символов.

⚠️ Таблица «расширение → MIME» скопирована в первые два модуля
(см. [14](./14-improvements.md#5-политики-загрузки)).

## 14. Скачивание папки архивом

Пункт «Скачать папку архивом» в контекстном меню рабочей области. Ядро —
`lib/storage/zip-stream.ts` (формат) и `lib/storage/archive.ts` (состав и
разбиение), поверхность — `GET /api/storage/v1/archive/plan` и
`GET /api/storage/v1/archive`.

### Что происходит

```
браузер                              сайт                              R2
   │                                  │                                 │
   ├── GET /archive/plan ───────────► │  каталог поддерева               │
   │   {projectId, folderId,          │  → пустые папки + файлы          │
   │    partSize}                     │  → жадная раскладка по частям    │
   │ ◄── {parts:[…], version} ────────┤     (размер готового .zip!)      │
   │                                                                    │
   ├── GET /archive?part=2&version=… ────────────────────────────────►   │
   │ ◄── Content-Length + поток zip ──┤ ── GetObject по одному объекту ─►│
```

Байты идут **через приложение** — третий случай в проекте после двух
проксирующих роутов витрины. Иначе никак: архива в бакете не существует, он
собирается на ходу.

### Почему части, а не один архив

Папка проекта — исходники и рендеры, десятки гигабайт. Один такой файл не
примет FAT32 на флешке, его нельзя начать распаковывать до последнего байта, а
обрыв на 90% означает начать заново. Поэтому файлы раскладываются по
независимым архивам не больше `partSize` (по умолчанию 2 ГБ, минимум 64 МБ) —
как в Google Drive.

Части — **не тома**: каждый `.zip` открывается сам по себе. Файл, который сам
больше лимита, уезжает в свою часть целиком и помечается `oversize` — резать
файл посередине означало бы ровно тот многотомный архив, которого мы избегаем.

Считается размер **готового архива**, а не сумма файлов: на десятках тысяч
мелких файлов заголовки и опись складываются в мегабайты, и часть, обещавшая
2 ГБ, выдала бы 2 ГБ с лишним.

### Три решения в формате

| Решение | Почему |
| --- | --- |
| только `store`, без сжатия | в папках видео и картинки — сжатие даёт единицы процентов, а стоит процессорного времени на каждый гигабайт; зато размер известен заранее |
| дескрипторы данных (бит 3) | CRC на момент локального заголовка неизвестен, а читать объект дважды — удвоить исходящий трафик; правильные значения дублируются в описи |
| точный `Content-Length` | браузер рисует настоящий прогресс и остаток времени. Цена: поток обязан выдать ровно обещанное, поэтому короткий объект добивается нулями, а длинный обрезается — с записью в лог |

ZIP64 включается по расчёту: часть за 4 ГБ, больше 65 535 записей или отдельный
файл больше 4 ГБ. Обычная часть до 2 ГБ остаётся классическим архивом.

Пустые папки попадают в архив отдельными записями: распаковщик создаёт каталоги
по путям файлов, и пустой каталог иначе исчезает. Для проекта это существенно —
структура папок и есть договор с программой обработки.

### Плана в базе нет

Состав выводится из каталога заново на каждый запрос, а `version` — отпечаток
состава (sha1 по путям и размерам). Совпал — часть №2 та же самая; не совпал —
409, и клиент перечитывает список. Ни таблицы, ни уборки просроченных планов.
Диалог перечитывает план перед запуском и объясняет расхождение сам, чтобы
вместо файла не открылась вкладка с JSON-ошибкой.

### Пределы и эксплуатация

| | |
| --- | --- |
| Записей в плане | 100 000 — упирается в память процесса, раскладка держится целиком |
| Докачка | нет: `Accept-Ranges: none`, CRC считается на ходу |
| Служебные файлы | `options/` и `_catalog/` в архив не попадают никогда, в том числе у админа |

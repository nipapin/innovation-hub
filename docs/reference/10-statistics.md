# 10 — Статистика и посещения

Три независимые системы: витрина статистики (проекты, файлы, задачи, обработки),
трекинг посещений и архив обработок с машин.

План и обоснования — `docs/STATISTICS_PLAN.md`, контракт архива —
`docs/PIPELINE.md` §14.

---

## 1. События и состояния — ключевое различие

| | События | Состояния |
| --- | --- | --- |
| Что | задачи, обработки, посещения, ошибки | «сколько сейчас в хранилище» |
| Хранение | строка на событие | суточные срезы |
| Период влияет | да | **нет** |
| Таблицы | `tasks`, `processing_stats`, `visitor_events` | `storage_snapshots` |

Из этого следует: «сколько файлов у пользователя сейчас» считается по
`project_files`, а «как рос объём» — **только** по `storage_snapshots`. Иначе
никак: журнал не хранит историю размеров.

Пропущенный день среза невосстановим. Поэтому тик живёт в процессе
(`lib/statistics/stats-loop.ts`), а не только в cron-роуте.

## 2. Одна витрина, две области видимости

`lib/repositories/statistics.ts` — единственный слой запросов. Админка и кабинет
отличаются **только** `scope.ownerId`:

```ts
type StatsScope = {
  ownerId:   string | null   // null = админка; иначе жёсткая рамка кабинета
  userId:    string | null   // провал в пользователя
  projectId: string | null   // провал в проект
}
```

| Витрина | Эндпоинт | `ownerId` | Оси |
| --- | --- | --- | --- |
| Админка | `GET /api/admin/statistics` | `null` | все |
| Кабинет | `GET /api/account/statistics` | `userId` сессии | без `user`, `machine`, `cost` |

**Скоуп добавляет роут, а не клиент** — иначе кабинет сможет попросить чужие
данные. Разбор осей из query-строки общий: `lib/statistics/query.ts`.

Справка у витрин тоже разная — две тройки статей вместо одной с оговорками:
`statistics.personal*` для кабинета, `statistics.overview` / `.metrics` /
`.breakdowns` для админки, плюс `statistics.import` под своим тегом. Якоря:
кнопка в шапке страницы и знаки «?» у переключателей «Метрика» и «Разрез»
(тема выбирается по `variant`). Контракт — [HELP_SYSTEM.md](../HELP_SYSTEM.md) §5.

**Оси тоже сводит сервер.** `getStatistics` выводит витрину из скоупа
(`ownerId` есть → `account`) и заменяет недопустимый разрез на `project`, а
`userId` в кабинете сбрасывает целиком: провала в человека там нет. Ответ несёт
`variant`, чтобы клиент не гадал. Запрет, живущий только в наборе кнопок, — не
запрет: `?breakdown=machine` уходит мимо интерфейса.

Компонент один — `components/statistics/statistics-explorer.tsx`, ему передаются
`endpoint` и `variant`.

## 3. Оси

`lib/statistics/types.ts` — один набор типов на три слоя (запросы, API, UI),
потому что расхождение скоупа между витринами и есть главный риск раздела.

**Метрики** (`STAT_METRICS`): `files`, `bytes`, `tasks`, `errors`, `procs`,
`spend`, `cost`, `render`. В кабинете — `ACCOUNT_METRICS`, то же без `cost`.

⚠️ **`spend` и `cost` — разные счета, а не одна сумма в двух валютах.**

| | Что это | Источник | Единица |
| --- | --- | --- | --- |
| `spend` | списано с человека | `billing_transactions`, `kind = 'charge'` | копейки, ₽ |
| `cost` | во что работа обошлась нам | `processing_stats.total_cost` | доллары |

`spend` включает нашу цену за результат и наценку, `cost` — только счёт внешнего
сервиса. Набор видов у `spend` тот же, что на «Балансе и расходе», чтобы два
экрана про одни деньги сходились до копейки.

**Разрезы** (`STAT_BREAKDOWNS`): `user`, `project`, `fileType`, `machine`. В
кабинете — `ACCOUNT_BREAKDOWNS`: только `project` и `fileType`.

**Периоды** (`STAT_PERIODS`):

| Период | Шаг таймлайна | Окно таймлайна | Окно разреза |
| --- | --- | --- | --- |
| `7d` | день | 6 дней | 7 дней |
| `30d` | день | 29 дней | 30 дней |
| `90d` | неделя | 12 недель | 90 дней |
| `12m` | месяц | 11 месяцев | 12 месяцев |
| `all` | месяц | 35 месяцев | без ограничения |

## 4. Что отдаёт ответ

```ts
StatsResponse = {
  totals,      // состояние на сейчас — период на него не влияет
  rows,        // строки разреза, ВСЕ метрики сразу
  timeline,    // события по бакетам
  volume,      // объём по снимкам состояний
  histogram,   // распределение времени рендера
  funnel,      // задачи конвейера по статусам
  card,        // карточка элемента — только при провале
  bucketUnit, variant, breakdown, period, scope,
  truncated,   // сколько строк отброшено лимитом
}
```

Три решения, которые стоит знать:

1. **В строке разреза лежат все метрики сразу** — переключение метрики в
   интерфейсе не ходит на сервер.
2. **`renderP50` и `renderP95` вместо среднего** — среднее прячет выбросы.
3. **`truncated` возвращается всегда.** `STAT_ROW_LIMIT = 200`; молчаливых
   обрезаний быть не должно, иначе усечённая витрина читается как «это всё».

`procsTotal = 0` значит «архив ещё не импортирован», а пустой `volume` — «снимки
ещё не копились». Это разные вещи, и обе отличимы от нуля данных.

### Карточка элемента

Появляется при провале в проект или пользователя. Фиксированный набор, а не
конструктор: заголовок, подзаголовок, последняя активность, число участников
(помимо владельца), вклад (кто работал в проекте / какие проекты у пользователя),
распределение по типам файлов.

Готовность данных показывает `components/account/stats-readiness.tsx` — один
компонент на обе витрины.

## 5. Суточные срезы состояний

`lib/statistics/snapshots.ts#takeStorageSnapshot()`.

Идемпотентно: повторный вызов в тот же день перезаписывает строки, поэтому тик
может дёргаться сколько угодно раз.

Проекты **без файлов тоже получают строку с нулями** — иначе «сколько проектов
было в тот день» посчитать нельзя.

Проекты в корзине не снимаются: иначе ряд «рост объёма» разошёлся бы с плитками,
где корзина исключена, и одна страница показала бы два разных объёма. Уже снятые
дни не переписываются — это честная история.

Внешних ключей у `storage_snapshots` нет: история переживает удаление проекта и
пользователя.

## 6. Архив обработок

Машины пишут JSONL в `_stats/` **внутри папок проектов**. Канал односторонний:
**сайт в `_stats` не пишет никогда**.

### Импорт — `lib/statistics/import-archive.ts`

```
для каждого проекта → LIST его _stats/*.jsonl
  → читаем с позиции из stats_import_state (курсор по ключу + etag)
  → строки → INSERT ... ON CONFLICT (item_id) DO NOTHING
```

Свойство, на которое всё опирается: **строки иммутабельны, ключ дедупа —
`item_id`**. Поэтому файл можно перечитывать сколько угодно раз и с любого
места, дублей не будет.

Бюджет прохода: `MAX_FILES_PER_RUN = 500` файлов, вставка пачками по 200.

Результат подробный: `projectsScanned`, `filesSeen`, `filesRead`, `linesRead`,
`rowsInserted`, `duplicates`, `malformed`, `partial`, `filesSkipped`, `errors`.

Имя машины восстанавливается из ключа объекта (`machineFromStatsKey`) — в самой
строке архива его нет.

### Экспорт копии — `lib/statistics/export-archive.ts`

Месячная выгрузка в `_site/stats/YYYY-MM.jsonl`.

Зачем, если файлы машин уже лежат в R2: они лежат **внутри папок проектов**.
Удалили проект — ушёл и его `_stats`, и восстановить базу с нуля будет нечем.
Этот экспорт от пользовательских папок не зависит.

Один файл на месяц здесь безопасен, в отличие от машинного архива: писатель ровно
один — сайт, и проблемы «две машины затирают объект» не существует.

Формат — дамп строк таблицы, а не схема v1: он сохраняет `project_id` и
`machine`, которых в машинной строке нет. Восстановление из него — прямой
`INSERT`, а не путь приёмника.

Ограничители:
- `MAX_ROWS_PER_FILE = 100 000` — файл собирается целиком в память (~40 МБ на
  100k строк). Больше — нужен потоковый multipart, и до тех пор экспорт честно
  отказывается, а не падает по OOM;
- `MIN_REWRITE_MS = 20 часов` — не перезаписываем один месяц чаще раза в сутки.
  Тик часовой, а текущий месяц меняется почти каждый час: без этого горячий файл
  заливался бы двадцать четыре раза в день целиком.

### Часовой тик

`lib/statistics/stats-loop.ts`, интервал 1 час, первый через 30 секунд:

1. `takeStorageSnapshot()`
2. `importProcessingArchive()`
3. `exportMonthlyStats()`

Все три идемпотентны — снимок за сутки перезаписывается, строки дедуплицируются
по `item_id`, экспорт пропускается, если с прошлого раза ничего не
импортировали. Поэтому час это «последнее состояние дня» и «догнать то, что
дописали машины», а не двадцать четыре копии.

Отсутствие таблицы (миграция не накачена) логируется и не роняет процесс.

### Ручные входы

`POST /api/admin/statistics/import`, `POST /api/cron/storage-purge`.

## 7. Посещения

### Сбор

`components/site/visitor-tracker.tsx` смонтирован в корневом layout, на каждой
клиентской навигации стучится в `POST /api/visitors/track`.

Роут:

| Шаг | Что |
| --- | --- |
| Валидация | zod: `path` (≤2048), `query`, `referer` |
| Фильтр | отсекает `^/api/`, `^/_next/`, `^/admin` — иначе каждое обновление `/admin/visitors` становится «посещением», которое тут же показывается |
| IP | `X-Forwarded-For` → `X-Real-IP` → `CF-Connecting-IP` |
| Отпечаток | `sha256(ip \| UA \| Accept-Language)`, первые 16 символов |
| Пользователь | если есть сессия — `userId`, `email`, `fullName` (best-effort: сбой профиля не ломает трекинг) |
| Ответ | **всегда `{ok: true}`**, даже на мусор и при ошибке записи |

Последнее принципиально: трекинг не должен ломать страницу.

### Хранение

`visitor_events`. `user_id` — мягкая ссылка без FK, `user_email` и
`user_full_name` денормализованы: удаление пользователя не должно уносить историю.

Индексы: по времени (DESC), по отпечатку + времени, частичный по `user_id`, по
пути.

### Показ

`/admin/visitors` → `GET /api/admin/visitors` →
`components/admin/visitors/visitors-content.tsx`.

## 8. Сводка для дашборда

`GET /api/account/stats?range=day|week|month` — отдельный, более простой
эндпоинт для `/account`: баланс, число проектов и файлов, суммарный
хронометраж, столбцы графика, показатели за период.

⚠️ Имя путается с `/api/account/statistics`
(см. [14](./14-improvements.md#12-именование-путающее-эндпоинты)).

## 9. Что уже считается, а что ещё нет

| Метрика | Источник | Состояние |
| --- | --- | --- |
| Файлы, объём «сейчас» | `project_files` | ✅ |
| Рост объёма | `storage_snapshots` | ✅ (с момента первого среза) |
| Проекты | `projects` | ✅ |
| Задачи конвейера, ошибки, воронка | `tasks` | ✅ |
| Обработки, себестоимость (`cost`), хронометраж рендера | `processing_stats` | 🟡 зависит от импорта архива |
| Спенд (`spend`) | `billing_transactions` | ✅ с момента первых списаний |
| Гистограмма времени рендера | `processing_stats` | 🟡 то же |
| Разрез по машинам | `processing_stats.machine` | 🟡 то же |
| Посещения | `visitor_events` | ✅ (своя витрина в админке) |

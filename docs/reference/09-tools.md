# 09 — Инструменты и работа с документами

Два независимых блока: раздел «Инструменты» — редактор титров и озвучка — и
система markdown-описаний проекта.

Это описание того, что есть. Рядом, в `docs/`: как сделать новый инструмент —
[TOOLS_DEV_GUIDE.md](../TOOLS_DEV_GUIDE.md); каждый существующий инструмент
подробно — [SRT_EDITOR.md](../SRT_EDITOR.md) и [VOICE_OVER.md](../VOICE_OVER.md).

# Часть I. Раздел «Инструменты»

Открывается как раздел рабочей области: `/account/projects?tab=tools`. Своё
дерево компонентов, но **внутри того же провайдера** — ему нужны и режим
области, и список проектов (из них выбирается папка задачи).

## 1. Каталог инструментов — в коде

`lib/tools/registry.ts`. Не таблица, и это осознанно: у инструмента есть
интерфейс, поэтому появление нового — всё равно деплой. Таблица добавила бы
второй источник правды и состояние «запись есть, кода нет».

```ts
type ToolDefinition = {
  key: string            // стабильный ключ, попадает в БД, менять нельзя
  kinds: ToolKind[]      // srt | text | video | image | audio | data — из них теги-фильтры
  icon: string           // строковый ключ: модуль читают серверные роуты
  status: "ready" | "soon"
  defaults: Record<string, unknown>
}
```

Имена и описания — не здесь, а в словаре `components/account/i18n.tsx`. Связь
«ключ инструмента → три ключа словаря» держит `TEXT` в
`components/account/tools/registry-ui.ts` (`toolSrtEditorName` / `…Short` / `…Long`),
там же иконки — реестр читают серверные роуты, и React-компонентам в нём места нет.

| Ключ | Виды | Статус | Настройки по умолчанию |
| --- | --- | --- | --- |
| `srt-editor` | srt, video, audio | ✅ ready | `sourceRoot: "OUT"`, `hiddenProjectIds: []`, `autoExport: true`, `autosaveMs: 15000` |
| `voice-over` | audio, srt | ✅ ready | `sourceRoot: "OUT"`, `hiddenProjectIds: []`, `concurrency: 2` |

`status: "soon"` — виден в каталоге, добавить нельзя.

## 2. Экземпляры

Таблица `user_tools`. У экземпляра есть имя, настройки, подключённый источник
(проект + папка задачи), порядок и отметка последнего открытия.

`PATCH /api/account/tools/[id]` **сливает** `settings` и `source` с сохранёнными,
а не заменяет: страница присылает только то, что поменяла, и не должна знать про
остальные ключи.

Удаление мягкое (`deleted_at`).

## 3. Подключение источника

`components/account/tools/source-picker.tsx` — каскадное меню: проект → папка
внутри `settings.sourceRoot` (по умолчанию `OUT`). В `source.label` пишется
человекочитаемая подпись вроде `Sharing Test / OUT / Moneyball`.

Инструмент работает **только онлайн**: папка в хранилище — единственное место,
где лежат файлы, локального кеша нет.

## 4. Область открытого инструмента

`components/account/tools/tool-host.tsx`:

```
tool.toolKey === "srt-editor"  → <SrtEditor tool={tool} />     ← вся область его
tool.toolKey === "voice-over"  → <VoiceEditor tool={tool} />   ← вся область его
иначе                          → общая шапка + сводка документа
```

У инструмента с собственным рабочим местом вся область, с топбаром включительно,
принадлежит ему: топбар несёт счётчики, переключатель языка и экспорт, которые
знает только он.

Ветка «общая шапка + сводка» (`TaskSummary`) — задел под будущие инструменты:
оба существующих имеют своё рабочее место.

# Часть II. Редактор титров по дорожкам персонажей

Полная техдокументация — `docs/SRT_EDITOR.md`, формат документа —
`docs/DIALOG_FORMAT.md`, план — `docs/TOOLS_SRT_EDITOR_PLAN.md`. Здесь — карта.

## 5. Что это

Редактор субтитров, где каждая дорожка — персонаж. Читает папку задачи из `OUT`,

## 7. Документ `dialog.json`

```ts
DialogDoc = {
  format: "dialogDoc", version: 1,
  id, revision, updatedAt, updatedBy, producer,
  media:     { video, mix, peaks, durationMs, fps },
  languages: { original, targets[] },
  rules:     DialogRules,
  tracks:    Track[],
  cues:      Cue[],
  removed:   { id, at }[],
  extra?:    {…}
}
```

| Сущность | Ключевое |
| --- | --- |
| `Cue` | `trackId`, `startMs`/`endMs`, `text`, переводы `tr` по коду языка, `status` (`auto`/`edited`/`approved`/`conflict`), `rev`, `origin`, `extra` |
| `Track` | `no`, `name`, `color`, свой `audio` и свои `peaks` (может не быть), `diar`, `voice` |
| `DialogRules` | `maxCps: 25`, `maxTranslationRatio: 1.2`, `minDurationMs: 250`, `minGapMs: 80`, `overlapWithinTrack: "forbid"` |

**Поле `extra` есть у документа, дорожки и реплики.** В него складывается всё,
чего эта реализация не знает, и записывается обратно как есть — чтобы вторая
реализация (локальный редактор) не теряла свои поля.

Порядок реплик в файле: `startMs`, затем `trackId`, затем `id` — детерминированно,
чтобы диффы файла были осмысленными.

### Отказ вместо молчаливой починки

`parseDialogDoc` при проблеме **отказывается открыть** документ. Причины
(`DocError`): не наш файл, версия новее, плохой путь, дубль дорожки, дубль
реплики, неизвестная дорожка, некорректный интервал, отсутствующее поле.

Документ общий с программой, и «поправили и записали обратно» испортило бы файл
у второй стороны. Текст ошибки подбирает интерфейс — модель возвращает только
повод.

`DOC_VERSION = 1` — единственная поддерживаемая major-версия.

### Цвета дорожек

`TRACK_COLORS` — цвета по умолчанию, когда конвейер их не проставил.
`TRACK_PALETTE` (12 цветов) — из чего человек выбирает руками.

Не пипетка и не колесо: цвет здесь — метка персонажа, и её задача одна —
отличаться от соседней. Свободный выбор на тёмном фоне даёт нечитаемые оттенки,
поэтому набор фиксированный и проверенный на этом фоне.

## 8. Правки и отмена

Все операции модели чистые: принимают документ, возвращают новый. Поэтому
**undo — это стек снимков ссылок**, а не обратные действия. Одно движение мыши
(протяжка клипа) = один шаг отмены: `setTiming` принимает признак `gesture`.

## 9. Инструменты таймлинии и горячие клавиши

| Инструмент | Клавиша по умолчанию |
| --- | --- |
| выделение (`select`) | `V` |
| создание (`create`) | `C` |
| разрез (`razor`) | `B` |
| перенос (`shift`) | `M` |
| объединение (`merge`) | `J` |
| play/pause | `Space` |
| основная волна (`mainWave`) | `W` |

Клавиши хранятся **кодом физической кнопки** (`KeyB`), а не набранным символом:
`event.key` зависит от раскладки — на русской та же кнопка даёт «и», и привязка к
букве перестаёт работать, пока не переключишь язык. Переназначаются в настройках.

## 10. Флаги дорожки — это вид, а не документ

`TrackFlags = { solo, mute, shy, wave }` живут вне документа.

Что звучит, решают `solo` и `mute`; `wave` — показывать волну этой дорожки или
нет. Волна на звук не влияет и наоборот: иначе одна кнопка делала бы две разные
вещи.

Звук — один режим на редактор, `SoundMode`: `main` (звучит звук видео, дорожки
молчат), `solo` (звучат только дорожки с `solo`) и `mute` (звучат все, кроме
выключенных). `solo` старше `mute`: пока `solo` включён хоть где-то, нажатые
раньше `M` на звук не влияют. В режимах `solo` и `mute` звук видео заглушён,
иначе к стему подмешивался бы тот же голос из микса. Слышно только дорожки с
`tracks[].audio` и найденным файлом; если таких нет — тишина, и подпись под
превью называет причину.

Волна дорожки: своя, если есть; иначе общая, приглушённо.

## 11. Автосохранение

`use-autosave.ts`:

| Параметр | Значение | Почему |
| --- | --- | --- |
| Затишье | 1200 мс | человек ждёт, что правка сохранится сразу. Задержка нужна только чтобы протяжка клипа и набор текста уехали одной записью, а не шестьюдесятью |
| Максимум ожидания | 8000 мс | дольше не тянем даже при непрерывной работе |

Состояния: `clean` → `pending` → `saving` → `saved` | `merged` | `error`.

## 12. Запись документа: `PUT /api/account/tools/[id]/document`

**Читает-сливает-пишет на сервере**, а не тремя запросами из браузера, и по
одной причине: между чтением и записью не должно быть окна, в которое влезет
вторая вкладка.

```
PUT { doc, baseRevision }
  → находим экземпляр инструмента, из него projectId + folderPath
  → requireProjectAccess(projectId, userId, "editor")
  → parseDialogDoc(doc)         ← испорченный документ до хранилища не доходит
  → читаем dialog.json из папки
  → ревизия в папке совпадает с baseRevision?
        да  → пишем поверх
        нет → mergeDialogDocs(наш, их)  и пишем результат
  → stampForSave: revision, updatedAt, updatedBy, producer
  → writeNotifyUpload — ТОТ ЖЕ путь записи, что у остальных файлов проекта
```

Последнее важно: журнал изменений и курсор синхронизации остаются верными,
документ виден в дереве и уезжает клиентам через `delta`.

### Правила слияния

| Ситуация | Решение |
| --- | --- |
| Реплика только у одной стороны | берётся как есть, если её нет в `removed` у другой |
| Реплика у обеих | выигрывает та, у которой больше `rev` |
| `rev` равны, содержимое разное | берётся **наша** (мы правим прямо сейчас), выжившая помечается `status: "conflict"` — человек должен увидеть, что чужая правка не пропала бесследно, а была перекрыта |
| Дорожки | объединение по `id`; имя и цвет — из документа с большей `revision` |
| `removed` | объединение; всё, что в нём, выбрасывается из реплик |
| `revision` результата | `max(наш, их) + 1` |

Побеждать «последнему записавшему» нельзя — это молча стирает чужую работу.

Тот же алгоритм переезжает в локальный редактор программы, где применяется по
`mtime` + `size` вместо ETag.

## 13. Экспорт

`SRT`, `SRT с BOM` (для плееров, которые иначе не читают UTF-8), `VTT`.
`settings.autoExport` — экспортировать при каждом сохранении документа.

## 14. Что нужно от программы обработки

Папка задачи в `OUT` (контракт — `docs/SRT_EDITOR.md`, часть II):

```
OUT/{задача}/
  dialog.json          ← документ
  source.mp4           ← видео
  mix.peaks.json       ← общая волна
  {no}/orig.srt        ← сырьё титров дорожки
  {no}/{lang}.srt      ← переводы
  {no}/audio.wav       ← стем дорожки (необязательно)
  {no}/audio.peaks.json
  exports/             ← результаты экспорта
```

Со стороны программы нужны две новые ноды: `audioPeaks` (пики для таймлинии) и
`dialogDocBuild` (сборка документа). Оба помечены ⬜ в плане; реальные данные
приходят из конвейера Cast Analyzer Next
(`scripts/import-castanalyzer.mjs` конвертирует его проекты в задачи).

# Часть III. Озвучка

Инструмент целиком — [VOICE_OVER.md](../VOICE_OVER.md), решения и статус —
`docs/TOOLS_VOICEOVER_PLAN.md`. Здесь — карта.

## 15. Что это

Тот же документ и та же папка, что у редактора титров: озвучка — следующий шаг над
тем же материалом. Реплика уходит в синтез, результат встаёт клипом на дорожку
своего персонажа, там же его правят и оттуда выгружают сведённый звук.

Инструмент **отдельный**, а не вкладка в редакторе титров: работы разные, и
таймлиния у них про разное. Компоненты при этом общие — каркас в `shared/`.

## 16. Карта кода

### Логика — `lib/tools/voice/` (чистая, кроме сведения)

| Модуль | Что |
| --- | --- |
| `stub.ts` | поддельный синтез: настоящий звук, длительность по тексту, форма волны по словам. Заменяется одним модулем «текст → байты» |
| `wav.ts` | запись PCM в WAV; `toInt16` |
| `export.ts` | `planVoiceExport` — какие тейки, в какие файлы, под какими именами |
| `render.ts` | сведение через `OfflineAudioContext`. Единственное, чему нужен браузер |

Тейки в документе — в `lib/tools/dialog/voice.ts`: озвучка живёт в том же
`dialog.json`, а не в своём файле.

### Интерфейс — `components/account/tools/voice/`

| Файл | Что |
| --- | --- |
| `voice-editor.tsx` | сборка: топбар (язык, «озвучка / оригинал», счётчик, «Озвучить всё», экспорт), зоны, клавиши |
| `voice-context.tsx` | состояние и операции одним объектом |
| `prefs.ts` | настройки вида, раскладка клавиш, сколько генераций в полёте |
| `cue-list.tsx` | две колонки: что озвучиваем и разметка для синтеза |
| `timeline-pane.tsx` | слой клипов тейков на общем каркасе; титры позади полупрозрачными |
| `use-generation.ts` | очередь генерации: состояния, отмена, дописывание документа перед запросом |
| `export-dialog.tsx` | выгрузка и ход сведения |
| `settings-dialog.tsx`, `help-dialog.tsx` | настройки и справка |

### Роут генерации

`POST /api/account/tools/[id]/voice/generate` — синтезирует одну реплику, пишет
файл и пики в `{NN}/voice/` папки задачи и возвращает описание тейка. **Документ
роут не правит**: тейк в документ добавляет клиент, чтобы у правки был обычный
путь — отмена, автосохранение, слияние.

## 17. Что добавляется в документ

`tracks[].voice` — чем озвучивать дорожку (провайдер, голос, пример голоса).
`cues[].voice` — что и чем озвучено: разметка для синтеза по языкам и список
тейков.

У тейка есть `offsetMs`, `rate` и `gainDb` — **параметры, а не запечённое в файл**:
файл синтеза остаётся как пришёл, подстройка живёт в документе и применяется при
воспроизведении и при экспорте. И `source` — текст, который отдали синтезу: по нему
видно, что титр правили после генерации.

## 18. Экспорт

Только **WAV**: сведение идёт в браузере, `ffmpeg` у сайта нет. Три пункта в
меню — всё одной дорожкой, все дорожки по отдельности, расширенное окно. Правило
имён то же, что у титров: один файл отдаётся файлом, несколько — архивом, язык
внутри архива становится папкой.

⚠️ `rate` при сведении применяется пересэмплированием и **меняет высоту голоса**, а
в превью браузер её сохраняет. Окно экспорта об этом предупреждает; закрывается
это `atempo` у `ffmpeg`, когда рендер уедет на сервер.

# Часть IV. Описание проекта (markdown)

Формат — `docs/DESCRIPTION_FORMAT.md`, эталон — `docs/description.example.md`.

## 19. Что это

`options/description.md` в папке проекта — развёрнутый бриф: текст с цветными
выделениями, картинки, таблицы, блок-схемы. Отдельный файл, а не поле в
`options.json`: тот принадлежит редактору нод, его формат задаёт десктоп.
Короткая подпись остаётся в `projects.description` — она нужна на карточке в
списке, а ходить за ней в R2 на каждый рендер нельзя.

Пишет команда (админский «Конвейер» или программа), читает клиент.

## 20. Конвейер рендеринга

```
markdown → remark-parse → remark-gfm → remark-rehype(allowDangerousHtml)
         → rehype-raw → rehype-sanitize(descriptionSanitizeSchema) → HTML
```

**Порядок критичен.** Если санитайз встанет раньше `rehype-raw`, разметка либо не
разберётся, либо пролезет непроверенной. Санитайз обязателен именно **на
рендере**, а не только при сохранении: файл приходит из программы и мог быть
отредактирован кем угодно — доверенным содержимым он не является ни для одной из
сторон.

Один и тот же конвейер в трёх местах: просмотрщик
(`components/markdown/markdown-view.tsx`, через `react-markdown`), загрузка в
редактор (`lib/markdown/markdown-to-html.ts`, через `hast-util-to-html`), превью
внутри редактора. Одним компонентом рисуется и панель, и модалка, и превью —
иначе «как вижу» и «как сохранится» разъезжались бы.

## 21. Палитра: в файле имя цвета, не код

```html
<span class="fg-yellow">текст</span>
<span class="fg-red bg-yellow">текст</span>
```

В файле лежит **имя** цвета; в токен темы его превращает CSS в
`app/globals.css`. Ступень насыщенности (`-2`, `-3`) — прозрачность того же
токена. Новых цветов не заводится.

Всё вложено в `.md-palette`, а не лежит глобально, по двум причинам: имя
`bg-muted` из контракта совпадает с утилитой Tailwind от токена `--muted`, и без
вложенности они спорили бы за одно правило; плюс имена палитры не текут в
остальной интерфейс. Тот же класс висит на сетке образцов в тулбаре — цвет
кнопки берётся оттуда же, откуда цвет текста, и не может разъехаться.

Доступно: `blue`, `green`, `orange`, `red`, `yellow`, `teal`, `purple`, `cyan`,
`pink`, `muted` (по три ступени каждый) и серая шкала `gray-0`…`gray-5`.
Заливка (`bg-*`) не меняет цвет текста: `fg-*` и `bg-*` могут стоять на одном
span.

Плюс `align-left|center|right|justify` и `indent` (красная строка).

## 22. Типографика

`.md-body` в `app/globals.css`. `@tailwindcss/typography` в проекте нет, и он всё
равно не знает про классы `fg-*` / `align-*` / `indent`.

Две переменные задают всё остальное:
- `--md-font-size` (14px) — базовый кегль, вся типографика считается от него в
  `em`, поэтому переключатель размера в модалке меняет одну переменную;
- `--md-measure` (820px) — ширина колонки текста; контейнер при этом тянется.

Правила адаптивности, без которых описание ломает страницу (жёстких размеров в
файле нет by design):
- `overflow-wrap: anywhere` — длинный путь или URL иначе распирает layout;
- широкая таблица прокручивается внутри `.md-table-wrap` — обёртку из markdown
  задать нельзя, её ставит рендерер;
- `pre { overflow-x: auto }`;
- `img { max-width: 100%; height: auto }`.

## 23. Два редактора, одна панель кнопок

| Режим | Модуль API | Что внутри |
| --- | --- | --- |
| Текстом | `lib/markdown/editor-api.ts` | поверх чистых функций `markdown-commands.ts` |
| «Как выглядит» | `lib/markdown/tiptap-api.ts` | Tiptap, схема расширений повторяет закрытый список HTML из контракта |

Тулбар (`components/markdown/markdown-toolbar.tsx`) один и не знает ни про
синтаксис markdown, ни про имена классов палитры — за интерфейсом `EditorApi`
стоят две реализации. Так же устроено в программе.

## 24. Блок-схемы

Фенсы с языком `mermaid` рендерит `components/markdown/mermaid-block.tsx`. Библиотека
импортируется **динамически**. Незнакомый язык фенса обязан выглядеть обычным
блоком кода, а не ошибкой: диаграмма получает свой контейнер `.md-mermaid`, всё
остальное остаётся `<pre>`.

Цвета диаграммы задаются через `mermaid.initialize` готовыми CSS-значениями,
считанными из токенов темы, — потому что mermaid не понимает `hsl(var(--…))`.

## 25. Картинки внутри файла

Картинки лежат в самом markdown как `data:`-URI. `next/image` для `data:` не
годится, поэтому просмотрщик рисует обычный `<img>`. Подготовка (сжатие,
масштабирование перед вставкой) — `lib/markdown/prepare-image.ts`.

Картинка без `src` после санитайза — это вырезанный мусор, а не картинка, и не
рисуется вовсе.

# Часть V. Сборка элемента в `IN`

## 26. Что это и почему не инструмент каталога

Обработка начинается с **одного** элемента в папке `IN`, поэтому набор файлов
собирают в папку. Диалог собирает такую папку по требованиям ноды `checkFolder`
и заканчивается запуском обработки.

В каталоге «Инструментов» его нет, и это решение владельца: инструмент правит
то, что обработка уже положила в `OUT` (`TOOLS_DEV_GUIDE.md §0`), а этот диалог
работает в `IN` **до** обработки. Подключать ему нечего — папка всегда одна.
Поэтому это диалог рабочей области, а `user_tools`, `source` и `settings` ему не
нужны.

Флаг установки — `workspace.element` (`kind: "subsystem"`). Читает его серверная
страница `/account/projects` и передаёт пропсом: состояние флагов лежит в базе,
и модуль, который её читает, тянет `pg`.

**Главное свойство: имена файлов даёт инструмент, а не человек.** Человек
приносит файл, инструмент кладёт его под именем, которое ждёт граф.

## 28. Откуда берётся форма

`options/onSiteFolderCheckForm.json`, через `GET /api/storage/v1/sidecars?name=on-site-folder-check-form`.
**`options.json` сайт для этого не разбирает**: там граф, и доставать форму
оттуда значило бы завести второго читателя модели нод, который ломается молча
при любой правке редактора. Файл компилирует десктоп при сохранении графа — тот
же приём, что у `postSources.json`.

Нет файла — нет и кнопки: проект не собирается папками. Чужая `version` —
инструмент не открывается и говорит почему.

### Файл на «чужом» ключе — чтение мягче записи

У объекта в хранилище кроме логического имени есть физический ключ. Обычная
заливка (presign → PUT → notify) минтит его как `{uuid}-{имя}`, а сайдкары сайт
читает по ФИКСИРОВАННОМУ адресу `options/<имя>` — чтобы находить их, не
спрашивая каталог.

Файлы, залитые обычным путём до появления запрета в `writeNotifyUpload`, лежат
с uuid. В каталоге они выглядят совершенно правильно — папка `options`, верное
имя, — и отказ читать такой файл выглядит снаружи как «сайт не видит файл,
который лежит на месте». Ровно на это и напоролись при первом включении.

Поэтому GET `/sidecars` устроен так: не нашли байтов по фиксированному адресу —
спрашиваем каталог (`findFileByName`) и читаем по ключу оттуда. Второго
источника правды не появляется: строка в каталоге одна, имя в ней уникально по
индексу. Запись при этом осталась строгой — канонический ключ держит
`writeNotifyUpload`, а перекладывать байты на чтении нельзя: это молчаливая
запись в чужой проект.

## 29. Имена — единственная связь слота с файлом

```
папка элемента  -<имя по шаблону>            «-Ролик 2026-09-23 14.05»
файл в слоте    NN <label> - <исходное имя>  «01 Ведущий - clip.mp4»
файл без имени  NN <label>                   «01 Ведущий.txt»
подпапка        NN <label>                   «01 Сцена»
```

Манифеста в папке нет намеренно: он стал бы вторым источником правды, а правки
из десктопа его не обновляют. Разбор — не «до первого ` - `» (сам `label` может
содержать дефис), а: отрезать `NN `, найти среди `label` уровня самый длинный
подходящий, остаток после ` - ` считать исходным именем.

Номер — позиция, а не идентификатор: дыр не бывает, перестановка мышью
пересчитывает номера. Это переименование пачкой (см. ниже).

## 30. Интерфейс — `components/account/workspace/element/`

| Файл | Что |
| --- | --- |
| `element-dialog.tsx` | оболочка: имя папки, «Запустить», «лишние», развилка по упавшей задаче, окно редактора текста |
| `element-slots.tsx` | рекурсивная форма слотов: заливка, удаление, добавление, перетаскивание (`@dnd-kit`) |
| `element-io.ts` | закрытый список операций над папкой — единственное место, которое ходит в сеть |
| `text-editor.tsx`, `text-marks.ts` | урезанный Tiptap под формат разметки |
| `tree.ts` | переходник `DriveFile` → записи для разбора; признак «это элемент» |

Точки входа — в файловом дереве: кнопка «+ Новый элемент» в содержимом `IN`,
иконка при наведении на папку элемента и дублирующий пункт контекстного меню.

**Кнопка — такая же ячейка, как остальные, и стоит в одном ряду с ними.** Вид
плиткой — значит плитка, список — строка, колонки — строка колонки
(`NewElementCell`, три формы). Полоса во всю ширину внизу области, какой кнопка
была сначала, выпадала из ряда: она читалась как подпись к области, а не как
ещё один элемент, который можно завести. Геометрия поэтому повторяет `FileCard`
и `FileRow` вплоть до скруглений и отступов, а отличает кнопку только пунктир.

Отсюда же `useCanAddElement`: ответ нужен ДО выбора ветки разметки, потому что
пустая папка `IN` со сборкой показывает не «папка пуста», а сразу кнопку —
действие объясняет себя лучше, чем текст про него.

Иконка правки живёт во всех трёх отрисовщиках строк (`FileRow`, `FileCard`,
`FileColumn`), поэтому она есть и в упрощённом режиме, и на мобильном: те
рисуют файлы теми же компонентами.

**Зон две, и обе надо подключать отдельно.** Кабинет (`/account/projects`) и
админские «Папки пользователей» (`/admin/workspaces`) поднимают
`WorkspaceProvider` каждая по-своему, поэтому флаг `workspace.element` читает
СВОЯ серверная страница и передаёт пропсом, а `<ElementDialog />` монтируется в
СВОЕЙ раскладке. Забыть вторую зону легко, и выглядит это как «кнопки нет без
объяснений»: провайдер по умолчанию считает сборку выключенной и даже не
спрашивает сайдкар.

### Строка слота: подсказка, отказ и прогресс

**Крестика у диалога нет.** Закрывают щелчком вне окна и `Esc`; в плотной шапке
крестик отнимал место у имени и кнопки «Запустить». У общего `DialogContent`
для этого появился проп `showClose` (по умолчанию `true` — прежние диалоги не
изменились).

**Подсказка при перетаскивании считается по MIME, а не по имени файла.** Это не
выбор, а необходимость: во время перетаскивания браузер намеренно скрывает
файл, `getAsFile()` возвращает `null` до того, как его отпустят, и имя тогда
пустое. Первая версия проверки спрашивала имя — и потому всегда красила зону
зелёной, даже под видео, летящим в «Картинки». Красным красим, только когда
семейство чужое И известное (`mimeFits`): `image` принимает и `pdf`, и `svg`, и
пугать на них нельзя.

**Окончательное слово — за расширением**, уже по настоящему имени, при броске
или выборе кнопкой (`extensionFits`). Отказ обязан быть заметным: раньше файл
просто не принимался молча, а это читается как поломка интерфейса, а не как
«сюда не годится». Теперь — красная строка плюс тост с именем файла.

**Полоса загрузки — это само подчёркивание.** Зелёная полоса растёт по ширине
строки, проценты стоят справа полупрозрачными. Место у строки одно, и заводить
под прогресс второй ряд незачем; проценты приходят из `uploadProjectFileDirect`
через `onProgress` у `ElementIO.putFile`.

### Цвет и размер в редакторе текста

**Цвет выбирается нативным `<input type="color">`** — тем же способом, что в
контроле титров и в настройке тени (`components/account/options/title-control.tsx`).
Это единственный способ дать полный спектр, не заводя в проекте третий свой
пикер, и человек получает привычную пипетку системы. Рядом остаются ряд
образцов и ряд «уже использованные».

Цвет **ставится** на `change` (его видно сразу, пока крутят), а **запоминается**
в «использованные» только на `blur`: иначе ряд зарастал бы десятком
промежуточных оттенков одного движения мыши. Лишний цвет убирается крестиком на
самом образце — крестик стоит СОСЕДОМ, а не внутри, потому что кнопка внутри
кнопки это недопустимая разметка.

**Размер — шаговый регулятор `− ×1 +`, шаг 0.1**, а не выбор из списка: у
множителя нет «правильных» значений (план §8.2), есть «чуть больше» и «чуть
меньше». Единица означает «как есть», и на ней свойство снимается совсем —
писать в файл `x1` незачем. Сам шаг — чистая функция `stepScale`
(`lib/tools/element/palette.ts`), и округление в ней обязательно: `1.1 + 0.1` в
двоичной арифметике даёт `1.2000000000000002`, и это число уехало бы в файл как
есть.

Папка заводится сразу при открытии диалога, а не по кнопке «сохранить»: слоты
кладут файлы в хранилище по мере того, как их приносят, и класть их некуда, пока
папки нет. Дефис в имени держит инструмент — до запуска обе линии сборки такую
папку пропускают.

**«Запустить» снимает дефис — и только.** Это `move`-событие внутри `IN`, и
событийная линия заводит задачу сама.

## 31. Дефис — общий канал, различитель это задача

Тем же дефисом помечается брак: и десктоп (`markSkippedWithDash`), и сайт
(`quarantineTaskSource`) так метят исходник упавшей задачи. По имени состояния не
различаются вообще, поэтому диалог смотрит на задачу (`inStatusOf`): `failed` —
сначала ошибка, форма по явному действию. Иначе человеку предлагалось бы
«дособрать» то, что на самом деле сломалось.

## 32. Переименование пачкой — `writeRenameBatch`

`POST /api/storage/v1/rename` принимает либо `fileId`, либо `items[]` (до 500).
Пачка нужна перенумерации, и не только ради числа запросов: **перестановка двух
соседей поштучно невыполнима** — `01` ↔ `02` это цикл, и любое первое
переименование упирается в занятое имя.

Поэтому внутри одной транзакции две фазы: все строки уезжают на временные имена,
затем встают на окончательные (поддерево папки переезжает вместе с ней). В журнал
уходит ровно одно `move`-событие на файл — клиент не должен видеть пересадку.

## 33. Свойств ноды `checkFolder` нет в «Настройках» проекта

У этой ноды есть СВОЙ интерфейс — диалог сборки, который рисует и шаблон имени
папки, и требования к содержимому. Показать их ещё и общим списком настроек
значит завести второе поле для того же значения: правки разъезжаются, а человек
не понимает, какое из двух главнее.

Поэтому `ExposedOption` носит `nodePlugin` (`data.pluginId` ноды-владельца,
проставляется в `readExposedOptions`), а `ExposedOptionsList` отсеивает по нему
всю ноду целиком. Отсев **на показе**: в `options.json` свойства остаются на
месте, обработка читает их как раньше, а PATCH трогает только то, что человек
правил в списке.

Это единственное место, где сайт заглядывает в граф ради сборки элемента, и
заглядывает он не за формой, а за одним полем «чья это нода». Сама форма
по-прежнему целиком приезжает из `onSiteFolderCheckForm.json` — в нём есть всё необходимое.

## 34. Запрет переименования внутри элемента

Имена держит инструмент, поэтому пункт «Переименовать» не показывается ни для
папки элемента, ни для её содержимого на любой глубине (`isInsideElement`). Файл,
лежащий **прямо** в `IN`, это не касается — он обычный одиночный исходник.

Прячем в интерфейсе, жёсткой проверки в API нет. Образец жёсткого запрета, если
понадобится усилить, — `assertSidecarPlaceIsStable` в `lib/storage/write-path.ts`:
там защита стоит на уровне операции, а не в `validateLogicalName`.

# Как разработать инструмент для сайта

**Для кого.** Для того, кто садится делать **новый** инструмент в разделе
«Инструменты» кабинета. Документ отвечает на три вопроса: что нужно добавить,
чтобы инструмент появился; чем он имеет право дотянуться до данных пользователя;
по каким правилам он выглядит и ведёт себя, чтобы не выпадать из остального
кабинета.

**Что здесь не описано.** Устройство уже существующих инструментов — у каждого
свой документ:

| инструмент | документ |
| --- | --- |
| редактор титров по персонажам | [SRT_EDITOR.md](./SRT_EDITOR.md) |
| озвучка реплик | [VOICE_OVER.md](./VOICE_OVER.md) |
| раздел целиком, как он работает сейчас | [reference/09-tools.md](./reference/09-tools.md) |

Нормативные контракты, на которые ссылается этот гайд:
[DIALOG_FORMAT.md](./DIALOG_FORMAT.md) (формат документа задачи),
[STORAGE_API.md](./STORAGE_API.md) (запросы к хранилищу),
[UI_GUIDE.md](./UI_GUIDE.md) и [UI_TOKENS.md](./UI_TOKENS.md) (интерфейс).
При расхождении прав контракт, а не этот гайд.

Дата сверки с кодом: **2026-08-27** (ветка `UI_dev`).

## 0. Что такое инструмент на этом сайте

Три уровня, и путать их нельзя:

| уровень | где живёт | кто меняет |
| --- | --- | --- |
| **Определение** — что вообще есть в каталоге | [lib/tools/registry.ts](../lib/tools/registry.ts), код | разработчик, деплоем |
| **Выключатель** — есть ли инструмент на этой площадке | [lib/features.ts](../lib/features.ts), значение — в админке | администратор, кнопкой |
| **Экземпляр** — то, что человек добавил себе | таблица `user_tools`, Postgres | пользователь, кнопкой |
| **Область** — открытое рабочее место | React-дерево внутри кабинета | разработчик |

**Почему каталог в коде, а не таблицей.** У инструмента есть интерфейс, значит
появление нового — всё равно деплой. Таблица добавила бы второй источник правды
и состояние «запись есть, кода нет». Это решение зафиксировано владельцем
([TOOLS_SRT_EDITOR_PLAN.md §3](./TOOLS_SRT_EDITOR_PLAN.md)) и не пересматривается
из удобства.

**Выключатель обязателен.** Новый инструмент заводит флаг в
[lib/features.ts](../lib/features.ts) — иначе он появится на всех площадках
сразу, включая упрощённые, где он не нужен. Выключенный инструмент исчезает из
каталога и не открывается, но экземпляры в `user_tools` остаются нетронутыми:
включили обратно — всё на месте. Правила — [FEATURE_FLAGS.md](./FEATURE_FLAGS.md).

**Что инструмент не делает.**

- Не работает с локальными папками. Инструмент на сайте — только онлайн: папка
  проекта в R2 единственное место, где лежат файлы, и ничего не скачивается и не
  зеркалится. Локальная работа — это отдельная задача в десктопной программе
  ([TOOLS_SRT_EDITOR_PLAN.md §7](./TOOLS_SRT_EDITOR_PLAN.md)).
- Не запускает обработку и не является нодой конвейера. Инструмент правит то,
  что обработка уже положила в папку.
- Не заводит своих таблиц под пользовательские данные без нужды: результат
  работы кладётся в папку проекта, рядом с материалом, а не в базу.

# Часть I. Шесть шагов до появления в каталоге

Минимальный путь: инструмент виден в каталоге, добавляется, открывается, знает
свой источник. Ни миграции, ни правки таблиц для этого не нужны.

## 1.1. Таблица «что где добавить»

| # | файл | что добавить |
| --- | --- | --- |
| 1 | [lib/tools/registry.ts](../lib/tools/registry.ts) | запись в `TOOLS`: `key`, `kinds`, `icon`, `status`, `defaults` |
| 2 | [components/account/tools/registry-ui.ts](../components/account/tools/registry-ui.ts) | иконку в `ICONS` и три ключа словаря в `TEXT` |
| 3 | [components/account/i18n.tsx](../components/account/i18n.tsx) | сами строки — имя, короткое и длинное описание, **в оба словаря** (`ru`, `en`) |
| 4 | [components/account/tools/tool-host.tsx](../components/account/tools/tool-host.tsx) | ветку `if (tool.toolKey === "<key>") return <YourTool tool={tool} />` |
| 5 | `components/account/tools/<key>/` | сам инструмент |
| 6 | `app/api/account/tools/[id]/<...>/route.ts` | свои роуты, если нужны (§6) |

## 1.2. Запись в реестре

```ts
// lib/tools/registry.ts
{
  key: "srt-editor",          // стабильный ключ: попадает в БД, менять нельзя
  kinds: ["srt", "video"],    // из них собираются теги-фильтры каталога
  icon: "captions",           // строковый ключ, не компонент
  status: "ready",            // "soon" — видно в каталоге, добавить нельзя
  defaults: { sourceRoot: "OUT", hiddenProjectIds: [] },
}
```

Три вещи, которые легко сделать неправильно:

- **`key` — навсегда.** Он лежит в `user_tools.tool_key` у всех, кто добавил
  инструмент себе. Переименование ключа = потеря экземпляров.
- **`icon` — строка, а не компонент.** Модуль реестра читают серверные роуты,
  тащить в них React незачем. Сопоставление «строка → компонент» — в
  `registry-ui.ts`.
- **Имён и описаний в реестре нет.** Они в словаре: интерфейс двуязычный.

`status: "soon"` — законный способ показать инструмент до готовности. Кнопка
«Добавить» выключена на странице **и** роут `POST /api/account/tools` отвечает
`409`: роут не должен верить странице.

## 1.3. Область инструмента: два варианта

Развилка в [tool-host.tsx](../components/account/tools/tool-host.tsx):

| вариант | когда | что получает |
| --- | --- | --- |
| **Своё рабочее место** | инструменту нужен свой топбар: счётчики, языки, экспорт | всю область целиком, вместе с топбаром; сам рисует `SourcePicker` и кнопку закрытия |
| **Общая шапка** | инструменту хватает «источник + содержимое» | готовую шапку с выбором источника, переименованием и закрытием, а под ней — своё содержимое |

Оба существующих инструмента — первый вариант. Второй остаётся рабочим по
умолчанию для простого инструмента, и ломать его не надо.

**Узкий экран.** Ниже 1024 px вместо инструмента показывается заглушка
(`NarrowScreen` в [tools-workspace.tsx](../components/account/tools/tools-workspace.tsx)).
Это не косметика: раньше обе ветки раскладки жили в DOM одновременно, CSS прятал
одну, но не размонтировал, и редактор существовал в двух копиях — два `<video>`
с одним файлом (эхо через пару секунд) и два обработчика клавиш на окне.
**Никогда не рендерьте инструмент в двух ветках раскладки.**

## 1.4. Проверки перед коммитом

```bash
npm run i18n:check   # захардкоженные русские строки в components/account
npm run lint
npm run build        # он же проверяет типы
```

`i18n:check` появился не от аккуратности: целый раздел был написан на хардкоде и
прошёл ревью, потому что рядом лежали такие же файлы.

# Часть II. Экземпляр: что платформа даёт бесплатно

## 2.1. Таблица `user_tools`

[db/schema.sql](../db/schema.sql) (`CREATE TABLE user_tools`), миграция —
[db/migrations/2026-08-24-user-tools.sql](../db/migrations/2026-08-24-user-tools.sql).

| поле | смысл |
| --- | --- |
| `tool_key` | ключ из реестра |
| `title` | имя, которое человек дал экземпляру; пусто — берётся из словаря |
| `settings` | `jsonb`, параметры экземпляра; при добавлении — `defaults` из реестра |
| `source` | `jsonb`, что подключено: `{ projectId, folderPath, label }` |
| `sort_order`, `last_opened_at` | порядок в списке и отметка открытия |
| `deleted_at` | мягкое удаление: убрал инструмент — настройки не потерялись |

**`settings` и `source` сливаются, а не заменяются.** `PATCH` шлёт только то, что
изменил, а SQL делает `settings || $patch`
([lib/repositories/user-tools.ts](../lib/repositories/user-tools.ts)). Страница не
обязана знать про чужие ключи — и не должна их присылать «на всякий случай».

**Экземпляров на инструмент сейчас один.** Это ограничение интерфейса: каталог
через `instanceOf(key)` показывает у добавленного «Открыть» и «Удалить» вместо
«Добавить». Роут `POST` второй экземпляр не запрещает, таблица тоже. Если вашему
инструменту нужно несколько экземпляров (два разных источника одновременно) —
менять придётся только каталог и список, схема уже готова.

## 2.2. API экземпляров

| запрос | что делает | порог |
| --- | --- | --- |
| `GET /api/account/tools` | список своих экземпляров | сессия |
| `POST /api/account/tools` | добавить из каталога (`{toolKey}`) | сессия; `status` должен быть `ready` |
| `PATCH /api/account/tools/[id]` | `title`, `settings`, `source`, `sortOrder`, `touch` | владелец экземпляра |
| `DELETE /api/account/tools/[id]` | мягкое удаление | владелец экземпляра |

Схемы — [lib/tool-schemas.ts](../lib/tool-schemas.ts), zod. Все четыре роута
авторизуют `requireUserApi` и находят экземпляр **по паре `(id, userId)`**:
чужой экземпляр не существует, а не «запрещён».

## 2.3. Клиентский контекст

[tools-context.tsx](../components/account/tools/tools-context.tsx) даёт через
`useTools()`: список, выбранный экземпляр, каталог, `addTool` / `removeTool` /
`renameTool`, `openTool` / `closeTool`, `patchSource`, `patchSettings`,
`instanceOf`. Свой `fetch` к `/api/account/tools` из инструмента писать не нужно.

Две детали, которые сэкономят полдня:

- **Адрес — `?tab=tools&tool=<id>`.** Параметр `?id=` занят выбранным проектом, и
  рабочая область попыталась бы его открыть.
- **Счётчик в сайдбаре** обновляется событием `ffworks:tools-changed`
  (`TOOLS_CHANGED_EVENT`), его слушает
  [use-project-counts.ts](../components/account/use-project-counts.ts). Меняете
  список в обход контекста — счётчик соврёт.

## 2.4. Настройки: база или браузер

| что | где хранить | почему |
| --- | --- | --- |
| источник, скрытые проекты, правила чтения папок, лимиты провайдера | `user_tools.settings` | это свойство работы, оно должно переезжать между машинами |
| высота дорожек, кегль, зум, раскладка клавиш, ширина зон | `localStorage` через `useViewPrefs` | это свойство экрана, за которым сидят |
| что сейчас выделено, что звучит, что генерируется | память вкладки | это вообще не данные |

`useViewPrefs` ([shared/editor-state.ts](../components/account/tools/shared/editor-state.ts))
сливает сохранённое с умолчаниями по вложенным объектам: в чужой сохранённой
раскладке клавиш может не быть действия, которое вы добавили сегодня, и оно
осталось бы без клавиши.

**Состояние интерфейса в документ задачи не пишется.** Правило §2.8 контракта
формата: `solo`, `mute`, `shy`, выделение, состояние очереди — это вид, а не
результат работы. Документ общий с десктопной программой, и вид одного человека
не должен уезжать второму.

# Часть III. Как инструмент связывается с данными пользователя

Это главная часть. Инструмент — не изолированное приложение во вкладке: всё, что
есть у пользователя на сайте, ему доступно, но по правилам.

## 3.1. Карта источников

Слева — что нужно инструменту, справа — куда за этим идти. Порог — минимальная
роль в проекте ([§3.7](#37-права-лестница-а-не-флажок)).

| нужно | куда идти | порог |
| --- | --- | --- |
| список проектов пользователя (свои + расшаренные) | `useWorkspace().projects` — уже загружен провайдером | — |
| дерево файлов проекта или папки | `GET /api/storage/v1/tree?projectId=&prefix=` | viewer |
| что изменилось с прошлого раза | `GET /api/storage/v1/delta?projectId=&since=` | viewer |
| содержимое файла (JSON, текст, небольшой бинарь) | `GET /api/projects/[id]/drive/files/[fileId]` | viewer |
| медиа для `<video>` / `<audio>` | `POST /api/storage/v1/presign` `{method:"GET", s3Key}` → прямой GET в R2 | viewer |
| залить файл из браузера | `POST /api/storage/v1/presign` `{method:"PUT"}` → PUT в R2 → `POST /api/storage/v1/notify` | editor |
| записать файл с сервера | `PutObjectCommand` + `writeNotifyUpload` ([§3.5](#35-запись-всегда-через-writenotifyupload)) | editor |
| создать папку, переименовать, скопировать, удалить | `mkdir` / `rename` / `copy` / `object` в `/api/storage/v1/*` | editor |
| параметры обработки проекта | `GET/PUT /api/storage/v1/sidecars?name=options`, `PATCH /api/projects/[id]/drive/options` | viewer / editor |
| развёрнутое описание проекта (markdown) | `GET/PUT /api/projects/[id]/description` | viewer / editor |
| состояние папок (тумблер слежения) | `sidecars?name=folder-state`, `/api/projects/[id]/drive/folder-state` | viewer / editor |
| чат проекта с командой | `GET/POST /api/projects/[id]/chat` | viewer / editor |
| статистика пользователя | `GET /api/account/statistics`, `GET /api/account/stats` | сессия |
| общие словари (типы файлов, цвета, маски) | `GET /api/storage/v1/settings` | сессия |
| очередь задач конвейера | `/api/storage/v1/queue` — **для машин парка**, не для инструментов | машинный токен |
| корзина, архив, пауза проекта | `trash`, `project-state` | по операции |

Полный справочник запросов с телами — [STORAGE_API.md](./STORAGE_API.md).

**Чего в этом списке нет намеренно:** прямого доступа к базе из клиентского кода,
доступа к бакету минуя роуты, и доступа к проектам других пользователей
([§8](#часть-viii-админские-инструменты)).

## 3.2. Проекты: список уже есть, своего запроса не надо

Раздел «Инструменты» живёт **внутри того же провайдера**, что и раздел проектов
([workspace-page.tsx](../components/account/workspace/workspace-page.tsx)), именно
затем, чтобы инструменту достались список проектов и режим области. Берите
`useWorkspace().projects` — там уже и свои, и расшаренные (`sharedWithMe`), с
флагами `isPaused`, `isArchived`, `deletedAt`.

Фильтр «что вообще можно подключить» — `pickableProjects` в
[source-picker.tsx](../components/account/tools/source-picker.tsx): пауза и архив
отсекаются всегда (работать с ними нечего), остальное — решение пользователя,
оно живёт в `settings.hiddenProjectIds` **этого экземпляра**, а не в настройках
аккаунта: у второго инструмента список может быть свой.

## 3.3. Источник: проект плюс папка

`source = { projectId, folderPath, label }`. Больше в нём ничего нет и быть не
должно: `label` — только подпись для карточки, доверять ей нельзя, при каждом
открытии путь перечитывается из хранилища.

Корень, внутри которого ищутся задачи, — `settings.sourceRoot` (по умолчанию
`OUT`). Что считать задачей внутри корня, решает **правило пары «инструмент —
проект»**: `settings.projectRules[projectId] = { rule, sort }`, где `rule` — одно
из `folders` (папки первого уровня), `srt` (только `*.srt` в корне), `flat` (всё).
Код — [shared/project-rules.ts](../components/account/tools/shared/project-rules.ts).

**Почему правило не общая настройка.** Раскладку `OUT` задаёт граф обработки, и
она у каждого проекта своя: у одного задача — папка, у другого в корне лежат
готовые файлы. Одна общая настройка означала бы «либо один проект работает, либо
другой».

Если ваш инструмент работает не с папкой задачи, а, скажем, с одним файлом или со
всем проектом целиком — расширяйте `source` своими ключами (они сливаются, а не
затирают чужие), но **не переиспользуйте `folderPath` под другой смысл**: на него
смотрят и общая шапка, и серверные роуты.

## 3.4. Чтение файлов: три разных пути, и они не взаимозаменяемы

| что читаем | чем | почему не иначе |
| --- | --- | --- |
| дерево папки | `GET /api/storage/v1/tree` | единственный источник правды о содержимом; в R2 напрямую клиент не смотрит |
| документ, JSON, текст | `GET /api/projects/[id]/drive/files/[fileId]` | отдаёт байты через сервер, доступ проверен, файл небольшой |
| видео и аудио | подписанный GET прямо в R2 (`presign`) | плееру нужен `Range`; через наш роут перемотки нет — он умеет только доиграть скачанное |

Готовые хуки на всё это — в
[shared/use-task-folder.ts](../components/account/tools/shared/use-task-folder.ts):
`useTaskFolder`, `useSignedUrl`, `useSignedUrls` (кэш подписанных ссылок на час),
`useDocPeaks`, `usePeaksByPath`, `findEntry`.

`findEntry` существует не для красоты: пути внутри документа относительные
(`01/audio.wav`), дерево знает абсолютные, и наивный поиск по имени подставил бы
файл из соседней папки.

## 3.5. Запись: всегда через `writeNotifyUpload`

Байты в бакет и строка в базе должны появляться вместе. Поэтому запись — не
`PutObject` и всё, а `PutObject` + `writeNotifyUpload`
([lib/storage/write-path.ts](../lib/storage/write-path.ts)). Второй вызов:

- заводит строки файла и промежуточных папок — без него файл попадёт в
  хранилище, но пропадёт из дерева;
- пишет журнал изменений, по которому живёт инкрементальная синхронизация
  десктопа (`delta`);
- решает, кто «заливщик» файла.

**Про `actor.isUploader`.** `contact` задачи конвейера — это тот, кто принёс
исходник. Инструмент исходников не приносит: он правит документ и кладёт
результаты. Поэтому все записи инструментов идут с
`actor: { userId, isUploader: false }`, и `contact` задачи от сохранения не
переезжает. Скопируете это поле неправильно — статистика конвейера начнёт
приписывать чужие задачи тому, кто просто нажал «сохранить».

## 3.6. Свой документ в папке: как писать безопасно

Если инструмент правит файл, который может править кто-то ещё (второй человек,
вторая вкладка, десктопная программа) — путь записи ровно один, он реализован в
[document/route.ts](../app/api/account/tools/%5Bid%5D/document/route.ts) и
описан в §8 [DIALOG_FORMAT.md](./DIALOG_FORMAT.md):

1. Клиент присылает документ целиком и `baseRevision` — ревизию, от которой правил.
2. Сервер **читает-сливает-пишет сам**, одним запросом. Три запроса из браузера
   оставили бы окно, в которое влезет вторая вкладка.
3. Запись условная, `If-Match` по ETag. Хранилище на несовпадение отвечает `412`,
   попытка начинается заново от актуальной версии, до трёх раз.
4. Ревизия в папке не совпала с `baseRevision` — значит документ тронули со
   стороны: делается слияние, и клиенту возвращается документ целиком с флагом
   `merged`, потому что его копия теперь неверна.
5. Трижды не удалось — `409`, клиент пробует позже (в
   [use-autosave.ts](../components/account/tools/shared/use-autosave.ts) это три
   попытки с паузой, без пугающих сообщений).

Испорченный документ до хранилища не доходит: разбор с валидацией на входе,
`422` в ответ. **Перезапись битым файлом хуже потери несохранённых правок** — это
правило, а не предпочтение.

Отдельно: документ не «починяется молча». Если он не проходит валидацию при
открытии — инструмент отказывается его открывать и говорит почему
(`docErrorText`). Файл общий с программой, и тихо исправленный документ испортил
бы его у второй стороны.

## 3.7. Права: лестница, а не флажок

Одна лестница на весь сайт — [lib/project-roles.ts](../lib/project-roles.ts):

```
viewer (1) → editor (2) → full (3) → owner (4)
```

Проверки почти везде «не ниже чем», поэтому `full` проходит там, где хватает
`editor`, а владелец — везде. Матрица «что даёт роль» — `permissionsFor()`, и
смотрят в неё **и роуты, и интерфейс**: иначе кнопка и проверка расходятся.

Две функции с одним именем, и путать их нельзя:

| функция | для чего | как отвечает |
| --- | --- | --- |
| `requireProjectAccess` из [lib/project-access.ts](../lib/project-access.ts) | роуты кабинета, авторизация сессионной кукой | нет доступа — `404` (чужой проект не подтверждает своё существование), роль ниже — `403` с внятным текстом |
| `requireProjectAccess` из [lib/storage/auth.ts](../lib/storage/auth.ts) | `/api/storage/v1/*`, знает и машинные токены | всегда `404` — контракт с десктопом менять нельзя |

Роуты инструментов берут **первую**: они часть кабинета.

Правило порога простое: читать — `viewer`, менять что-либо в проекте (включая
запись документа и генерацию файлов) — `editor`. Не полагайтесь на то, что
кнопки нет: `SourcePicker` показывает и расшаренные проекты, среди них бывают
`viewer`.

## 3.8. Чего платформа пока не даёт

Список честный — это то, чего нет, а не «работает частично».

| чего нет | следствие для нового инструмента |
| --- | --- |
| серверной очереди заданий для инструментов | долгая работа живёт в памяти вкладки; перезагрузка страницы теряет очередь (так сделана генерация озвучки) |
| фоновых задач с прогрессом | всё, что дольше запроса, придётся резать на запросы самому |
| вебсокетов и подписки на изменения папки | о чужой правке узнаёте только при сохранении (слияние) или перечитывании |
| записи результата в `exports/` | экспорт уходит файлом в браузер, а не в папку задачи |
| доступа к проекту другого пользователя | админский инструмент пока невозможен ([§8](#часть-viii-админские-инструменты)) |
| локальной папки на диске | инструмент на сайте только онлайн |

# Часть IV. Дизайнерская база

Инструмент живёт в **рабочей области** — это одна из трёх зон сайта, и у неё своя
стилистика. Подробно — [reference/12-ui-guidelines.md](./reference/12-ui-guidelines.md)
и [UI_GUIDE.md](./UI_GUIDE.md); здесь то, что касается инструментов.

## 4.1. Что задано зоной и не обсуждается

| | как в инструменте |
| --- | --- |
| шкала цветов | **только `ws-*`**: `bg-ws-panel`, `text-ws-1…5`, `bg-ws-action`, `border-white/10` |
| шрифт | IBM Plex Sans (наследуется от оболочки, ничего указывать не надо) |
| плотность | высоты 34–52 px, кегль 11–16 px, панели без внешних отступов |
| тон | плоские панели, тонкие бордеры, **никаких анимаций появления** |
| скролл | скроллятся внутренние панели; страница — никогда (`h-dvh` фиксирован) |
| иконки | только `lucide-react` |
| строки | только через словарь: `const { t } = useWorkspace()`, подстановка `tf(t.key, {…})` |
| минимальная ширина | 1024 px; ниже — заглушка, а не сжатая раскладка |

Поверхности и текст в двух словах: `ws-well` — самое глубокое (колонки), `ws-panel`
— панели и зоны, `ws-control` — строки, карточки, инпуты, `ws-raised` — диалоги и
меню, `ws-hover` — ховер приподнятого. Иерархия текста задаётся **ступенью**
(`text-ws-1` … `text-ws-5`), а не размером шрифта. Новых цветов не заводим —
набираем прозрачностью (`bg-white/[0.03]`, `border-white/10`).

Отдельные акценты, которые уже принадлежат инструментам: `ws-select` — выделение
и активные сегменты, `ws-out` — «есть результат» (он же акцент панели OUT),
`ws-playhead` — курсор воспроизведения. Последний единственный сигнальный цвет
зоны: красный здесь читался бы как поломка, а не как «мы сейчас тут».

## 4.2. Раскладка рабочего места

У обоих существующих инструментов одна анатомия, и новому стоит взять её же —
человек не должен переучиваться:

```
┌─────────────────────────────────────────────────────────┐
│ зона 1: топбар — источник, счётчики, язык, экспорт, ⚙, ✕ │
├──────────────────────────┬──────────────────────────────┤
│ зона 2: превью           │ зона 3: список реплик        │
│ (кадр, транспорт, звук)  │ (правка текста, статусы)     │
├──────────────────────────┴──────────────────────────────┤
│ зона 4: таймлиния во всю ширину                          │
└─────────────────────────────────────────────────────────┘
```

Границы зон тянутся мышью: [ResizeGrip](../components/account/resize-grip.tsx) +
`useDragSize`. Размеры по умолчанию и ключ `localStorage` — в `prefs.ts` вашего
инструмента.

Если инструменту не нужны ни превью, ни таймлиния — не выдумывайте им замену:
возьмите общую шапку из `ToolHost` и рисуйте одну панель с содержимым
([§1.3](#13-область-инструмента-два-варианта)).

## 4.3. Canvas и токены

Всё, что рисуется на `<canvas>` (волна, линейка, клипы), цвета получает
**строками** через `readToken` из
[shared/tokens.ts](../components/account/tools/shared/tokens.ts). Это единственное
место, где значение токена достают из CSS. Рисующий код про Tailwind не знает — и
поэтому переносится в десктопную программу без правок.

## 4.4. Горячие клавиши

- Хранятся **кодом физической кнопки** (`KeyB`), не символом. `event.key` зависит
  от раскладки: на русской та же кнопка даёт «и», и привязка к букве просто
  перестаёт работать.
- Переназначаются человеком: `HotkeyRow` / `HotkeySection` из
  [shared/settings-parts.tsx](../components/account/tools/shared/settings-parts.tsx)
  дают готовый интерфейс, ваш `prefs.ts` — список действий и умолчания.
- Справка по клавишам — `ToolHelpDialog`, открывается по `F1` и из настроек.
- Обработчик вешается на окно один раз; текущее состояние читайте через `ref`,
  иначе замыкание запомнит то, что было при подписке.

## 4.5. Чеклист UI перед коммитом

- ни одного цвета вне `ws-*` и прозрачностей;
- ни одной строки вне словаря — включая `aria-label`, `title`, `placeholder`,
  тосты, `confirm` и локаль в `toLocaleDateString`;
- страница не скроллится, скроллятся панели;
- ниже 1024 px инструмент не рендерится вовсе;
- `npm run i18n:check` чистый.

## 5.3. Скелет нового инструмента

```tsx
export function MyTool({ tool }: { tool: ToolInstance }) {
  const { t } = useWorkspace()
  const { state } = useTaskFolder(tool)                    // папка задачи
  const loaded = state.kind === "ready" ? state.doc : null

  const { doc, apply, reset, undo, redo, version } = useUndoableDoc(loaded)
  const save = useAutosave({
    toolId: tool.id,
    doc,
    version,
    revision: loaded?.revision ?? 0,
    onMerged: reset,                                       // чужую версию принимаем целиком
    networkError: t.driveUnavailable,
  })

  // Открытие задачи — не правка человека, иначе инструмент запишет в папку
  // только что прочитанный файл.
  useEffect(() => {
    reset(loaded)
    save.markClean()
  }, [loaded])

  const { prefs, setPref } = useViewPrefs(myPrefsKey(tool.id), DEFAULT_PREFS)
  // …своё состояние, свои зоны, свой контекст
}
```

Три вещи, на которых спотыкаются все:

1. **`markClean()` после загрузки.** Иначе каждое открытие задачи = запись в папку.
2. **`gesture` в правках.** Протяжка мышью даёт правку на каждый кадр; без склейки
  одно «отменить» вернёт клип на пиксель назад — шестьдесят раз подряд.
3. **Время не через `setState`.** Часы отдают время подпиской (`clock.subscribe`):
  при 60 кадрах в секунду `setState` перерисовывал бы весь редактор со списком.

## 5.4. Правила переносимости

Инструмент рано или поздно повторяют в десктопной программе, поэтому
([TOOLS_SRT_EDITOR_PLAN.md §20.3](./TOOLS_SRT_EDITOR_PLAN.md)):

- вся модель и все операции — в `lib/`, чистыми функциями, без React;
- операции над документом — **закрытый список**, а не произвольные правки полей:
  так их можно перечислить, проверить и повторить;
- рисующий код получает цвета строками;
- всё, что зависит от браузера (Web Audio, `<video>`, `localStorage`), — в
  тонком слое, который в переносе заменяется.

# Часть VI. Свои серверные роуты

## 6.1. Где и как

Роуты инструмента живут под `app/api/account/tools/[id]/…` — то есть привязаны к
**экземпляру**, а не к инструменту. Шаблон одинаковый у всех:

```ts
export const runtime = "nodejs"

export async function POST(request: NextRequest, { params }: Params) {
  const auth = await requireUserApi(request)            // 1. сессия
  if (auth instanceof NextResponse) return auth
  const { id } = await params

  const tool = await findUserTool(id, auth.userId)       // 2. экземпляр — свой
  if (!tool) return NextResponse.json({ message: "Tool not found." }, { status: 404 })

  const { projectId, folderPath } = tool.source ?? {}    // 3. источник из БД,
  if (!projectId || !folderPath)                         //    не из тела запроса
    return NextResponse.json({ message: "Tool has no source folder." }, { status: 400 })

  const access = await requireProjectAccess(projectId, auth.userId, "editor")  // 4. права
  if (access instanceof NextResponse) return access
  if (!isS3Configured())                                 // 5. хранилище на месте
    return NextResponse.json({ message: "Object storage is not available." }, { status: 503 })

  const parsed = schema.safeParse(await request.json())   // 6. zod на вход
  …
}
```

**Источник берётся из `tool.source`, а не из тела запроса.** Клиент присылает
только то, что он решил (какую реплику озвучить), а куда писать — знает сервер.
Иначе подделанное тело превращает роут инструмента в запись куда угодно.

## 6.2. Кто чем владеет

Разделение, которое уже проверено на двух инструментах:

| | владелец |
| --- | --- |
| документ задачи | **клиент**: он правит, он сливает историю отмены, он сохраняет |
| байты в хранилище | **сервер**: только он пишет, и только через `writeNotifyUpload` |
| результат долгой работы (например, синтез) | сервер кладёт файл и **возвращает описание**; вписывает его в документ клиент |

Последняя строка — не мелочь. Если бы генерация сама писала в документ, у него
стало бы два писателя, и второй гонялся бы с автосохранением первого.

Обратная сторона: если серверу нужен свежий документ, клиент обязан сначала
дописать правки (`await save.flush()`), иначе сервер прочитает версию до правки.
В озвучке это `beforeRequest` в очереди генерации.

## 6.3. Статусы

| код | когда |
| --- | --- |
| `400` | нет источника, битый JSON |
| `403` | роль ниже нужной (роуты кабинета) |
| `404` | экземпляр не свой, проекта нет или доступа нет вовсе, файла в папке нет |
| `409` | документ прямо сейчас пишет кто-то ещё — клиенту стоит повторить |
| `422` | документ или входные данные не проходят валидацию |
| `503` | хранилище недоступно или не настроено |

# Часть VII. Экспорт

Правило имён общее для раздела: **один файл отдаётся файлом, несколько —
архивом**, а внутри архива язык становится папкой
([lib/tools/dialog/export.ts](../lib/tools/dialog/export.ts),
[lib/tools/voice/export.ts](../lib/tools/voice/export.ts)).

- отдача в браузер — только через `downloadFile` из
  [shared/download.ts](../components/account/tools/shared/download.ts): он
  освобождает blob, а без `revokeObjectURL` каждый экспорт оставляет файл в
  памяти вкладки до перезагрузки;
- архив — `buildZip` из [lib/tools/dialog/zip.ts](../lib/tools/dialog/zip.ts),
  внешних зависимостей нет;
- сначала собирается всё, потом отдаётся: отдавать по одному значит оставить
  человека с половиной архива, если на третьем файле оборвётся сеть;
- **экспорт обязан применять то, что человек видел и слышал.** Если в интерфейсе
  тейк смещён, ускорен и приглушён — файл должен звучать так же, иначе следующий
  шаг получит не то, что принимали;
- запись экспорта в папку задачи (`exports/`) пока не сделана — выгрузка уходит
  в браузер.

# Часть VIII. Админские инструменты

Требование владельца зафиксировано: **админский инструмент должен уметь
подключаться вообще ко всему, включая проекты любого пользователя.** Ниже — что
для этого уже есть, чего нет, и какие решения предстоит принять. Ни одного
админского инструмента сейчас нет: раздел «Инструменты» целиком пользовательский.

## 8.1. Фундамент, который уже работает

| что | где | годится для |
| --- | --- | --- |
| выбор «пользователь → проект → дерево» | `/api/admin/workspaces/users`, `/api/admin/workspaces/projects?userId=`, `/api/admin/workspaces/projects/[id]/drive` | источник админского инструмента, ровно как в «Конвейере» |
| чтение любого файла любого проекта | `/api/admin/workspaces/projects/[id]/files/[fileId]` | открыть документ на чтение |
| служебная папка `options`, скрытая у пользователя | тот же listing с `includeServiceFiles` | инструменты, которые правят параметры обработки |
| **полный доступ ADMIN к `/api/storage/v1/*`** | `requireProjectAccess` в [lib/storage/auth.ts](../lib/storage/auth.ts): для роли `ADMIN` возвращается `accessRole: "owner"` на любой проект | и чтение, и запись — включая `presign PUT` + `notify` |
| авторство правки в документе | `stampForSave(… updatedBy: auth.email)` | видно, кто правил, даже если это админ |

То есть **на уровне хранилища админский инструмент уже возможен**: админская
сессия читает и пишет любой проект через `/api/storage/v1/*`. Это существующее
поведение, а не дыра: на нём стоит «Конвейер» и обслуживание парка машин. Но
именно поэтому админский инструмент нельзя делать «по-быстрому»: возможность
писать в чужой проект появится у него сама собой, ещё до того, как будет решено,
как это показывать и как за этим следить.

## 8.2. Чего не хватает

| препятствие | подробно |
| --- | --- |
| экземпляр всегда чей-то | `user_tools.user_id` + поиск по паре `(id, userId)`. Для админского инструмента это годится (экземпляр принадлежит админу), но `source` не знает, **чей** проект подключён: в нём только `projectId` |
| роуты инструментов не знают админа | `requireProjectAccess` из [lib/project-access.ts](../lib/project-access.ts) админу привилегий не даёт — на чужой проект будет `404`. Значит `PUT …/document` и подобные для админского инструмента не работают |
| `PATCH …/tools/[id]` не проверяет доступ к проекту | в `source` можно записать любой `projectId`; защиту сейчас держат пути чтения и записи, каждый из которых проверяет доступ сам. Для админского инструмента это станет единственной проверкой — её надо будет добавить явно |
| каталог один на всех | `TOOLS` не различает пользовательские и админские инструменты; каталог кабинета покажет админский инструмент любому |
| выбор источника рассчитан на свои проекты | `SourcePicker` берёт `useWorkspace().projects` — это проекты текущего пользователя |
| нет следа «правил админ» | в документе остаётся `updatedBy`, но у пользователя нет никакого признака, что в его проекте работал администратор |

## 8.3. Решения, которые предстоит принять

Рекомендации — мои, не согласованные; последнее слово за владельцем.

| # | вопрос | варианты | рекомендация |
| --- | --- | --- | --- |
| 1 | где живут админские инструменты | (а) отдельный раздел в `/admin`; (б) тот же раздел кабинета с признаком у инструмента | **(а)**: у админки своя зона, свой словарь и свой шелл; смешивать каталоги значит объяснять пользователю, почему часть карточек ему недоступна |
| 2 | как отличать инструмент | поле `scope: "user" \| "admin"` в `ToolDefinition` | да, и фильтровать **и в каталоге, и в `POST /api/account/tools`**: роут не должен верить странице |
| 3 | где хранить экземпляр | (а) та же `user_tools`; (б) своя таблица | **(а)**: поля те же, `user_id` — админ. В `source` добавить `ownerUserId` — не для проверки прав (её делает сервер), а чтобы показать, чей проект подключён, и чтобы выбор источника можно было восстановить |
| 4 | как авторизовать запись | (а) добавить админскую ветку в `requireProjectAccess` кабинета; (б) отдельная `requireAdminProjectAccess` | **(б)**: вариант (а) молча расширит права во всех роутах кабинета, включая те, где этого никто не ожидает |
| 5 | что видит пользователь | ничего / отметка в журнале / сообщение в чат проекта | как минимум **отметка в журнале изменений и в документе** (`updatedBy` уже есть); решение про видимость — за владельцем |
| 6 | пределы админского доступа | все проекты / только не в корзине / только с включённой автоматизацией | обсудить: «вообще всё» разумно для обслуживания, но корзина и архив — состояния, из которых лучше не править |

## 8.4. Что нельзя ломать при этом

- **`contact` задачи.** Правка админом не делает его заливщиком: `isUploader:
  false`, как и у пользовательских инструментов.
- **Журнал изменений.** Любая запись — через `writeNotifyUpload`, иначе
  синхронизация десктопа разъедется с содержимым бакета.
- **Ответ `404` на чужое.** Пользовательские роуты не должны начать отвечать
  `403` там, где раньше отвечали `404`: чужой проект не подтверждает своё
  существование.

# Часть IX. Чеклист и антипаттерны

## 9.1. Чеклист нового инструмента

**Каталог и экземпляр**
- [ ] `key` стабильный, добавлен в `TOOLS`, `kinds` заполнены осмысленно;
- [ ] иконка в `ICONS`, три ключа в `TEXT`, строки в **оба** словаря;
- [ ] `defaults` содержат всё, что инструмент читает из `settings`;
- [ ] `status: "soon"` пока инструмент не готов.

**Данные**
- [ ] источник читается из `tool.source`, а не из тела запроса;
- [ ] порог доступа выставлен на каждом роуте (`viewer` на чтение, `editor` на запись);
- [ ] запись только через `writeNotifyUpload`, `isUploader: false`;
- [ ] правка общего файла — через условную запись со слиянием;
- [ ] битые данные отвергаются, а не «починяются».

**Интерфейс**
- [ ] только `ws-*` и прозрачности; ни одной строки вне словаря;
- [ ] скроллятся панели, не страница; ниже 1024 px — заглушка;
- [ ] клавиши по `event.code`, переназначаемые, справка по `F1`;
- [ ] размеры зон и вид — в `localStorage`, работа — в `settings`.

**Проверки**
- [ ] `npm run i18n:check`, `npm run lint`, `npm run build`;
- [ ] инструмент открывается без источника и не падает;
- [ ] инструмент открывается на проекте с ролью `viewer` и не предлагает
      действий, которых нельзя.

**Документ**
- [ ] заведён `docs/<TOOL>.md` по образцу [SRT_EDITOR.md](./SRT_EDITOR.md) с
      разделом «Ограничения текущей версии»;
- [ ] инструмент добавлен в таблицы [reference/09-tools.md](./reference/09-tools.md)
      и в оглавления [docs/README.md](./README.md), [reference/README.md](./reference/README.md).

## 9.2. Антипаттерны

| нельзя | почему |
| --- | --- |
| заводить таблицу под каталог инструментов | второй источник правды и состояние «запись есть, кода нет» |
| писать в R2 без `writeNotifyUpload` | файл есть в бакете и нет в дереве; синхронизация десктопа разъезжается |
| хранить состояние интерфейса в документе задачи | документ общий с программой: чужой `solo` уедет второму человеку |
| хранить высоту дорожек и зум в `user_tools.settings` | это свойство экрана, а не работы |
| писать документ из двух мест (клиент и сервер) | гонка с автосохранением |
| рендерить инструмент в двух ветках раскладки | два `<video>` и два обработчика клавиш на окне |
| дублировать список проектов своим запросом | он уже загружен провайдером; свой запрос разойдётся с общим состоянием |
| обновлять время плеера через `setState` | 60 перерисовок в секунду вместе со списком реплик |
| привязывать клавиши к `event.key` | на русской раскладке перестанут работать |
| решать «можно ли» на клиенте | кнопки нет, а роут есть; порог ставится на сервере |

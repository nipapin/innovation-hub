# План доработок storage-бэкенда

**Кому:** разработчику (человеку или модели), который будет это реализовывать.
**Статус:** решения приняты владельцем продукта, код не написан. Ничего из разделов 2–9
в репозитории ещё нет, кроме явно помеченного «сделано».

**Что прочитать перед началом, в этом порядке:**

1. [STORAGE_SYNC_CONTRACT.md](./STORAGE_SYNC_CONTRACT.md) — разделение ответственности: каталог,
   журнал, права и ключи у бэкенда; байты и локальные копии у клиента.
2. [STORAGE_CLIENT_REQUESTS.md](./STORAGE_CLIENT_REQUESTS.md) — требования десктоп-клиента,
   написанные по чтению этого кода. Разделы 1–4 там — **баги, а не хотелки**.
3. [STORAGE_API.md](./STORAGE_API.md) — текущий справочник эндпоинтов.
4. Этот документ.

Клиент — отдельный проект `fs.manager.tauri` (Tauri + Rust), его синхронизатор реализован
и работает против мока. Раскладка зеркала на диске повторяет `projects/{userId}/{projectId}/…`,
поэтому логический путь из каталога у него превращается в путь на диске: расхождение каталога
означает «файл исчез», а не косметику.

## 1. Принятые решения

Зафиксированы владельцем продукта. Реализация не должна их пересматривать без разговора.

| # | Вопрос | Решение |
|---|---|---|
| 1 | Кто владеет именем файла | **Postgres.** Ключ R2 выдаётся один раз и не меняется никогда |
| 2 | Копирование | Внутри проекта **и между проектами / пользователями** |
| 3 | Коллизии имён | Автоматически: `имя (2).ext`, `имя (3).ext`, … |
| 4 | «Поделиться» | Только **проектом**, только внутренним пользователям. Публичных ссылок на файл/папку нет, но фундамент под них не ломаем |
| 5 | Архивные проекты | Фильтруются **на сервере** |
| 6 | Корзина | Есть, хранение **30 дней**, потом автоудаление |
| 7 | Конфликт двух правок | **Последний выиграл**, без версий и `If-Match` |
| 8 | Кто пишет в журнал | Всегда бэкенд. Клиенты ходят только через API, прямых ключей R2 ни у кого нет |
| 9 | Событие перемещения | Новая операция журнала **`move`**, одно событие на папку целиком |
| 10 | Отмена операций | **Только последнее действие.** Ни истории, ни стека, ни привязки ко времени |
| 11 | Большие файлы | Потолки снимаем, **multipart обязателен** |
| 12 | Почта | **Нужна**, отдельной инфраструктурной задачей |
| 13 | Права десктоп-клиента | Machine token — **полный доступ в папке своего владельца**: программа создаёт, переименовывает и удаляет проекты и файлы наравне с сайтом. Расшаренности она не видит и работает только с оригиналами |
| 14 | Баланс и биллинг | **Вне рамок**, не трогаем |

## 2. Модель имени (основание для всего остального)

### 2.1. Принцип

Логическое имя живёт **только** в `project_files.name` / `folder_path`.
Физический ключ `project_files.s3_key` выдаётся при первой заливке и **неизменен до удаления**.

```
логический путь   IN/материалы/Финальный монтаж.mov     ← Postgres, меняется свободно
физический ключ   projects/{userId}/{projectId}/IN/{uuid}-clip.mov   ← R2, не меняется
```

Это не новое решение: [STORAGE_SYNC_CONTRACT.md](./STORAGE_SYNC_CONTRACT.md) уже описывает
`POST /rename` как «Rename/move file or folder (**no R2 key change**)». Клиент со своей стороны
гарантирует: «`s3Key` считаем непрозрачным и никогда из него путей не выводим».

**Следствия, которые надо принять целиком:**

- переименование и перемещение — бесплатные операции над строками, байты не двигаются;
- бакет глазами человека нечитаем — имена только через API или через файлы-описатели (раздел 3);
- журнал обязан уметь сообщать о перемещении, иначе изменения невидимы для второй машины (раздел 4);
- **новые** ключи перестают зависеть от имени. Существующие ключи не переписываем — они уже
  лежат в `s3_key`, и переименование их не трогает.

### 2.2. Уровни 1–2: почта пользователя и имя проекта

Ключ `projects/{userId}/{projectId}/…` не меняется. Человеческие имена для этих двух уровней
уже есть в базе: `users.email` и `projects.name`. Нужно их отдавать и записывать рядом с данными.

**Задача 2.2.1. `GET /api/storage/v1/projects` не отдаёт `userId`.**
Блокер клиента, [STORAGE_CLIENT_REQUESTS.md §1](./STORAGE_CLIENT_REQUESTS.md). Без него
клиент не может сгруппировать проекты по пользователям, и всё сваливается в одну папку.
Добавить в `serializeProject` (`app/api/storage/v1/projects/route.ts:57`): `userId`, `ownerEmail`.

**Задача 2.2.2. `displayPath` в ответах `/tree` и `/delta`.**
Строка вида `aleksey@id.thesoul.io / Kotliar / IN / материалы`. Чтобы клиенты не собирали
её сами и не расходились в правилах.

**Задача 2.2.3. `project-meta.json` обновляется только при создании.**
`writeProjectMeta` вызывается ровно из одного места — `app/api/projects/route.ts:71`.
Переименовали проект → в бакете навсегда старое имя. Вызывать при любом изменении
`name`, `description`, `is_archived`, а также при смене владельца.

## 3. Папка проекта как источник истины

**Требование владельца:** папку проекта можно унести куда угодно, и по её содержимому
восстанавливается вся структура — имена, иерархия, принадлежность. В модели B имена лежат
в Postgres, поэтому без описателей папка станет набором uuid. Это обязательная часть модели B,
а не украшение.

Три файла внутри `projects/{userId}/{projectId}/`:

### 3.1. `project-meta.json` — паспорт проекта

Маленький, переписывается целиком при изменении полей проекта.

```json
{
  "schema": 1,
  "projectId": "uuid",
  "name": "Kotliar",
  "description": "Cat-rap production project.",
  "ownerId": "uuid",
  "ownerEmail": "aleksey@id.thesoul.io",
  "isArchived": false,
  "createdAt": "2026-07-22T13:04:00.000Z",
  "updatedAt": "2026-08-11T09:12:00.000Z"
}
```

### 3.2. `catalog.json` — снимок каталога

Полный список строк `project_files` проекта: `fileId`, `s3Key`, `folderPath`, `name`,
`isFolder`, `sizeBytes`, `contentHash`, `originMtime`, `deletedAt`, `lastSeq` и `cursor`
(значение `seq`, на котором снят снимок).

Переписывать на **каждое** изменение нельзя — на активном проекте это сотни перезаписей в минуту.
Правило: снимок пересобирается, когда с момента прошлого накопилось больше `N` событий
(старт: `N = 200`) или прошло больше суток. Пересборка — фоновой задачей, не в запросе пользователя.

### 3.3. `catalog.jsonl` — дописываемый журнал

Одна строка на событие, тот же формат, что отдаёт `GET /delta`. Дописывается в той же транзакции,
что и `storage_changes`, — точнее, сразу после её коммита (см. раздел 4.3 про надёжность).

**Восстановление** = `catalog.json` + все строки `catalog.jsonl` с `seq > cursor` снимка.

### 3.4. Где эти файлы лежат

Не под `options/`. Там уже есть открытая проблема: `/reindex` удаляет из каталога строки
под `options/` ([STORAGE_CLIENT_REQUESTS.md §3](./STORAGE_CLIENT_REQUESTS.md)), и класть туда
описатели — значит наступить на те же грабли. Предлагается служебный префикс `_catalog/`,
исключённый из листинга дерева и защищённый от `/reindex` тем же способом, что и `options/`.

### 3.5. Уровень пользователя

`projects/{userId}/user-meta.json`: `{ "schema": 1, "userId": "…", "email": "…", "createdAt": "…" }`.
Тогда, открыв бакет, можно опознать оба uuid-уровня без базы. Пишется при создании пользователя
и при смене email.

## 4. Журнал: протокол v2

### 4.1. Проблема

`writeRename` (`lib/storage/write-path.ts:443`) журналит только внутри `if (oldKey !== newKey)`
(`:509`), а оба ключа берутся из `s3_key` (`:494`), который при переименовании не меняется.

- **Файл:** `oldKey === newKey` → в `storage_changes` не попадает **ничего**. `GET /delta`
  о переименовании не расскажет никогда.
- **Папка:** `folder_path` потомков обновляется одним `UPDATE` (`:472`), но событие пишется
  только на саму папку — потомки у клиента остаются по старому пути.

Для клиента это блокер: сценарий «сайт переименовал → машина увидела» не работает.

### 4.2. Решение: операция `move`

```sql
ALTER TABLE storage_changes DROP CONSTRAINT storage_changes_op_check;
ALTER TABLE storage_changes ADD CONSTRAINT storage_changes_op_check
  CHECK (op IN ('put', 'delete', 'move'));
```

Формат события:

```json
{
  "seq": 1843,
  "op": "move",
  "key": "projects/{userId}/{projectId}/IN/{uuid}-clip.mov",
  "projectId": "...",
  "eventTime": 1722930000,
  "payload": {
    "fileId": "...",
    "isFolder": false,
    "from": { "folderPath": "IN",           "name": "clip.mov" },
    "to":   { "folderPath": "IN/материалы", "name": "Финальный монтаж.mov" }
  }
}
```

- `key` — неизменившийся физический ключ, он идентифицирует объект. Для папки `s3_key` пуст,
  туда кладётся логический путь `от` (папка в R2 не существует).
- Переименование папки — **одно** событие. Клиент переписывает префикс у потомков сам:
  `file_id` стабилен, перекачивать нечего. Клиент это подтвердил.

**Обязательно вместе с этим:** поднять версию в `GET /capabilities` (`protocol: 2`, `move: true`)
и написать клиенту, что `move` включён, — он ждёт сигнала, чтобы включить обработку у себя.

Альтернатива, которую владелец не выбрал, но она допустима, если `move` окажется дорог в реализации:
журналить `put` всегда, а для папки — `put` на каждого потомка. Тогда протокол не меняется,
но переименование папки на 500 файлов даёт 501 событие.

### 4.3. Надёжность записи в `catalog.jsonl`

`storage_changes` пишется в транзакции Postgres, R2 транзакций не знает. Правило:
сначала коммит в Postgres, затем дозапись в `catalog.jsonl`. Если дозапись упала —
это не ошибка операции; расхождение чинит пересборка снимка (3.2), которая читает из Postgres.
Postgres остаётся единственным источником истины, файлы в бакете — производные.

## 5. Переименование и перемещение

### 5.1. Что уже работает

Каскадное обновление `folder_path` у поддерева одним `UPDATE` с заменой префикса —
`lib/storage/write-path.ts:470`. Код есть и корректен, ему не хватает только журнала (раздел 4).

### 5.2. Уникальность имени

Сейчас ограничения нет: в одной папке можно создать два `cat.png`.

**Решение владельца: имена сравниваются без учёта регистра, но хранятся как введено.**
`IN` и `in` — одна и та же папка; при этом папку можно назвать `Материалы` и увидеть её
именно так.

```sql
CREATE UNIQUE INDEX project_files_unique_name_idx
  ON project_files (project_id, lower(folder_path), lower(name))
  WHERE deleted_at IS NULL;
```

Проверять **до** операции и возвращать `409` с понятным телом, а не ловить нарушение индекса.
Касается: `mkdir`, `notify` (первая заливка), `rename`, `copy`, `move`, «вставить».

### 5.3. Допустимые имена

Логическое имя превращается в имя файла на диске у клиента, поэтому фильтр — по самой строгой
из целевых систем (Windows):

- запрещены `/` `\` `:` `*` `?` `"` `<` `>` `|` и控-символы `0x00–0x1F`;
- запрещены имена `CON PRN AUX NUL COM1–COM9 LPT1–LPT9` (и они же с расширением);
- запрещены точка и пробел в конце;
- запрещены `.` и `..` целиком;
- длина имени ≤ 180 байт в UTF-8, полный логический путь ≤ 1000 байт.

Сейчас `renameFileSchema` (`lib/project-schemas.ts`) запрещает только слеши.

### 5.4. Прочее

- Перемещение папки в саму себя или в собственного потомка — `409`, иначе поддерево отвяжется.
- Вся операция — одна транзакция (уже так).
- Буфер обмена (вырезать/копировать) живёт **на клиенте**: `{ op, fileIds[] }`. В базе ничего
  не нужно, «вставить» — вызов `/move` или `/copy` со списком id и целевой папкой.

## 6. Копирование

Единственная из трёх операций, которая двигает байты. Внутри R2 это серверный `CopyObject`:
трафик не выходит наружу, но каждый объект — отдельный вызов.

### 6.1. Эндпоинт

Форма согласована с клиентом ([STORAGE_CLIENT_REQUESTS.md §5](./STORAGE_CLIENT_REQUESTS.md)):

```http
POST /api/storage/v1/copy
{
  "projectId": "...",
  "fileIds": ["...", "..."],
  "destProjectId": "...",          // опционально, по умолчанию тот же
  "destFolderPath": "IN/копии",
  "eventId": "..."
}
→ 202 { "jobId": "..." }           // для папок и пачек
→ 200 { "files": [ ... ] }         // для одиночного файла — синхронно
```

Клиенту нужен **новый `fileId`** в результате; связывать копию с оригиналом не требуется.

### 6.2. Между проектами и пользователями

Разрешено. Ключ назначения строится из `destProjectId` и **его** владельца, то есть меняется
префикс `projects/{userId}/`.

Права: актор должен иметь доступ к источнику **и** к назначению.

- машинный/админский токен — доступ ко всему (так работает десктоп: он видит оригиналы,
  расшаренности для него не существует);
- пользователь на сайте — источник это его проект или расшаренный ему, назначение — только
  тот, где у него роль `editor`.

Квоты не проверяем: биллинг вне рамок (решение 10).

### 6.3. Коллизии

`имя (2).ext`, при занятости — `(3)` и дальше. Номер подбирается без учёта регистра
(правило 5.2). Для папки суффикс приписывается к имени папки, содержимое переносится как есть.

### 6.4. Длинные операции

Копирование папки на 300 файлов в одном HTTP-запросе упрётся в таймаут.

```sql
CREATE TABLE storage_jobs (
  id           TEXT PRIMARY KEY,
  user_id      TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  project_id   TEXT NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
  kind         TEXT NOT NULL CHECK (kind IN ('copy','move','purge','recatalog')),
  state        TEXT NOT NULL CHECK (state IN ('queued','running','done','failed','cancelled')),
  total        INTEGER NOT NULL DEFAULT 0,
  done         INTEGER NOT NULL DEFAULT 0,
  error        TEXT,
  payload      JSONB NOT NULL DEFAULT '{}'::jsonb,
  created_at   TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at   TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

`GET /api/storage/v1/jobs/:id` — прогресс. Та же таблица пригодится для «Загрузить папку»,
очистки корзины и пересборки `catalog.json`.

Задача идемпотентна по `eventId`: повтор при обрыве не должен плодить дубли.

## 7. Корзина

Это же требование пришло от десктоп-клиента
([STORAGE_CLIENT_REQUESTS.md §6](./STORAGE_CLIENT_REQUESTS.md)) и там помечено как защита от потери
данных: у него удаление двухступенчатое (первое нажатие стирает локальную копию, второе — командует
`DELETE /object`), и вторая ступень сейчас уничтожает мастер безвозвратно. Для видео, которое
считали часами, это неприемлемо.

### 7.1. Текущее состояние — корзины нет

`writeFileDelete` (`lib/storage/write-path.ts:312`) ставит `deleted_at = NOW()`, чтобы записать
`last_seq`, и **тут же в той же транзакции** делает `DELETE FROM project_files` (`:425`).
Объект из R2 удаляется сразу (`DeleteObjectCommand`, `:434`). Восстановить нечего.

### 7.2. Что делать

1. Удаление помечает строку и **не удаляет** её: `deleted_at = NOW()`, плюс новое поле
   `deleted_by TEXT REFERENCES users(id)`.
2. Объект в R2 **остаётся на месте**. Ключ не меняется — восстановление это снятие пометки.
3. Все выборки уже фильтруют `deleted_at IS NULL` (`lib/storage/tree.ts:46`) — менять не нужно.
4. `GET /api/storage/v1/trash?projectId=` — список удалённого:
   `{ items: [{ fileId, name, folderPath, deletedAt }] }`.
5. `POST /api/storage/v1/trash/restore` — `{ fileId }` → снятие пометки. Если целевая папка
   удалена — восстанавливать в корень проекта; если имя занято — правило `(2)` из 6.3.
6. Автоочистка: задача `purge` раз в сутки удаляет строки и объекты старше **30 дней**,
   журналит `delete`. Ретеншен вынести в константу, а не размазывать по коду.
7. Индекс: `CREATE INDEX project_files_trash_idx ON project_files (project_id, deleted_at) WHERE deleted_at IS NOT NULL;`

Журнал: удаление в корзину — это `delete` (для клиента файл исчез), восстановление — `put`.

## 8. Расшаривание проекта

### 8.1. Границы

**Расшаривание — это выдача прав и ничего больше. Данные не двигаются.**

| | |
|---|---|
| Единица | **Только проект целиком.** Отдельный файл или папку расшарить нельзя |
| Кому | Только зарегистрированным пользователям системы |
| Где работает | **Только на сайте.** Десктоп-клиент расшаренности не видит вовсе |
| Что происходит в R2 | **Ничего.** Ни копирования, ни переноса, ни смены ключей |
| Чей проект | Остаётся проектом владельца, в его префиксе `projects/{ownerId}/{projectId}/…` |
| Что видит приглашённый | Проект в разделе «расшаренные» на своей странице проектов и возможность работать с ним по выданной роли |
| Кто может расшаривать | Владелец и участник с ролью `full`. Цепочка делегирования не ограничена по длине |

Это ключевой инвариант: приглашённый пользователь работает **с оригиналом**, лежащим
у владельца. Никакой второй копии не появляется, `projects.user_id` не меняется,
раскладка бакета не затрагивается. Всё различие — в ответе на вопрос «кто имеет право».

Публичных ссылок на файл и папку **нет** — под них пришлось бы делать отдельный интерфейс
для внешнего гостя, не зарегистрированного в системе. Схема ниже не мешает добавить их
позже отдельной таблицей `share_links`, но сейчас это вне рамок.

Кнопка «Поделиться» есть в контекстном меню проекта и показывается тем, у кого есть
право `manageMembers`, — владельцу и участнику с полным доступом.

### 8.2. Сценарий

Пользователь открывает модальное окно и вводит email:

- **пользователь есть в системе** → получает проект в разделе «расшаренные» с выданной ролью,
  ему уходит письмо-уведомление;
- **пользователя нет** → заводим аккаунт, генерируем временный пароль, отправляем письмо
  с приглашением и паролем; пароль можно сменить или оставить.

Роли: `viewer`, `editor`, `full`. Владелец проекта остаётся один, роль владельца
не выдаётся: он живёт в `projects.user_id`, строки в `project_members` на него нет.

### 8.2а. Что даёт роль

Матрица — [lib/project-roles.ts](../lib/project-roles.ts), функция `permissionsFor`.
Модуль чистый (ни базы, ни `next/server`), поэтому его берут и роуты, и интерфейс
([components/account/workspace/access.ts](../components/account/workspace/access.ts)):
матрица одна, а не по копии на слой — иначе кнопка и проверка расходятся.

| Действие | `viewer` | `editor` | `full` | владелец |
|---|:--:|:--:|:--:|:--:|
| Видеть проект, дерево, описание; скачивать файлы; читать чат | ✅ | ✅ | ✅ | ✅ |
| Писать в чат | — | ✅ | ✅ | ✅ |
| Заливать, создавать, переименовывать, удалять, перемещать файлы | — | ✅ | ✅ | ✅ |
| Параметры обработки, пауза слежения, состояние папок | — | ✅ | ✅ | ✅ |
| Переименовать проект, править короткое описание | — | — | ✅ | ✅ |
| Расшарить дальше, сменить роль, снять доступ | — | — | ✅ | ✅ |
| Отправить в архив и вернуть из архива | — | — | ✅ | ✅ |
| Удалить проект в корзину, восстановить, сменить раздел (`groupName`) | — | — | — | ✅ |

Почему удаление не входит в полный доступ: `full` — это право распоряжаться **работой**
в проекте (звать людей, убрать в архив), а не право убрать саму папку у того, кто её
завёл. Восстановить проект можно только из корзины владельца, поэтому и удалять — ему.

### 8.2б. Правила делегирования

Решения владельца продукта, по ним же стоят проверки `canGrantRole` и `canManageMember`:

1. **Выдать можно роль не выше своей.** `full` выдаёт в том числе `full` — цепочка
   делегирования не ограничена.
2. **Снять доступ или сменить роль можно только тому, кто ниже тебя.** Владелец —
   любому; `full` — читателям и редакторам, но не такому же `full`. Иначе двое
   приглашённых могут вычеркнуть друг друга из проекта, который завели не они;
   такие случаи разбирает владелец.
3. **Каскада нет.** Сняли доступ у участника — те, кого он позвал, остаются.
   Один клик не должен выключать группу людей: вернуть их можно только заново
   пригласив каждого, цена ошибки несоизмерима с задачей «убрать одного».
4. **`invited_by` — история, а не иерархия.** Роль меняется, приглашающий остаётся.
   В диалоге «Поделиться» рядом с участником показано «добавил N», если звал не тот,
   кто сейчас смотрит: при делегировании иначе не понять, откуда человек в проекте.
5. **Список плоский.** Владелец видит всех участников сразу, кем бы они ни были
   позваны, и там же снимает доступ или меняет роль.
6. **Приглашение уже существующего участника = смена его роли**, и правила п. 2
   действуют: иначе диалог «Поделиться» стал бы обходным путём для понижения.

### 8.2в. Подсказки: кого уже приглашали

Диалог показывает историю получателей — имя и адрес тех, кому этот человек уже
давал доступ. Из неё выбирают строкой, по ней же работает ввод **по имени**: поле
принимает и адрес, и имя из истории.

Решения:

1. **История принадлежит приглашающему, а не проекту.** Один и тот же диалог
   открывается из «Проектов» и из админских «Папок пользователей»
   ([components/admin/workspaces/workspaces-content.tsx](../components/admin/workspaces/workspaces-content.tsx)
   импортирует тот же `ShareDialog`), и подсказки в обоих местах обязаны быть
   одни и те же. Владелец записи — тот, кто нажал «Отправить»: админ, раздающий
   чужой проект, копит свою историю, а не историю владельца.
2. **Пишет сервер, а не браузер.** Запись идёт в `POST /api/projects/:id/members`
   после удавшегося приглашения. Была бы она клиентской — историю пополняли бы
   и опечатки, и вторая точка входа записывала бы по-своему.
3. **Ключ — почта.** Приглашение адресуется адресу: аккаунта под ним может ещё
   не быть (роут его и заводит). Имя лежит рядом снимком и обновляется при
   следующем приглашении — ради подписи в списке не нужен JOIN к `users`.
4. **Имя не адресует само по себе.** Набранное имя превращается в адрес только
   если в истории оно одно; тёзки и обрывки ничего не выбирают. Целиком набранный
   адрес всегда понимается буквально — иначе похожий знакомый адрес подменил бы
   новый.
5. **Строку можно забыть.** Крестик в выпадающем списке —
   `DELETE /api/account/share-contacts?email=`. Доступ это не трогает: подсказка
   и участие — разные вещи, снимают доступ в списке ниже.

### 8.3. Схема

```sql
CREATE TABLE project_members (
  project_id  TEXT NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
  user_id     TEXT NOT NULL REFERENCES users(id)    ON DELETE CASCADE,
  role        TEXT NOT NULL CHECK (role IN ('viewer','editor','full')),
  invited_by  TEXT REFERENCES users(id),
  created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  PRIMARY KEY (project_id, user_id)
);
CREATE INDEX project_members_user_idx ON project_members (user_id);

-- История получателей диалога (8.2в): у кого какие подсказки.
CREATE TABLE share_contacts (
  user_id      TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  email        TEXT NOT NULL,
  full_name    TEXT NOT NULL DEFAULT '',
  last_used_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  created_at   TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  PRIMARY KEY (user_id, email)
);
CREATE INDEX share_contacts_recent_idx ON share_contacts (user_id, last_used_at DESC);
```

### 8.4. Главная цена — не таблица, а авторизация

Модель «один проект — один владелец» вшита в каждый запрос: `findOwnedProject`,
`findProjectForUser`, `listProjectsByOwner` и все вызовы `WHERE user_id = $1`.

Сделано: [lib/project-access.ts](../lib/project-access.ts) —
`resolveProjectAccess(projectId, userId)` и `requireProjectAccess(projectId, userId,
minimum)`; роуты кабинета ходят через них, `findProjectForUser` из роутов проекта ушёл.
Машинный протокол проверяется через `requireProjectAccess` в
[lib/storage/auth.ts](../lib/storage/auth.ts) — та же лестница ролей.

Разница ответов намеренная: **нет доступа вовсе — 404** (чужой проект не подтверждает
сам факт своего существования), **доступ есть, но роль ниже нужной — 403** с внятным
текстом: человек проект видит и должен понять, почему действие не прошло, а не решить,
что проект исчез.

Отдельно стоит помнить про ловушку, из которой это выросло: до появления ролей роуты
кабинета (`drive`, `drive/options`, `drive/files/:fileId`, `chat`, `media`) проверяли
доступ через `findProjectForUser`, то есть **любой участник значил редактора** —
`viewer` мог удалить файл и написать в чат. Роль различалась только на `/api/storage/v1/*`.
Отсюда правило: новый роут проекта берёт `requireProjectAccess` с явным порогом,
а не «проект найден — значит можно».

Хвосты, оставленные владельцу намеренно (расшаривание их не касается):
`/api/projects/:id/files`, `/api/projects/:id/files/presign` и
`/api/projects/:id/messages` — старые эндпоинты без клиентов в интерфейсе.

**Десктоп-клиент не затрагивается:** машинный токен продолжает видеть проекты по владельцу,
расшаренности для него не существует — он всегда работает с оригиналом.
`GET /api/storage/v1/projects` для машинного токена не меняется.

### 8.5. Зависимость: почта (решено — добавляем)

Ни одной библиотеки отправки почты в `package.json` сейчас нет. Владелец подтвердил:
почту заводим.

Это отдельная задача **до** расшаривания, потому что сценарий приглашения без письма
не работает вовсе:

1. выбрать провайдера (Resend / SMTP / другой) и завести ключи в окружении;
2. слой отправки с шаблонами — минимум два письма: «вам открыли доступ к проекту»
   и «вас пригласили, вот временный пароль»;
3. поведение при недоставке: приглашение не должно теряться молча — логировать,
   показывать статус пригласившему, давать повторную отправку;
4. заранее пригодится и для другого: сброс пароля, уведомления о сообщениях в чате.

Временный пароль: генерировать криптостойко, хранить только хэш, помечать аккаунт флагом
«пароль временный» и требовать смены при первом входе — иначе пароль из письма живёт вечно.

Новых полей в базе не нужно. Достаточно обычного пути заливки: клиент кладёт пустой

Что решить на бэкенде:

- разрешённые расширения и `content_type` (`.txt`, `.md`, `.json` — остальное отклонять,
  чтобы через «текстовый файл» не заливали произвольное);
- имя по умолчанию и его уникализация тем же правилом `(2)` из 6.3;

### 8а.2. Загрузить папку

Новых полей в базе не нужно, но операция длинная и составная:

1. клиент обходит выбранную папку и присылает список относительных путей;
2. бэкенд создаёт недостающие папки — рекурсивный `mkdir` по цепочке `a/b/c`,
   сейчас `POST /mkdir` создаёт только один уровень;
3. дальше обычный `/presign` → PUT → `/notify` на каждый файл;
4. прогресс — через `storage_jobs` (6.4), потому что сотня файлов в один запрос не влезет.

Отдельно проверить фильтры: скрытые файлы (`.DS_Store`, `Thumbs.db`), пустые папки,
символические ссылки, и лимит на количество файлов в одной операции.

## 9. Отдельные хвосты

### 9.1. Лимиты загрузки и multipart

Задача обязательная, не «по возможности». Делится на две части — дешёвую и полноценную.

**Часть А: снять потолки (быстро, чинит ежедневную боль).**

| Путь | Кто ходит | Сейчас | Что делать |
|---|---|---|---|
| `/api/projects/:id/media` — байты через наш сервер | веб-интерфейс | **250 МБ** (`ADMIN_UPLOAD_MAX_BYTES`) | перевести на presigned PUT; гонять гигабайты через Next не нужно |
| `/api/projects/:id/files/presign` (легаси кабинета) | никто из живого кода | 500 МБ (`presignUploadSchema.sizeBytes`) | снять лимит или удалить роут |
| `/api/storage/v1/presign` | десктоп-клиент | **лимита нет** — схема размер не принимает | оставить; потолок задаёт S3 |
| Одиночный presigned PUT | оба | 5 ГиБ, без возобновления | часть Б |

Потолок в 250 МБ ощущается на сайте при каждой загрузке видео — самая заметная из всех
проблем списка для обычного пользователя. У десктоп-клиента ограничения нет: он упрётся
только в 5 ГиБ на объект.

**Часть Б: multipart.** Четыре ручки — `create` / `presign-part` / `complete` / `abort` —
плюс правило жизненного цикла на бакете «abort incomplete multipart uploads», иначе брошенные
части копятся и тарифицируются молча.

Даёт две вещи сразу: файлы больше 5 ГиБ и **возобновление** — обрыв на четвёртом гигабайте
перестаёт означать «начинай сначала».

Клиент готов и ждёт: стратегия по размеру выбирается автоматически, поля `upload_id` /
`parts_done` в очереди передач есть, и при `capabilities.multipart = false` он отказывает
**до** начала передачи. После включения не забыть выставить флаг в `/capabilities` —
клиент переключится сам.

### 9.2. Фильтрация архивных на сервере

`GET /api/projects` отдаёт архивные вместе с рабочими, фильтрует фронт. Решение владельца —
фильтровать на сервере: параметр `?archived=true|false|all`, по умолчанию `false`.
`GET /api/storage/v1/projects` продолжает отдавать все, но с полем `isArchived` — обработчик
сам решает; в контракте уже записано, что архивные он пропускает.

### 9.3. Два бага `/reindex`

Из [STORAGE_CLIENT_REQUESTS.md](./STORAGE_CLIENT_REQUESTS.md) §3 и §4, оба в
`reindexProject` (`lib/storage/write-path.ts:634`):

- **§3:** объекты под `options/` исключены из `remoteKeys` (`:660`), но финальный проход (`:741`)
  удаляет все строки, которых нет в `remoteKeys`. Любой файл под `options/` при первом
  же реиндексе объявляется удалённым. Там лежит статистика обработки — терять нельзя.
  Починка: пропускать в проходе удаления строки, чей `s3_key` подходит под `isOptionsKey`
  (`lib/storage/keys.ts:47`) — одно условие.
- **§4:** имя берётся как `key.slice(key.lastIndexOf("/") + 1)` (`:688`), то есть в `name`
  попадает физическое `{uuid}-clip.mov`. `/notify` при этом пишет логическое имя. Один и тот же
  файл называется по-разному в зависимости от пути попадания в каталог.
  Починка: срезать префикс `{uuid}-`, а для строк, которые уже есть в каталоге, не считать
  реиндекс источником имени.

Оба всплывают именно тогда, когда «что-то разошлось» и зовут реиндекс, — то есть в худший момент.

### 9.4. Отмена последнего действия

**Рамки заданы владельцем: отменяется только последнее действие.** Ни истории, ни стека,
ни отмены «того, что было полчаса назад». Это решение сильно удешевляет задачу —
новых таблиц не нужно вообще.

Каждая операция уже обратима существующими эндпоинтами:

| Действие | Обратное | Что для этого нужно от ответа сервера |
|---|---|---|
| Переименование, перемещение | `POST /rename` с прежними `name` / `folderPath` | обновлённая строка (уже возвращается) |
| Копирование | удаление созданных строк | список новых `fileId` (уже возвращается; для задачи — из `storage_jobs.payload`) |
| Удаление | `POST /restore` из корзины | список `fileId`, ушедших в корзину |
| Создание папки | удаление | `fileId` созданной строки |

**Отсюда решение: отмену держит клиент.** Он помнит последнюю операцию и данные для обратной
и вызывает существующий эндпоинт. Сервер ничего не хранит.

Что нужно доделать на бэкенде — только полнота ответов: каждая мутирующая ручка обязана
вернуть достаточно, чтобы построить обратную операцию (для пачек и задач — полный список
затронутых `fileId`, а не только счётчик).

Отмена не считается особой операцией: она журналится как обычное действие и уезжает клиентам
через `/delta`. Проверять «не изменилось ли с тех пор» не нужно — по решению 7 конфликты
разрешаются как «последний выиграл».

Не делаем: таблицу `storage_operations`, групповую отмену, отмену чужих действий,
отмену после перезапуска клиента.

### 9.5. CRUD проекта под machine token

Требование десктоп-клиента ([STORAGE_CLIENT_REQUESTS.md §5](./STORAGE_CLIENT_REQUESTS.md)),
в плане раньше отсутствовало.

**Проблема.** Файлы и папки внутри проекта программа менять умеет — `/storage/v1/rename`
принимает machine token. А сам проект нет: `POST /api/projects`,
`PATCH /api/projects/[id]` и `DELETE /api/projects/[id]` авторизуются через `requireUserApi`,
то есть только сессией. Под machine token эти пункты в программе серые.

Почему это заметно: в колонке проектов облачные папки выглядят как локальные, и «сходи на сайт,
чтобы создать проект» ломает работу. Хуже — локальное переименование папки проекта разрывает
связь с каталогом: путь перестаёт разбираться, значки синхронизации исчезают, а в облаке имя
остаётся прежним. Клиент это сейчас блокирует у себя.

**Что нужно** — три тонких роута по образцу `/rename`, все с `requireStorageApi`
и `requireOwnedProjectAccess` на изменяющих:

```http
POST   /api/storage/v1/projects        { "name": "Новый проект", "clientId": null }
                                       → { "project": { id, name, userId, … } }
POST   /api/storage/v1/project-rename  { "projectId": "…", "name": "Новое имя" }
                                       → { "project": { … } }
DELETE /api/storage/v1/projects        { "projectId": "…" }  → { "ok": true }
```

Внутри — уже написанная логика кабинета. Ключи в бакете от имени проекта не зависят,
поэтому переименование это один `UPDATE` и ноль операций в R2. В журнал имя не пишем:
в `storage_changes` оно не участвует, клиент перечитает его следующим `/projects`.
Не забыть обновить `project-meta.json` (2.2.3).

Пользователя программа не создаёт — это остаётся за сайтом.

Приоритет внутри пункта: **создание и переименование** — ежедневные действия, нужны первыми;
удаление — следом, и оно уходит в корзину (раздел 7), а не стирает данные.

### 9.6. Подтвердить клиенту

Вопросы из [STORAGE_CLIENT_REQUESTS.md §8](./STORAGE_CLIENT_REQUESTS.md) — кода не требуют,
но ответить надо, клиент на них закладывается: пустые логические папки в `/tree`,
Range-запросы по presigned GET, CORS на бакете, лимит в `/presign`, окно ретеншена
`storage_changes`, разрешена ли запись под `options/` через presign+notify.

## 10. Порядок работ

Слои снизу вверх: без первого не проверяется второе.

| Этап | Что | Почему в этом порядке |
|---|---|---|
| **0** | **Развернуть бэкенд и отдать URL десктоп-клиенту** | Клиент реализован и упирается только в это: его пункт 0′ «round-trip против живого бэкенда» ждёт адрес. Токен они заведут сами. Первый прогон делать сразу с заливкой — иначе пустой `/tree` не отличить от неработающего |
| **1** | `userId` + `ownerEmail` в `/projects` (2.2.1); два бага `/reindex` (9.3); фильтр архивных (9.2) | Одна-две строки каждый, разблокируют клиента и убирают тихую потерю данных |
| **2** | Снять потолки загрузки, веб на presigned PUT (9.1, часть А) | Самая заметная пользователю проблема, чинится настройкой и одним переключением пути |
| **3** | Журнал `op: "move"` (4.2), `capabilities.protocol = 2`, сообщить клиенту | Снимает блокер второй машины. Без него всё дальнейшее не наблюдаемо извне |
| **4** | Уникальность имён (5.2), валидатор имён (5.3), `409` вместо нарушения индекса | Дальше идут операции, создающие имена; правила должны существовать раньше |
| **5** | `project-meta.json` на любое изменение (2.2.3), `user-meta.json` (3.5), `displayPath` (2.2.2) | Дешёвые, закрывают требование «папка — источник истины» на уровне идентичности |
| **5а** | CRUD проекта под machine token (9.5) — создание и переименование вперёд, удаление после корзины | Логика уже написана, отличается только авторизация. Снимает серые пункты в программе и запрет на локальное переименование |
| **6** | `storage_jobs` (6.4) | Инфраструктура для всего длинного, что идёт дальше |
| **7** | Корзина (7) | Переводит удаление в обратимое **до** того, как появятся массовые операции |
| **8** | `POST /copy` (6) — сперва файл, затем папка задачей | Клиент уже читает `capabilities.copy` и переключится сам |
| **9** | Multipart (9.1, часть Б) | Возобновление и файлы больше 5 ГиБ; клиент готов, ждёт флага |
| **10** | Полнота ответов мутирующих ручек (9.4) | Даёт клиенту отмену последнего действия почти бесплатно |
| **11** | `catalog.json` + `catalog.jsonl` (3.1–3.4) | Полное восстановление из папки; опирается на `storage_jobs` |
| **12** | Почта → `project_members` → ревизия авторизации → расшаривание (8) | Самый дорогой и рискованный блок, делать последним и целиком |

Пункты меню «Создать текстовый файл» и «Загрузить папку» (8а.1, 8а.2) не имеют жёсткой
привязки к очереди: первый ни от чего не зависит, второй — только от `storage_jobs` (этап 6).

## 11. Чего делать не нужно

Из [STORAGE_CLIENT_REQUESTS.md §9](./STORAGE_CLIENT_REQUESTS.md) — чтобы не потратить время зря:

| | Почему |
|---|---|
| Прокачивать байты через API | удвоит трафик и упрётся в лимиты сервера; presigned уже решает |
| Создавать объекты-маркеры папок в R2 | папки логические, в Postgres — это правильнее |
| Отдавать клиентам ключи R2 | файлы попадут в бакет мимо каталога, и сайт не увидит их до реиндекса |
| Хранить состояние локальных копий клиента | что скачано на конкретной машине — дело этой машины |
| Генерировать превью и прокси-файлы | клиент достаёт метаданные `ffprobe` по Range |
| Трогать баланс и биллинг | вне рамок по решению владельца |

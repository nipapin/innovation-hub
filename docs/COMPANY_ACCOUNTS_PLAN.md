# Компании внутри сайта

**Для кого.** Для того, кто заводит компанию, разбирается, почему у сотрудника
нет кошелька, или собирается трогать админский раздел и деньги в конвейере.

Дата сверки с кодом: **2026-09-09**.

Смежные документы: [FEATURE_FLAGS.md](./FEATURE_FLAGS.md) — выключатели разделов,
[BILLING_AND_TRIAL_PLAN.md](./BILLING_AND_TRIAL_PLAN.md) — устройство денег,
[ADMIN_ROLES_PLAN.md](./ADMIN_ROLES_PLAN.md) — роли и теги прав.

---

## 0. Решение

**Компания — это слой внутри сайта, а не отдельная его копия.**

Одна база, один процесс, один бакет, один деплой. Компания — сущность в базе:
у неё свои сотрудники, общий кошелёк, свой набор разделов, своё оформление и
свой главный. Заводит компанию суперадмин кнопкой, а не развёртыванием.

Зафиксировано 2026-09-09. Разбор отвергнутых путей — §1, путь отхода — §11.

## 1. Что было отвергнуто и почему

### 1.1. Копия репозитория

Общие файлы разошлись бы навсегда, каждый перенос правки стал бы разбором
конфликтов в самых часто правимых файлах. Механизм, который делает копию
ненужной, уже влит — выключатели разделов, [FEATURE_FLAGS.md](./FEATURE_FLAGS.md).

### 1.2. Площадка на компанию: своя база, свой бакет, свой процесс

Путь рабочий и дешёвый в коде: различались бы только `.env`, база и бакет, а
репозиторий остался бы один. Отвергнут не из-за цены, а потому что закрывает
ровно то, ради чего затевалось:

| требование | при отдельной площадке |
| --- | --- |
| Суперадмин видит все компании и переключается | нужно подключаться к N базам сразу |
| Перенести человека из общего раздела в компанию | перенос строк между базами, а не кнопка |
| Суперадмин заводит компанию | это база, бакет, `.env`, nginx, процесс — деплой, а не кнопка |
| Общий раздел рядом с компаниями | его нет: каждая площадка сама себе всё |

### 1.3. Своя база на компанию внутри одного приложения

Худший из всех: складывает эксплуатационную цену N баз с переписыванием слоя
данных.

| что мешает | факт в коде |
| --- | --- |
| Пул один и создаётся при импорте модуля | [lib/db.ts](../lib/db.ts) — `readEnvConnectionConfig()` и `new Pool(...)` на уровне модуля |
| `query()` не принимает «чья база» | 526 операторов зовут её без контекста |
| Фоновые циклы стартуют раз на процесс | [instrumentation.ts](../instrumentation.ts) — runner, stats-loop, chat-poller; состояние каждого лежит в своей базе, значит каждый становится N циклами |
| Связность | `PG_POOL_MAX` = 3 → 3 соединения × число компаний × число процессов |

И отдельная база не даёт того, ради чего её обычно хотят. Падает не база —
падает процесс: плохой релиз, утечка памяти, `pm2 reload` с ошибкой сборки. Один
процесс на N баз ляжет для всех одинаково. **От отказа спасает отдельный
процесс, а не отдельная база**, а отдельный процесс — это уже §1.2.

## 2. Что такое компания в этой модели

Не раздел базы, а **слой видимости вверх**.

Ключевой факт, на котором держится вся конструкция: **сайт уже изолирован по
пользователю.** Выборка всех людей — `listUsers()` — вызывается ровно из одного
места, [app/api/admin/users/route.ts:20](../app/api/admin/users/route.ts#L20).
Проекты скоупятся по `projects.user_id` и `project_members`, ключи вендоров — по
`owner_user_id`, деньги — по `user_id`. В пользовательской половине кода нет
выборок «покажи других людей».

Значит «сотрудники компании А не видят компанию Б» — правда уже сегодня, до
всяких компаний, потому что сотрудники не видят друг друга вовсе.

Компания добавляет ровно две вещи:

1. **кто-то смотрит поперёк нескольких пользователей** — главный видит своих;
2. **кто-то платит за нескольких пользователей** — общий кошелёк.

Отсюда профиль риска. При разрезе базы по `company_id` забытый фильтр означал бы,
что чужой пользователь видит чужие данные. Здесь забытый scope означает, что
**главный видит лишнее** — дефект в одном ограниченном разделе, а не дыра в
фундаменте.

## 3. Модель данных

```sql
CREATE TABLE IF NOT EXISTS companies (
  id          TEXT PRIMARY KEY,
  -- Латинский идентификатор: уходит в префикс хранилища и в адреса.
  slug        TEXT NOT NULL UNIQUE,
  title       TEXT NOT NULL,
  -- Домен, по которому резолвится оформление страницы входа. NULL — общий адрес.
  domain      TEXT UNIQUE,
  -- Оформление и набор разделов: форма меняется вместе с интерфейсом, поэтому
  -- JSONB, а не колонки. Тот же приём, что у billing_settings.
  branding    JSONB NOT NULL DEFAULT '{}'::jsonb,
  features    JSONB NOT NULL DEFAULT '{}'::jsonb,
  is_active   BOOLEAN NOT NULL DEFAULT TRUE,
  created_by  TEXT REFERENCES users(id) ON DELETE SET NULL,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- NULL = общий раздел, то есть сайт ровно такой, каким работает сейчас.
ALTER TABLE users
  ADD COLUMN IF NOT EXISTS company_id TEXT REFERENCES companies(id) ON DELETE RESTRICT;

CREATE INDEX IF NOT EXISTS users_company_idx ON users (company_id)
  WHERE company_id IS NOT NULL;
```

**Больше никаких колонок ни в одной таблице.** Проекты, файлы, задачи, деньги,
инструменты, статистика — компания у них выводится через владельца. Это то, что
делает затею дешёвой: модель данных уже устроена как надо, пользователь в ней
корень.

`ON DELETE RESTRICT`: удалить компанию, в которой есть люди, нельзя — сначала
перевести их в общий раздел или в другую компанию.

Регистрация самообслуживанием даёт `company_id = NULL`. Иначе человек с улицы
попадал бы в чью-то компанию, а компания узнавала бы об этом по счёту.

| Статистика | только в админке | scope, §5 |

Вся работа по изоляции — в одной колонке таблицы и в админской поверхности.

## 5. Админская поверхность — основная работа

**56 роутов** в `app/api/admin` и **23 страницы** в `app/admin`. Это
единственное место, где по замыслу видно поперёк пользователей, и потому
единственное, где компания должна ограничивать.

### 5.1. Точка входа уже одна

[`requireAdminApi`](../lib/admin-auth.ts#L103) для роутов и
[`requireCapabilityPage`](../lib/admin-page-guard.ts) для страниц. Первая **уже
грузит пользователя целиком** через `findUserById`, поэтому `companyId` в её
ответе достаётся без лишнего запроса.

Правило: гейт возвращает `companyId`, и раздел обязан его применить.

```
companyId === null  →  суперадмин или админ общего раздела: видит свою область
companyId === "..." →  главный компании: видит только своих
```

### 5.2. Почему нужен `company:check`

56 мест, где можно забыть, — это вопрос не дисциплины, а времени. В проекте уже
шесть механических проверок ровно этого класса: `i18n:check`, `md:check`,
`dialog:check`, `admin:check`, `help:check`, `features:check`
([package.json](../package.json)).

`company:check` встаёт в тот же ряд: роут, который забрал `companyId` из гейта и
не передал его в выборку, обязан валить проверку. Это то, что превращает риск из
«кто-то однажды забудет» в «CI не пропустит».

### 5.3. Права главного компании

Пресет поверх готового `CAPABILITY_PRESETS`
([admin-capabilities.ts:97](../lib/admin-capabilities.ts#L97)): кошелёк,
статистика, пользователи и права, внешние сервисы. Без настроек конвейера, без
общих словарей, без выключателей разделов — это наше, не его.

## 6. Общий кошелёк: главный и подчинённые

Проекты остаются у людей, заводить их люди могут сами, расход ложится на
компанию. Один человек — главный: он пополняет и видит ленту. Остальные о деньгах
не думают вовсе.

### 6.1. Где сходятся деньги

| точка | файл | что делает |
| --- | --- | --- |
| чтение | `getFunds(userId)` — [funds.ts:174](../lib/billing/funds.ts#L174), 7 вызовов | остатки, резервы, гранты, лимит овердрафта |
| гейт | `admitItem({ ownerId })` — [admission.ts:61](../lib/billing/admission.ts#L61), вызов из [scan.ts:875](../lib/pipeline/scan.ts#L875) | пускать ли задачу в работу |
| запись | единственный `INSERT INTO billing_transactions` — [ledger.ts:109](../lib/billing/ledger.ts#L109) | движение денег |

Один читатель, один гейт, один писатель.

### 6.2. Почему нельзя просто подставить плательщика

Соблазнительно решить одной строкой: везде вместо владельца передавать аккаунт
компании. **Так нельзя, и ломается молча.**

| величина | откуда | при подстановке плательщика |
| --- | --- | --- |
| остаток | кэш `users.balance_*_cents` | компании — верно |
| гранты | `billing_grants.user_id` | компании — верно |
| овердрафт | `users.overdraft_limit_cents` | компании — верно |
| **резерв** | **`JOIN projects p ON p.user_id = $1`** | **проекты компании, а их нет → ноль** |

Резерв — это оценки живых задач ([funds.ts:63](../lib/billing/funds.ts#L63)), и
считается он по проектам того, чей идентификатор передали. У аккаунта-кошелька
своих проектов нет. Значит `availableOwnCents = остаток − 0 + овердрафт`, то есть
«доступно всё» при любой загрузке конвейера.

Последствие: гейт пускает работ на сумму, которую баланс не покрывает, и компания
уходит в минус тем глубже, чем больше сотрудников работают одновременно. Ошибки
при этом нет — задачи просто проходят.

**Отсюда требование: резерв обязан считаться по проектам всех, за кого платит
этот кошелёк, одним запросом.**

### 6.3. Связь: колонка на подчинённом

```sql
ALTER TABLE users
  ADD COLUMN IF NOT EXISTS payer_user_id TEXT REFERENCES users(id) ON DELETE RESTRICT;

-- Плательщик платит за себя сам: цепочки запрещены. Иначе COALESCE ниже даёт
-- только один уровень, и рекурсию пришлось бы городить в каждом запросе о деньгах.
ALTER TABLE users
  ADD CONSTRAINT users_payer_not_self CHECK (payer_user_id IS DISTINCT FROM id);

CREATE INDEX IF NOT EXISTS users_payer_idx ON users (payer_user_id)
  WHERE payer_user_id IS NOT NULL;
```

`NULL` — платит сам, как сейчас. Плательщик = `COALESCE(payer_user_id, id)`.

Почему отдельная колонка, а не «платит главный моей компании»: платит **не
всегда** компания. Компанию можно настроить так, что сотрудники платят сами
(§3, `features`), и человек в общем разделе тоже может платить за коллегу без
всякой компании. Связь «кто за кого платит» и связь «кто с кем в компании» —
разные вопросы, и одно поле на оба ответило бы неверно на один из них.

Резерв после правки:

```sql
JOIN users u ON u.id = p.user_id
WHERE COALESCE(u.payer_user_id, u.id) = $1
```

Список подчинённых при этом не нужен ни в коде, ни отдельным запросом.

### 6.4. Что меняется в коде

| место | сейчас | становится |
| --- | --- | --- |
| `readBalances` [ledger.ts:180](../lib/billing/ledger.ts#L180) | кэш владельца | кэш плательщика |
| `listGrants` [funds.ts:110](../lib/billing/funds.ts#L110) | гранты владельца | гранты плательщика |
| `overdraftLimitFor` [funds.ts:160](../lib/billing/funds.ts#L160) | лимит владельца | лимит плательщика |
| `liveReserves` [funds.ts:63](../lib/billing/funds.ts#L63) | `WHERE p.user_id = $1` | JOIN по `COALESCE(u.payer_user_id, u.id)` |
| `INSERT` в ленту [ledger.ts:109](../lib/billing/ledger.ts#L109) | `user_id` = владелец | `user_id` = плательщик |

### 6.5. Освобождение от оплаты НЕ наследуется

`users.billing_exempt` читается у владельца проекта
([admission.ts:157](../lib/billing/admission.ts#L157),
[repository.ts:180](../lib/pipeline/repository.ts#L180)) и так и остаётся.

Соблазн прочитать его ещё и у плательщика («компания-партнёр не платит») ведёт к
тихой катастрофе: миграция биллинга проставила `billing_exempt = TRUE` всем
администраторам
([2026-08-27-billing.sql:169](../db/migrations/2026-08-27-billing.sql#L169)).
Сделай главного компании администратором — и вся компания перестанет платить, не
показав ни одной ошибки.

Компания целиком освобождается флагом в `companies.features`, а не этим полем.

### 6.6. Кто главный

**Главный компании — не администратор площадки.** Он её клиент. Признак —
`payer_user_id IS NULL` при наличии подчинённых; по нему в кабинете показывается
раздел «Кошелёк компании»: остаток, лента, пополнение.

Подчинённый не видит денег вовсе: ни остатка, ни ленты, ни кнопок. Проект
останавливается по той же причине `no-funds`, но текст ему адресуется другой —
«обратитесь к ответственному за оплату», а не «пополните баланс».

### 6.7. Углы, которые надо закрыть сразу

| угол | решение |
| --- | --- |
| **Пробный период.** `activateTrial(auth.userId)` [trial.ts](../lib/billing/trial.ts) выдаёт грант нажавшему; у подчинённого он ляжет на него, а читается у плательщика — деньги повиснут невидимыми | В режиме подчинённого `readTrialState` возвращает `unavailable`. Пробный период — механизм для одиночки; компания заходит с деньгами |
| **Личный баланс при переводе в подчинённые** | Остаётся на человеке и перестаёт использоваться. Не сгорает и не переносится: перекладывать чужие деньги молча нельзя. Вернули `payer_user_id = NULL` — баланс снова в деле |
| **Личный лимит овердрафта** перестаёт действовать: читается лимит плательщика | Поведение верное, но неочевидное. Показывать на странице человека, чей лимит применяется |
| **Один сотрудник выедает весь кошелёк** | На первом шаге лимит на человека НЕ делаем: он потребовал бы счётчика потраченного, а счётчик пришлось бы сводить с лентой и он бы с ней разошёлся — ровно та причина, по которой резерв не пишется лентой ([billing.sql:66](../db/migrations/2026-08-27-billing.sql#L66)) |
| **Удаление плательщика** | `ON DELETE RESTRICT`: сначала перевести подчинённых |

### 6.8. Кто сколько потратил

Отдельная колонка не нужна: расход по людям строится через
`billing_transactions.task_id` → `processing_stats`, эта связь уже используется в
[statistics.ts:340](../lib/repositories/statistics.ts#L340).

Колонку `spender_user_id` заводим только если понадобится разрез по сотрудникам
прямо в ленте. Переиспользовать `actor_user_id` нельзя: он означает «кто
распорядился деньгами», а списание никто не заказывал — работа просто
завершилась.

## 7. Хранилище

**Для изоляции не нужно ничего.** Доступ к файлу идёт через `/api/media/` с
проверкой прав на проект, а не по знанию ключа. Ключи остаются
`projects/{storageOwnerId}/{projectId}/`.

Отдельный бакет на компанию отвергнут: `getS3Bucket()` вызывается **38 раз в 26
файлах**, и «чей бакет» пришлось бы протащить в каждый, включая фоновые задачи.
Изоляции это не добавляет.

Если понадобится операционное разделение — своя квота, свои lifecycle-правила,
отдельный счёт от R2 — это префикс `companies/{slug}/projects/…`, то есть одна
функция `projectObjectPrefix` в [s3-config.ts](../lib/s3-config.ts). Префикс
здесь для эксплуатации, а не для безопасности: границу держат права в базе.

## 8. Дизайн и брендинг

### 8.1. Что переделывается

`SITE_NAME` и `SITE_MONOGRAM` ([site.ts](../lib/site.ts)) — константы сборки,
используются в восьми местах, и [header.tsx](../components/header.tsx) с
[admin-sidebar.tsx](../components/admin/shell/admin-sidebar.tsx) — клиентские
компоненты. Значение должно приходить сверху контекстом, а не импортом.

[app/icon.svg](../app/icon.svg) и `apple-icon.svg` содержат зашитый градиент и
`aria-label="FF Works"` — заменяются на генерируемые (`icon.tsx`) из монограммы и
акцентного цвета, иначе у каждой компании во вкладке чужие буквы.

### 8.2. Домен решается без `proxy.ts`

[proxy.ts](../proxy.ts) работает в edge-рантайме, где базы нет, и знать о
компаниях ему не нужно: он занимается сессией и маршрутом. Оформление резолвится
в [app/layout.tsx](../app/layout.tsx) — это серверный компонент, база ему
доступна: `headers()` → домен → компания → палитра и логотип.

После входа компания определяется пользователем, а не адресом. Домен влияет
только на то, как выглядит страница входа.

### 8.3. Правило: переопределять мало токенов

Палитра — CSS-переменные в `:root` ([app/globals.css](../app/globals.css)), тема
одна, тёмная ([UI_TOKENS.md](./UI_TOKENS.md)). Компания переопределяет **только
акцент**: `--primary`, `--primary-foreground`, `--accent`, `--accent-foreground`,
`--ring`. Остальные сорок с лишним токенов наследуются.

Полная тема на компанию — это та же копия, только в CSS: новый токен, заведённый
на сайте, в чужую тему не приедет, и разойдутся они молча. Наследование означает,
что новое работает сразу. Тот же принцип, что `FEATURE_DEFAULT` в
[FEATURE_FLAGS.md §5](./FEATURE_FLAGS.md).

## 9. Внешние сервисы компании

`vendor_accounts.owner_user_id` уже различает «наша платформенная учётка» (NULL)
и «клиент принёс свой ключ»
([2026-09-02-vendor-accounts.sql](../db/migrations/2026-09-02-vendor-accounts.sql)).

Ключи компании — это учётки, принадлежащие аккаунту главного. На «Моих ключах» у
сотрудника показываются его собственные плюс ключи его компании, помеченные как
компанийские. Это правило видимости, а не новая колонка.

## 10. Что остаётся ценой

| цена | почему |
| --- | --- |
| Один бэкап на всех | восстановить компанию на вчера = откатить всех. Это единственное, что отдельные площадки дают, а эта модель — нет |
| Общий радиус отказа | плохой релиз гасит все компании сразу |
| Риск в админской поверхности | 56 роутов, где можно забыть scope; лечится `company:check`, но не исчезает |

## 11. Путь наружу

Модель выбрана в том числе потому, что **из неё можно выйти, а в неё — почти
нет.**

**Выделить компанию в отдельную площадку** — выгрузка: обход графа владения от
`users` вниз (проекты, файлы, задачи, деньги, инструменты, ключи, статистика)
плюс объекты R2 по префиксам этих пользователей, заливка в свежую базу, отдельный
процесс со своим `.env`. Код при этом не меняется вовсе: это тот же репозиторий,
развёрнутый второй раз, а `company_id` в новой базе просто везде пустой. Скрипт
пишется тогда, когда понадобится.

**Обратно — слияние**, и оно тяжелее: `users.email` уникален глобально
([schema.sql:5](../db/schema.sql#L5)), и один человек, заведённый на двух
площадках, становится конфликтом, который разбирают руками.

## 13. Что здесь НЕ делаем

**`company_id` в остальных таблицах.** Компания выводится через владельца.
Колонка в проектах и задачах создала бы второй источник правды, который однажды
разойдётся с первым.

**RLS и переделку [lib/db.ts](../lib/db.ts).** Row Level Security защищает от
забытого фильтра в пользовательских выборках. У нас риск не там: пользовательские
выборки уже скоупятся по владельцу, а админские RLS не закрыла бы — админ по
определению смотрит за пределы своей строки.

**Отдельный бакет и отдельную базу на компанию.** §1.3 и §7.

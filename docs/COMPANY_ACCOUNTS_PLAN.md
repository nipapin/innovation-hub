почему у сотрудника нет кошелька, или собирается трогать деньги в конвейере.

## 0. Решение

**Компания — это слой внутри сайта, а не отдельная его копия.**

Одна база, один процесс, один бакет, один деплой. Компания — сущность в базе: у
неё свои сотрудники, свои админы с разными правами, общий кошелёк, свой набор
разделов и своё оформление. Заводит компанию суперадмин кнопкой, а не
развёртыванием.

Зафиксировано 2026-09-09. Уточнено 2026-09-11: роли в компании (§4), отдельная
консоль вместо ограничений в нашей админке (§6), служебный аккаунт кошелька
(§7.3), доступ к работе через участие в проекте (§8), задел под пайплайны и чаты
(§12).

Сделано: этапы 1–6 (§15). План выполнен; дальше — пайплайны и чаты (§12), отдельными планами.

## 1. Что было отвергнуто и почему

### 1.1. Копия репозитория

Общие файлы разошлись бы навсегда, каждый перенос правки стал бы разбором
конфликтов в самых часто правимых файлах. Механизм, который делает копию
ненужной, уже влит — выключатели разделов, [FEATURE_FLAGS.md](./FEATURE_FLAGS.md).

### 1.2. Площадка на компанию: своя база, свой бакет, свой процесс

Путь рабочий и дешёвый в коде: различались бы только `.env`, база и бакет, а
репозиторий остался бы один. Отвергнут не из-за цены, а потому что не даёт ровно
того, ради чего всё затевалось:

| требование | при отдельной площадке |
| --- | --- |
| Суперадмин видит все компании и переключается | нужно подключаться к N базам сразу |
| Перенести человека из общего раздела в компанию | перенос строк между базами, а не кнопка |
| Суперадмин заводит компанию | это база, бакет, `.env`, nginx, процесс — деплой, а не кнопка |
| Общий раздел рядом с компаниями | его нет: каждая площадка сама себе всё |

### 1.3. Своя база на компанию внутри одного приложения

Худший из всех: складывает эксплуатационную цену N баз с переписыванием слоя
данных.

| что мешает | факт в коде |
| --- | --- |
| Пул один и создаётся при импорте модуля | [lib/db.ts](../lib/db.ts) — `readEnvConnectionConfig()` и `new Pool(...)` на уровне модуля |
| `query()` не принимает «чья база» | 526 операторов зовут её без контекста |
| Фоновые циклы стартуют раз на процесс | [instrumentation.ts](../instrumentation.ts) — runner, stats-loop, chat-poller; состояние каждого лежит в своей базе, значит каждый становится N циклами |
| Связность | `PG_POOL_MAX` = 3 → 3 соединения × число компаний × число процессов |

И отдельная база не даёт того, ради чего её обычно хотят. Падает не база —
падает процесс: плохой релиз, утечка памяти, `pm2 reload` с ошибкой сборки. Один
процесс на N баз ляжет для всех одинаково. **От отказа спасает отдельный
процесс, а не отдельная база**, а отдельный процесс — это уже §1.2.

## 2. Что такое компания в этой модели

Не раздел базы, а **слой поверх пользователей**.

Ключевой факт, на котором держится вся конструкция: **сайт уже изолирован по
пользователю.** Выборка всех людей — `listUsers()` — вызывается ровно из одного
места, [app/api/admin/users/route.ts:20](../app/api/admin/users/route.ts#L20).
Проекты скоупятся по `projects.user_id` и `project_members`, ключи вендоров — по
`owner_user_id`, деньги — по `user_id`. В пользовательской половине кода нет
выборок «покажи других людей».

Значит «сотрудники компании А не видят компанию Б» — правда уже сегодня, до
всяких компаний, потому что сотрудники не видят друг друга вовсе.

Компания добавляет три вещи:

1. **кто-то смотрит поперёк нескольких пользователей** — админы компании видят
   своих;
2. **кто-то платит за нескольких пользователей** — общий кошелёк;
3. **кто-то распоряжается людьми и правами** — внутри своей компании.

И ничего сверх этого. В частности, **компания не даёт доступа к работе**: кто
видит проект, решает участие в проекте, как и сейчас (§8).

Отсюда профиль риска. При разрезе базы по `company_id` забытый фильтр означал бы,
что чужой пользователь видит чужие данные. Здесь всё, что смотрит поперёк людей,
живёт в одной новой поверхности — консоли компании (§6), и ограничено там по
построению.

## 3. Модель данных

```sql
CREATE TABLE IF NOT EXISTS companies (
  id             TEXT PRIMARY KEY,
  -- Латинский идентификатор: уходит в префикс хранилища и в адреса.
  slug           TEXT NOT NULL UNIQUE,
  title          TEXT NOT NULL,
  -- Служебный аккаунт, на котором лежат деньги компании (§7.3).
  wallet_user_id TEXT NOT NULL UNIQUE REFERENCES users(id) ON DELETE RESTRICT,
  -- Домен, по которому резолвится оформление страницы входа. NULL — общий адрес.
  domain         TEXT UNIQUE,
  -- Оформление и набор разделов: форма меняется вместе с интерфейсом, поэтому
  -- JSONB, а не колонки. Тот же приём, что у billing_settings.
  branding       JSONB NOT NULL DEFAULT '{}'::jsonb,
  features       JSONB NOT NULL DEFAULT '{}'::jsonb,
  is_active      BOOLEAN NOT NULL DEFAULT TRUE,
  created_by     TEXT REFERENCES users(id) ON DELETE SET NULL,
  created_at     TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at     TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- person — человек; company_wallet — служебный аккаунт кошелька компании:
-- без пароля, без входа, не показывается ни в одном списке людей.
ALTER TABLE users
  ADD COLUMN IF NOT EXISTS kind TEXT NOT NULL DEFAULT 'person'
    CHECK (kind IN ('person', 'company_wallet'));

-- NULL = общий раздел, то есть сайт ровно такой, каким работает сейчас.
ALTER TABLE users
  ADD COLUMN IF NOT EXISTS company_id TEXT REFERENCES companies(id) ON DELETE RESTRICT;

-- Роль внутри компании — вторая ось, независимая от users.role (§4).
ALTER TABLE users
  ADD COLUMN IF NOT EXISTS company_role TEXT
    CHECK (company_role IN ('member', 'admin', 'owner'));

-- Роль в компании есть ровно у тех, кто в компании.
ALTER TABLE users
  ADD CONSTRAINT users_company_role_pair
    CHECK ((company_id IS NULL) = (company_role IS NULL));

CREATE INDEX IF NOT EXISTS users_company_idx ON users (company_id)
  WHERE company_id IS NOT NULL;

-- Теги прав внутри компании. Компания выводится через человека: отдельная
-- колонка была бы вторым ответом на вопрос «в какой он компании».
CREATE TABLE IF NOT EXISTS company_capabilities (
  user_id     TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  capability  TEXT NOT NULL,
  granted_by  TEXT REFERENCES users(id) ON DELETE SET NULL,
  granted_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  PRIMARY KEY (user_id, capability)
);

-- Журнал компании читается из её консоли; компанию пишем с первого дня,
-- потому что историю задним числом не восстановить.
ALTER TABLE admin_audit_log ADD COLUMN IF NOT EXISTS company_id TEXT;
CREATE INDEX IF NOT EXISTS admin_audit_log_company_idx
  ON admin_audit_log (company_id, created_at DESC) WHERE company_id IS NOT NULL;
```

Плюс `users.payer_user_id` — §7.4.

**В таблицах работы — проектах, файлах, задачах, деньгах, инструментах,
статистике — никаких новых колонок.** Компания у них выводится через владельца.
Это то, что делает затею дешёвой: модель данных уже устроена как надо,
пользователь в ней корень.

Служебный аккаунт кошелька живёт с `company_id = NULL` и связан с компанией только
через `companies.wallet_user_id`: он не человек компании, у него нет роли в ней, и
в её списке людей он появиться не должен.

`ON DELETE RESTRICT`: удалить компанию, в которой есть люди, нельзя — сначала
перевести их в общий раздел или в другую компанию.

Регистрация самообслуживанием даёт `company_id = NULL`. Иначе человек с улицы
попадал бы в чью-то компанию, а компания узнавала бы об этом по счёту.

**Перевод человека между компаниями или в общий раздел — одна транзакция:**
сменить `company_id`, выставить или снять `company_role`, **удалить все его
`company_capabilities`** и решить `payer_user_id`. Иначе человек унесёт права
админа старой компании в новую, а его задачи продолжат списываться с чужого
кошелька.

## 4. Роли: сайт и компания — две оси

У человека две независимые роли:

| ось | где хранится | что открывает |
| --- | --- | --- |
| **Роль на сайте** | `users.role` + `admin_capabilities` | нашу админку `/admin` |
| **Роль в компании** | `users.company_role` + `company_capabilities` | консоль компании `/company` |

Сотрудник обычно `USER` на сайте и `admin` в своей компании. Одно на другое не
влияет.

**Устройство второй оси повторяет первую, этажом ниже:**

| сайт | компания | кто это |
| --- | --- | --- |
| `USER` | `member` | работает в своих проектах, консоли не видит |
| `ADMIN` + теги | `admin` + теги компании | видит в консоли только выданные разделы |
| `SUPERADMIN` | `owner` | все теги компании неявно, выдаёт права |

Зачем `owner`, если есть `admin` с полным набором тегов:

- **Правилу «выдать можно только то, что есть у тебя» нужен корень.** Кто-то
  должен иметь всё, чтобы было из чего раздавать. Владельца назначает суперадмин
  при заведении компании.
- **Два админа с правом на людей могли бы снять друг друга.** Последнего
  владельца снять нельзя — та же защита, что у последнего суперадмина
  (`countActiveSuperAdmins`, [users.ts:147](../lib/repositories/users.ts#L147)).
  Владельцев может быть несколько.

**Админам компании роль `ADMIN` на сайте не выдаётся никогда.** Она открывает
`/admin` ([proxy.ts](../proxy.ts), `isElevated`) — нашу админку со всеми людьми,
конвейером и чужими папками.

**Правило выдачи.** Сейчас права выдаёт только суперадмин
([capabilities/route.ts](../app/api/admin/users/[id]/capabilities/route.ts)). В
компании их раздают сами админы, поэтому правило другое: **выдать можно только
тег, который есть у тебя самого, и только человеку своей компании.** Владелец
выдаёт любые. Без этого правила админ с правом на людей выписал бы себе всё
остальное.

**Реестр тегов — в коде**, `COMPANY_CAPABILITIES`, по образцу
[admin-capabilities.ts](../lib/admin-capabilities.ts): новый инструмент компании
приносит свой тег без миграции. Состав тегов определяется позже; для ориентира —
кошелёк, статистика компании (просмотр отдельно от настройки), люди, права,
ключи компании. «Типы админов» — это наборы тегов поверх реестра, и они тоже
добавляются позже, не меняя схему.

**Наша сторона.** Суперадмин в консоли любой компании действует как её владелец,
с переключателем компаний. Админ сайта заводит компании и назначает владельцев
по отдельному тегу сайта `companies.manage`.

## 6. Консоль компании — основная работа

### 6.1. Отдельная поверхность, а не ограничения в нашей админке

Раз у админов компании своя ось прав, а в `/admin` их не пускает `proxy.ts`,
консоль компании — это **отдельный раздел `/company`** со своим гейтом.

| | ограничения в `/admin` | консоль `/company` |
| --- | --- | --- |
| Работа | дописать scope в 56 существующих роутов и 23 страницы | новая небольшая поверхность |
| Если забыли | админ компании видит всех людей сайта | роут не проходит `company:check` |
| Наша админка | переделывается | не трогается |

Где инструменты пересекаются с нашими — статистика, люди, ключи, — переиспользуем
компоненты и функции с обязательным параметром `companyId`, а не роуты.

### 6.2. Гейт

`requireCompanyApi(request, capability)` и `requireCompanyPage(capability)` —
по образцу [`requireAdminApi`](../lib/admin-auth.ts#L103), который уже грузит
пользователя целиком через `findUserById`. Гейт **всегда** возвращает `companyId`:
для админа компании — его компанию, для суперадмина — выбранную в переключателе.
Вызвать функцию консоли без `companyId` нельзя по типу.

### 6.3. `company:check`

В проекте шесть механических проверок ровно этого класса: `i18n:check`,
`md:check`, `dialog:check`, `admin:check`, `help:check`, `features:check`
([package.json](../package.json)). `company:check` встаёт в тот же ряд: каждый роут
под `app/api/company` обязан идти через гейт компании, а каждая страница под
`app/company` — через его страничный вариант.

Проверяется четыре вещи ([scripts/company-check.mjs](../scripts/company-check.mjs)):
гейт в **каждом** экспортируемом обработчике (а не где-то в файле), проверка его
результата на `NextResponse` — иначе отказ утечёт в тело ответа вместо кода
состояния, — гейт на каждой странице, и отсутствие админских гвардов в консоли:
перепутанный гвард открыл бы страницу не тем людям, а снаружи это выглядит
одинаково.

### 6.4. Что в консоли на старте

| раздел | тег |
| --- | --- |
| Кошелёк: остаток, лента, пополнение | кошелёк |
| Статистика компании | статистика |
| Люди: завести, пригласить, назначить плательщика | люди |
| Права: выдать теги, назначить админа | права |
| Ключи внешних сервисов компании | ключи |
| Журнал действий компании | виден всем админам компании |

### 6.5. Статистика — третий режим

[`getStatistics`](../lib/repositories/statistics.ts#L1021) принимает scope, который
сервер берёт из сессии, и режимов сейчас два:

| режим | scope | разрез по людям |
| --- | --- | --- |
| кабинет | `ownerId` — только свои проекты | нет |
| админка | всё | да |
| **компания** | **`companyId` — проекты всех её людей** | **да, только внутри компании** |

Ограничение ставится в `sanitizeScope`, клиент его не переопределяет — как и
сейчас. У сотрудника в кабинете статистика остаётся только своей.

### 6.6. Что меняется в нашей админке

Только добавления: раздел «Компании» (завести, назначить владельца, перевести
людей, выключить компанию), колонка и фильтр «компания» в списке людей и в
статистике. Остальные разделы не трогаются.

## 7. Общий кошелёк

Проекты остаются у людей, заводить их люди могут сами, расход ложится на
компанию. Сотрудники о деньгах не думают вовсе.

### 7.1. Где сходятся деньги

| точка | файл | что делает |
| --- | --- | --- |
| чтение | `getFunds(userId)` — [funds.ts:174](../lib/billing/funds.ts#L174), 7 вызовов | остатки, резервы, гранты, лимит овердрафта |
| гейт | `admitItem({ ownerId })` — [admission.ts:61](../lib/billing/admission.ts#L61), вызов из [scan.ts:875](../lib/pipeline/scan.ts#L875) | пускать ли задачу в работу |
| запись | единственный `INSERT INTO billing_transactions` — [ledger.ts:109](../lib/billing/ledger.ts#L109) | движение денег |

Один читатель, один гейт, один писатель.

### 7.2. Почему нельзя просто подставить плательщика

Соблазнительно решить одной строкой: везде вместо владельца передавать кошелёк
компании. **Так нельзя, и ломается молча.**

| величина | откуда | при подстановке плательщика |
| --- | --- | --- |
| остаток | кэш `users.balance_*_cents` | компании — верно |
| гранты | `billing_grants.user_id` | компании — верно |
| овердрафт | `users.overdraft_limit_cents` | компании — верно |
| **резерв** | **`JOIN projects p ON p.user_id = $1`** | **проекты кошелька, а их нет → ноль** |

Резерв — это оценки живых задач ([funds.ts:63](../lib/billing/funds.ts#L63)), и
считается он по проектам того, чей идентификатор передали. У кошелька своих
проектов нет. Значит `availableOwnCents = остаток − 0 + овердрафт`, то есть
«доступно всё» при любой загрузке конвейера.

Последствие: гейт пускает работ на сумму, которую баланс не покрывает, и компания
уходит в минус тем глубже, чем больше сотрудников работают одновременно. Ошибки
при этом нет — задачи просто проходят.

**Отсюда требование: резерв обязан считаться по проектам всех, за кого платит
этот кошелёк, одним запросом.**

### 7.3. Кошелёк принадлежит компании, а не человеку

Админов в компании несколько, и любой из них может уйти. Будь кошелёк записан на
человека, его увольнение означало бы переезд денег. Поэтому плательщик компании —
**служебный аккаунт** (`users.kind = 'company_wallet'`, §3): строка в `users` без
пароля и без входа, не показывается ни в одном списке людей.

Деньги по-прежнему ключуются по `user_id`, поэтому в денежном контуре не меняется
ничего: лента, гранты, кэш остатков, овердрафт работают с кошельком как с любым
пользователем. Альтернатива — перевести биллинг с пользователя на компанию —
задела бы все эти таблицы разом.

Цена служебного аккаунта — три запрета: пометить, спрятать из списков людей,
отклонять вход.

В общем разделе, где компании нет, плательщиком может быть человек: связь
«кто за кого платит» от компаний не зависит (§7.4).

### 7.4. Связь: колонка на том, за кого платят

```sql
ALTER TABLE users
  ADD COLUMN IF NOT EXISTS payer_user_id TEXT REFERENCES users(id) ON DELETE RESTRICT;

-- Плательщик платит за себя сам: цепочки запрещены. Иначе COALESCE ниже даёт
-- только один уровень, и рекурсию пришлось бы городить в каждом запросе о деньгах.
ALTER TABLE users
  ADD CONSTRAINT users_payer_not_self CHECK (payer_user_id IS DISTINCT FROM id);

CREATE INDEX IF NOT EXISTS users_payer_idx ON users (payer_user_id)
  WHERE payer_user_id IS NOT NULL;
```

`NULL` — платит сам, как сейчас. Плательщик = `COALESCE(payer_user_id, id)`. У
сотрудников компании — кошелёк компании; у человека в общем разделе — он сам или
тот, кто за него платит.

Почему отдельная колонка, а не «платит кошелёк моей компании»: платит **не
всегда** компания. Её можно настроить так, что сотрудники платят сами
(`companies.features`), а в общем разделе человек может платить за коллегу без
всякой компании. «Кто за кого платит» и «кто в какой компании» — разные вопросы,
и одно поле на оба ответило бы неверно на один из них.

Резерв после правки:

```sql
JOIN users u ON u.id = p.user_id
WHERE COALESCE(u.payer_user_id, u.id) = $1
```

Список сотрудников при этом не нужен ни в коде, ни отдельным запросом.

### 7.6. Освобождение от оплаты НЕ наследуется

`users.billing_exempt` читается у владельца проекта

без единого сообщения.

Компания целиком освобождается флагом в `companies.features`, а не этим полем.

### 7.7. Кто видит деньги

**В компании** кошельком распоряжаются по тегу «кошелёк» в консоли, а не потому,
что это чей-то аккаунт.

**В общем разделе** плательщик — человек, и раздел «Кошелёк» у себя в кабинете
видит он сам.

**Тот, за кого платят,** денег не видит вовсе: ни остатка, ни ленты, ни кнопок.
Проект останавливается по той же причине `no-funds`, но текст ему адресуется
другой — «обратитесь к ответственному за оплату», а не «пополните баланс».

| угол | решение |
| --- | --- |
| **Пробный период.** `activateTrial(auth.userId)` [trial.ts](../lib/billing/trial.ts) выдаёт грант нажавшему; у сотрудника он ляжет на него, а читается у плательщика — деньги повиснут невидимыми | Для того, за кого платят, `readTrialState` возвращает `unavailable`. Пробный период — механизм для одиночки; компания заходит с деньгами |
| **Акции, адресные подарки, овердрафт.** Акция — грант на `userId` со списком проектов ([promo/route.ts:26](../app/api/admin/billing/promo/route.ts#L26)); выданный сотруднику, он повиснет так же | **Грант и овердрафт всегда выдаются плательщику.** Ограничение проектами сотрудника — через `billing_grant_projects`, механизм «подарок только в этих проектах» уже работает. Экран акций, выбрав сотрудника компании, сам подставляет её кошелёк. Сценарии: компенсация за сбой на проекте, пилот нового инструмента за наш счёт, партнёрская акция |
| **Личный баланс при переводе в компанию** | Остаётся на человеке и перестаёт использоваться. Не сгорает и не переносится: перекладывать чужие деньги молча нельзя. Ушёл из компании — баланс снова в деле |
| **Личный лимит овердрафта** перестаёт действовать: читается лимит плательщика | Поведение верное, но неочевидное. Показывать на странице человека, чей лимит применяется |
| **Один сотрудник выедает весь кошелёк** | На первом шаге лимит на человека НЕ делаем: он потребовал бы счётчика потраченного, а счётчик пришлось бы сводить с лентой и он бы с ней разошёлся — ровно та причина, по которой резерв не пишется лентой ([billing.sql:66](../db/migrations/2026-08-27-billing.sql#L66)) |
| **Удаление плательщика** | `ON DELETE RESTRICT`: сначала перевести тех, за кого он платит |

## 8. Доступ к работе: участие в проекте

**Компания — это администрирование и деньги. Доступ к работе — участие в
проекте**, как и сейчас: `project_members` с ролями `viewer` / `editor` / `full`
([project-roles.ts](../lib/project-roles.ts)).

Правила «все в компании видят всё в компании» нет и не будет. Иначе внешний
участник — фрилансер из общего раздела, проверяющий из другой компании — стал бы
исключением, которое встраивают задним числом. Сейчас участие уже работает
поперёк компаний, и платит по-прежнему владелец проекта («отдал доступ — платишь
ты», [funds.ts:63](../lib/billing/funds.ts#L63)).

### 8.1. Как человек попадает в проект

| путь | что происходит |
| --- | --- |
| Расшарили | как сейчас: «Поделиться» |
| Назначен в пайплайне | становится участником проектов своих шагов по умолчанию (§12.1) |
| Тегнули в чате | входит в проект: видит всю переписку и файлы этого этапа |

**Тег в чате — это приглашение**, и подчиняется он тем же правам, что кнопка
«Поделиться»: звать людей может `full` и владелец (`manageMembers`). Упоминание
того, кто уже участник, — просто уведомление. У `editor` тег не-участника
становится запросом владельцу. Компания может ослабить правило для своих
сотрудников настройкой, но не для внешних: иначе любой участник раздаёт чужим
людям файлы проекта одним сообщением.

### 8.2. С какой ролью входит тот, кого тегнули

Ему нужно читать всё и писать в чат, но не трогать файлы. **Такой ступени сейчас
нет**: писать в чат и писать файлы открываются одной ступенью, `editor`
([project-roles.ts](../lib/project-roles.ts), `writeChat` и `writeFiles`). Ступень
`commenter` между `viewer` и `editor` заводится вместе с чатами компании.

### 8.3. Выход: «вышел из чата — забыл проект»

**Сейчас выйти из чужого проекта может только участник с полным доступом.** Роут
требует `full` ещё до проверки «удаляю самого себя»
([members/route.ts:522](../app/api/projects/[id]/members/route.ts#L522)), и
исключение для себя (:549) до `viewer` и `editor` не доходит. Человек, которому
расшарили проект на просмотр, сегодня не может убрать его из своего списка.

Выход нужно открыть любой роли. Правка мелкая и полезна уже сейчас, независимо от
компаний.

### 8.4. Происхождение участия

Выход из чата должен снимать участие, полученное по тегу, но **не назначение в
пайплайне** — иначе шаг молча теряет исполнителя. `project_members` хранит
`invited_by`, но не «откуда». Колонка `via` (`share` / `pipeline` / `mention`)
добавляется вместе с пайплайном; миграция тривиальна, существующие строки
получают `share`.

## 9. Хранилище

**Для изоляции не нужно ничего.** Доступ к файлу идёт через `/api/media/` с
проверкой прав на проект, а не по знанию ключа. Ключи остаются
`projects/{storageOwnerId}/{projectId}/`.

Отдельный бакет на компанию отвергнут: `getS3Bucket()` вызывается **38 раз в 26
файлах**, и «чей бакет» пришлось бы протащить в каждый, включая фоновые задачи.
Изоляции это не добавляет.

Если понадобится операционное разделение — своя квота, свои lifecycle-правила,
отдельный счёт от R2 — это префикс `companies/{slug}/projects/…`, то есть одна
функция `projectObjectPrefix` в [s3-config.ts](../lib/s3-config.ts). Префикс
здесь для эксплуатации, а не для безопасности: границу держат права в базе.

### 11.1. Порядок поиска учётки

> ⚠️ **Отменено.** Лестница ниже заменена на две непересекающиеся —

> ключ разрешается в границах КОМПАНИИ проекта, и личная ступень внутри компании
> ломала бы это — перенос проекта в другую компанию молча срабатывал бы на личном
> ключе сотрудника вместо ошибки.

Сейчас — своя или платформенная
([gate.ts:106](../lib/vault/gate.ts#L106): `owner_user_id IS NULL OR = владелец`).
Добавляется одна ступень:

```
своя  →  компании  →  платформенная
```

Правка в двух местах: проверка графа (`checkAccounts`) и выдача ключей машине —
порядок у них обязан совпадать.

### 11.2. Одинаковые метки

Метка уникальна в пределах владельца
([2026-09-03-vendor-account-labels.sql](../db/migrations/2026-09-03-vendor-account-labels.sql)),
а в `options.json` проекта пишется только строка метки. Если у сотрудника своя
`main` и у компании `main` на тот же сервис, нода **молча** возьмёт личную.

Формат `options.json` — контракт с десктопом, и менять его ради этого не стоит.
Вместо этого: не давать завести метку, которая уже есть на соседнем уровне (своя
против компании), и помечать учётки компании в выпадающем списке ноды.

| что нужно | что уже есть |

| Передать результат шага следующему | цепочки [PROJECT_CHAINS_PLAN.md](./PROJECT_CHAINS_PLAN.md), но **только внутри одного владельца** |

| Кто платит | плательщик (§7): шаги у разных людей спишутся с одного кошелька сами |
| Кто что может | теги компании (§4): пайплайн принесёт свои |

Сегодняшние цепочки копируют результат нодой `Copy File` с путём
`../<проект>/<папка>`, и копирование за пределы владельца **невозможно по
построению** ([PROJECT_CHAINS_PLAN.md §2.1](./PROJECT_CHAINS_PLAN.md)). Пайплайн с
шагами у разных людей — это как раз выход за владельца, поэтому он делается
сайтом, а не десктопом.

Там же (§4.2–4.4) записано, что цепочки ломаются от переименования проекта,
опечатки и совпадения имён. Отсюда правило: **в пайплайне шаги связываются по id
проекта, а не по имени.**

Открытый вопрос: как хранить и передавать файлы между шагами и как фиксировать
передачу. Сейчас граница проекта совпадает с границей хранения, и передать файл
другому человеку — значит скопировать объект в R2 ([copy.ts](../lib/storage/copy.ts)).
Копировать между шагами или ссылаться — решается в отдельном плане.

### 12.2. Чаты компании

**Отдельный канал, а не новый тип отправителя в существующем.**
[`project_chat_messages`](../db/schema.sql#L598) — это переписка клиента с **нашей**
командой, и сообщения клиента зеркалятся в YouGile. Построенные на нём внутренние
чаты компании отправили бы переписку её сотрудников на нашу доску поддержки.

Модель прочтения тоже другая. Отметка `chat_team_last_read_at` одна на проект и
задумана как «прочитал один — прочитали все»
([2026-09-07-chat-team-read.sql](../db/migrations/2026-09-07-chat-team-read.sql)):
для поддержки верно, для чата внутри компании нет — там отметка на каждого
человека.

**Участники чата — это участники проекта**, один список, а не два (§8). Отдельный
список участников чата однажды разошёлся бы с доступом к файлам: человек в чате
без доступа к обсуждаемому, или наоборот.

Что понадобится: доставлено и прочитано на человека, имя отправителя, время,
картинки, упоминания, выход. Имя, время и «доставлено» в текущей схеме уже есть —
как образец формы, не как таблица для переиспользования.

## 14. Путь наружу

Модель выбрана в том числе потому, что **из неё можно выйти, а в неё — почти
нет.**

**Выделить компанию в отдельную площадку** — выгрузка: обход графа владения от
людей компании и её кошелька вниз (проекты, файлы, задачи, деньги, инструменты,
ключи, статистика, журнал) плюс объекты R2 по префиксам этих пользователей,
заливка в свежую базу, отдельный процесс со своим `.env`. Код при этом не
меняется вовсе: это тот же репозиторий, развёрнутый второй раз. Скрипт пишется
тогда, когда понадобится.

**Обратно — слияние**, и оно тяжелее: `users.email` уникален глобально
([schema.sql:5](../db/schema.sql#L5)), и один человек, заведённый на двух
площадках, становится конфликтом, который разбирают руками.

**Два отказа, которых в этом разделе плана не было, а в коде есть.** Оба —
про тихую потерю денег, и оба нашлись при разборе, а не в работе:

- **Удаление компании при живой ленте.** `billing_transactions.user_id` стоит
  `ON DELETE CASCADE` ([billing.sql:72](../db/migrations/2026-08-27-billing.sql#L72)),
  поэтому удаление служебного кошелька унесло бы всю ленту компании молча.
  Удаление отклоняется, пока на кошельке есть транзакции или гранты.
- **Перевод обходил защиты плательщика.** Смена `payer_user_id` при переводе —
  та же операция, что на экране акций, поэтому и проверки те же, что у
  `setPayer` (§7.8): открытый подарок и «платит за других» отклоняются
  причиной, а не ошибкой базы.

**Компания на этом этапе ещё ничего не открывает — она только существует.**
Консоли нет. Это намеренно: модель и поверхность разведены по этапам, чтобы
ошибку в правах не пришлось искать вместе с ошибкой в модели.

**Приёмка:** компания заводится кнопкой вместе с кошельком; кошелёк не виден ни в
одном списке людей и не может войти; человек переносится в обе стороны и теряет
права старой компании; удаление непустой компании отклоняется.

### Этап 4 — консоль компании ← основная работа и риск

**Статус 2026-09-11:** сделано и проверено на временной локальной базе. Схема не
менялась — всё нужное завёл этап 3, новой миграции у этого этапа нет.

`/company` с гейтом `requireCompanyApi` / `requireCompanyPage` (§6.2);
`company:check` (§6.3); разделы консоли (§6.4); статистика — третий режим scope
(§6.5); правило выдачи прав и защита последнего владельца (§4); ключи компании и
порядок поиска учётки (§11).

*Зависит от этапа 3.*

**Что оказалось тоньше, чем записано выше.**

- **Разрез по людям в деньгах.** В компании плательщик у всех строк ленты один —
  её кошелёк, поэтому разрез по `billing_transactions.user_id` дал бы одну
  строку «кошелёк компании» вместо ответа «кто сколько потратил». Ключом стал
  владелец проекта (`ledgerBreakdownExpr`, аргумент `byProjectOwner`).
- **Рамка ленты — не только кошелёк.** Расход компании считается по строкам, чей
  плательщик её кошелёк **или** кто-то из её людей. Второе слагаемое не
  перестраховка: плательщик проставляется при переводе, но человек мог платить
  сам по настройке — и его списания просто не попали бы в счёт, молча.
- **Журнал без тега.** Виден всем админам компании (§6.4) — это названное
  решение, а не умолчание, поэтому для него заведён отдельный гвард
  `requireCompanyApiAnyAdmin`, а не необязательный аргумент у общего.
- **Деньги не пересчитываются.** Остаток и резерв компании читает
  `getFunds(walletUserId)`. Свой запрос был бы вторым ответом на вопрос
  «сколько доступно» и разошёлся бы с тем, по которому работает допуск задач.

**Чего в консоли намеренно нет.** Заводить и переводить людей — только из нашей
админки (§6.6): перевод меняет плательщика и снимает права, и отдать его
компании значило бы дать ей сажать чужого человека на свой счёт. Заводить ключи
— только в «Сервисах»: второе место, куда можно положить чужой ключ, — это
второе место, где его можно положить не туда. Пополнять кошелёк — тоже не
здесь.

**Справка у консоли есть** (`companies.console`). Реестр тем знал только теги
САЙТА, поэтому у `HelpAudience` появилось значение `"company-admin"`: админ
компании — обычный `USER` на сайте, и любой сайтовый тег закрыл бы ему статью
про его же консоль. Видимость решает гейт консоли, а не роль с тегами, — второй
источник правды однажды разошёлся бы с первым.

**Переключатель компаний у суперадмина (исправлено 2026-09-11).** Своя компания
проверялась в гейте ПЕРЕД кукой переключателя, поэтому суперадмин, оказавшийся в
какой-нибудь компании, прилипал к ней намертво: список в шапке рисовался, кука
ставилась, а выбор молча не срабатывал. Теперь ветка суперадмина идёт первой, а
прежнее умолчание сохранено — не выбрал ничего, попадает в свою.

**Приёмка:** админ компании видит в консоли только своих и только разделы по
своим тегам; не может выдать тег, которого нет у него; последнего владельца снять
нельзя; `company:check` валит роут без гейта; суперадмин переключается между
компаниями; `/admin` для админа компании недоступен.

забытого фильтра в пользовательских выборках. У нас риск не там: пользовательские
выборки уже скоупятся по владельцу, а поперёк людей смотрит только консоль,
ограниченная гейтом.

**Внутренние чаты на `project_chat_messages`.** §12.2.

**Таблицы пайплайнов и чатов заранее.** §12.3.

**Отдельный бакет и отдельную базу на компанию.** §1.3 и §9.

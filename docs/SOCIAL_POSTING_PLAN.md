# Автопостинг на площадки силами сайта — план

**От кого:** десктоп-клиент (`fs.manager.tauri`), где автопостинг уже работает локально.
**Зачем документ:** решением 2026-08-24 постинг переносится **с машин на сайт**. Здесь — что
для этого нужно на бэкенде, и всё, что мы уже знаем про площадки, чтобы не проходить их
грабли второй раз.

**Статусы в этом файле:** ✅ работает · 🔧 частично · ⬜ не сделано

**Связанный документ:** [POSTING_NODES_PLAN.md](./POSTING_NODES_PLAN.md) — какие ноды графа
сайт исполняет сам (цепочка до Poster'а, текстовые ноды, фаза подготовки) и куда это растёт:
план публикаций, режимы проекта, остановка и просроченные.

**Текущее состояние сайта (2026-09-07).** Первый круг сделан: сейф аккаунтов площадок, очередь
публикаций, обход папок-источников, адаптер VK и раздел «Автопостинг» в админке. Публикует сайт,
байты идут из R2 прямо в VK. Что именно работает и чего пока нет — §11.

## 1. Почему постинг должен жить здесь, а не на машине

Сейчас (у нас, локально) цикл такой: файл лежит в R2 → машина **скачивает** его в зеркало →
машина заливает байты на площадку. То есть один и тот же файл едет по сети дважды, и всё это —
на домашнем интернете исполнителя.

Если публикует сайт, байты идут **из R2 прямо в площадку**, по короткому пути внутри дата-центра.
Плюс исчезает главная слабость локального постинга: расписание работает только пока у человека
запущена программа. Сайт — постоянно живой хост (pm2 + nginx, `ecosystem.config.json`), у него
уже есть cron-роуты (`/api/cron/storage-jobs` с `Bearer $CRON_SECRET`).

Разделение после переноса:

| что | где |
|---|---|
| настройка: какие папки постить, куда, в каком окне, с каким интервалом | **машина** (граф нод, как сейчас) |
| хранение токенов площадок | **сайт** (см. §4) |
| решение «пора публиковать этот файл» | **сайт** |
| байты и загрузка на площадку | **сайт** (стрим из R2) |
| судьба файла после публикации (переложить/удалить) | **сайт** через каталог, машина увидит в `/delta` |

## 2. Откуда сайт узнаёт, что и куда постить

**Ничего нового синхронизировать не надо.** Конфигурация постинга уже лежит в графе проекта, в
`options/options.json`, который сайт и так читает при сборке задач:

- нода-источник **`finder`** — папка, тип файлов, порядок, интервал, окно/дни (судьба файла
  переехала оттуда в ноду публикации, см. §7.1);
- нода-**Poster** (`autoPostVK` / `autoPostYT` / `autoPostTG`) — аккаунт, цель (профиль/сообщество/
  канал), заголовок/описание/теги (могут быть с масками пути);
- **платформа выводится из того, какой Poster стоит в графе**, а не из отдельного поля. У нас это
  карта `POSTER_PLATFORM` в `src/PROCESSING/autoPost/posters.ts` — одна строка на площадку.

У нас рядом есть локальный сайдкар `options/postSources.json` (выжимка из графа: наличие файла =
тумблер постинга). Для сайта он не нужен и в канал `/sidecars` не входит — читайте граф.

Что при этом важно не сломать: **связь важнее поля.** Если в графе к свойству `description`
Poster'а идёт ребро от другой ноды, текст берётся оттуда, а напечатанное в поле игнорируется. В
пайплайне, который вы уже собираете, эта связь есть — используйте её так же, как при обработке.

## 3. Модель данных

### 3.1. Очередь публикаций

Отдельная таблица, а не `tasks`: у задачи обработки исполнитель — машина с лицензией AE, у
публикации — сам сайт, и смешивать их аренды/повторы не надо.

```sql
CREATE TABLE post_jobs (
  id             TEXT PRIMARY KEY,
  project_id     TEXT NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
  file_id        TEXT REFERENCES project_files(id) ON DELETE SET NULL,
  source_key     TEXT NOT NULL,             -- ключ в R2 на момент постановки
  platform       TEXT NOT NULL,             -- 'vk' | 'youtube' | 'tg'
  account_id     TEXT NOT NULL,             -- ссылка на аккаунт из §4
  target         JSONB NOT NULL,            -- группа/канал/профиль, зависит от площадки
  meta           JSONB NOT NULL DEFAULT '{}'::jsonb,  -- title/description/tags после резолва масок
  status         TEXT NOT NULL DEFAULT 'queued'
                   CHECK (status IN ('queued','running','done','failed','skipped')),
  attempts       INTEGER NOT NULL DEFAULT 0,
  max_attempts   INTEGER NOT NULL DEFAULT 3,
  error          TEXT,
  external_id    TEXT,                      -- id поста/видео на площадке
  external_url   TEXT,
  published_at   TIMESTAMPTZ,
  created_at     TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at     TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

### 3.2. Дедуп — реестр опубликованного

Главное требование: **один файл не должен уехать на одну площадку дважды**, даже если очередь
перезапустилась, задача повторилась или файл переиндексировали.

```sql
CREATE TABLE post_ledger (
  file_id     TEXT NOT NULL,
  platform    TEXT NOT NULL,
  account_id  TEXT NOT NULL,
  post_job_id TEXT NOT NULL REFERENCES post_jobs(id) ON DELETE CASCADE,
  external_id TEXT,
  posted_at   TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  PRIMARY KEY (file_id, platform, account_id)
);
```

Ключ **`файл + площадка + аккаунт`** (у нас локально ровно такой же: `file + platform`). Один
файл в две группы VK — это две разные строки, и это законно; тот же файл в ту же группу второй
раз — нет.

**Отличие от реализации (2026-09-07):** файл в реестре опознаётся не по `file_id`, а по
`project_id + source_key` — по ключу в R2. Причина простая: `afterPost: Delete` убирает исходник
сразу после публикации, строка каталога исчезает, и реестр по `file_id` потерял бы адресата — файл,
залитый заново под тем же именем, снова считался бы неопубликованным. Ключ переживает удаление.

Запись в реестр — **в одной транзакции** с переводом `post_jobs` в `done`. Иначе окно между
«площадка приняла» и «мы записали» даёт дубль публикации, который уже не отменить.

### 3.3. Интервалы и окна

Локально мы держим тайминг в файле `_post/$MM.$YYYY.jsonl` (последняя публикация по маршруту +
кулдаун после ошибки). Здесь это два запроса к `post_ledger` / `post_jobs`:

- **интервал**: `MAX(posted_at)` по проекту+площадке — если прошло меньше, чем задано в `finder`,
  не ставим задачу;
- **окно/дни недели**: считать в таймзоне проекта, а не сервера. Наш опыт: рассинхрон TZ — одна
  из трёх ловушек, на которых мы обожглись в статистике;
- **кулдаун после ошибки площадки**: при 429/квоте отложить площадку целиком, а не конкретный
  файл — иначе очередь долбит лимит по кругу.

## 4. Токены площадок — сейф

Публикация невозможна без секретов, а секреты сейчас лежат **на машинах** (`accounts/*.json` в
папке приложения). Перенос постинга = перенос секретов, и это отдельный кусок работы, который у
нас уже спроектирован со стороны клиента: `fs.manager.tauri/ideasAndTest/SECRETS_VAULT_SITE_PLAN.md`
(модель B: сайт = UI + сейф, машины авторизуются и тянут токены с TTL). Со стороны сайта нужно:

- таблица аккаунтов площадок: `id`, `user_id`/`client_id`, `platform`, человекочитаемое имя,
  `secret` (шифрованный), `meta` (каналы/группы), `created_at`, `revoked_at`;
- **шифрование at-rest** ключом из окружения (не в БД), и никогда не отдавать секрет наружу —
  ни в API, ни в логах. Наружу только «аккаунт такой-то подключён»;
- OAuth-редиректы для YouTube (см. §5.2) — на сайте это проще, чем у нас: не нужен loopback;
- отзыв: `revoked_at` + отказ всех очередей по этому аккаунту.

До сейфа постинг с сайта невозможен физически, поэтому это **первый** пункт порядка работ.

Тот же сейф нужен ключам внешних сервисов ([VENDOR_SERVICES_PLAN](./VENDOR_SERVICES_PLAN.md), С4):
аккаунты площадок и ключи вендоров — один вопрос «где лежат чужие секреты и кто их
отзывает». Делать два хранилища значит завести две процедуры отзыва, и вторую забудут.

## 5. Что мы знаем про площадки (не проходить заново)

### 5.1. VK

- Один токен приложения **`vk.com` (`client_id 6287487`)** покрывает и видео, и Клипы. **Не Kate
  Mobile** — у него Клипы скрыты. Со scope `offline` токен бессрочный, refresh не нужен.
- Обычное видео: `video.save` → `POST upload_url` (поле `video_file`) → `wall.post`.
- Клипы (вертикаль 9:16): `shortVideo.create` → upload (поле `file`) → **пауза на обработку** →
  `shortVideo.edit` → `shortVideo.publish`; `wallpost=1` даёт дубль в ленту.
- У нас в проде включён только режим Video (Post); код Клипов написан и лежит рядом
  (`plugins-dev/autoPostVK/_publisher.ts`) — можно портировать целиком.
- Версия API у клипов своя, отличается от общей (`V_SHORT`).

#### 5.1.1. Как человек подключает VK на сайте — и что даст своё приложение

Решено 2026-09-07. В программе токен ловит Rust: окно-webview идёт на
`oauth.vk.com/authorize` (Kate Mobile, `2685278`, `response_type=token`), а `on_navigation`
перехватывает редирект на `blank.html#access_token=…`
(`src-tauri/src/commands/vk_auth_commands.rs`). **В браузере так нельзя.** После входа вкладка
стоит на домене VK, и прочитать её адрес с нашей страницы запрещает политика источников —
причём токен лежит во фрагменте, который вообще не покидает браузер и на сервер VK не уходит.

Поэтому на сайте воспроизводится вторая ветка того же компонента — ручная вставка
(`VkAccountDDM.tsx`, пункт «Вставить токен вручную»). Вкладка со входом при этом открывается
САМА, как только известна площадка: лишний клик между «хочу подключить» и «вошёл» не решает
ничего, и программа ведёт себя так же — «Add New Account» сразу открывает окно логина. Кнопка
рядом остаётся на два случая: браузер заблокировал вкладку и человек закрыл её случайно.

Адрес входа при этом НЕ зависит от базы. Это выяснилось на живом экране: до применения миграций
`GET /api/account/social-accounts` падал, каталог площадок приезжал пустым — и вместе с ним
исчезала кнопка входа, молча. Теперь каталог отдаётся всегда (он статический), ошибка чтения
аккаунтов приезжает отдельным полем и показывается на экране, а адрес входа у браузера есть и
своим ходом (`vkAuthorizeUrl()`).

**Что даст своё приложение VK с `redirect_uri` на сайт.** Четыре вещи, и только последняя —
про удобство:

1. **Клипы.** Kate Mobile их не отдаёт вовсе (`shortVideo` скрыт), а код публикации клипов у нас
   уже написан (`plugins-dev/autoPostVK/_publisher.ts#publishClip`). Пока приложения нет,
   вертикальные клипы недоступны в принципе — ни на сайте, ни в программе.
2. **Токен, привязанный к нашему IP, а не к чужому.** Это главное и неочевидное. Постит сайт —
   значит запросы к VK идут с адреса VPS. Токен, полученный **implicit-потоком в браузере**,
   выдаётся тому, кто вошёл, то есть привязывается к IP человека; со своим приложением можно
   взять **code-поток**, где обмен кода на токен делает наш сервер со своего адреса. Именно
   поэтому программа сидит на Kate Mobile: его `offline`-токен не привязан к IP вообще, и это
   был единственный способ не думать про адреса. У сайта появляется второй способ — правильный.
3. **Проверяемая привязка к сессии.** В code-потоке есть `state`: мы знаем, что вернулся тот же
   человек, который начинал. При вставке мы принимаем на веру всё, что вставили, — включая
   чужой токен, вставленный по ошибке или по чьей-то просьбе.
4. **Один клик** вместо «войди → скопируй адрес → вернись → вставь». Заодно токен перестаёт
   ехать через буфер обмена и адресную строку, то есть мимо скриншотов и чатов поддержки.

**Чего это стоит:** зарегистрировать приложение, прописать в нём `redirect_uri` на сайт, положить
`client_id`/`client_secret` в окружение. Пункт 2 при этом надо **проверить на живом приложении**
до переключения — поведение привязки к IP у VK менялось, и полагаться тут на общее знание нельзя.

Код написан так, что вторая ветка включается переменной окружения и не требует переписывания:
`vkAuthorizeUrl()` принимает `redirectUri`, а адаптер площадки (`lib/social/platforms.ts`) —
единственное место, которое про это знает.

### 5.2. YouTube

- Модель **B (BYO credentials)**: API-клиентом является пользователь — его Google Cloud проект,
  его OAuth-клиент, его квота (10 000 юнитов/день, `videos.insert` ≈ 1600), его audit. Ответственность
  за контент и за поведение клиента — на нём. Менять эту модель на «наш общий клиент» —
  значит взять на себя аудит и риск блокировки всего приложения.
- `access_token` живёт час → нужен `refresh_token` на канал. **Один `refresh_token` = один канал.**
- Загрузка — **resumable**: `POST …/videos?uploadType=resumable` (метаданные) → `PUT` тела
  чанками с `Content-Range`. Общий размер известен из каталога.
- До прохождения audit у пользователя видео принудительно уходят в `private` — это Google, не мы.
- На сайте OAuth проще, чем у нас: обычный web-redirect вместо системного браузера + loopback + PKCE
  (это была вынужденная схема для десктопа, Google блокирует OAuth в webview).

### 5.3. Telegram

- Публикация ботом (`@BotFather`), бот — админ канала. Каталог каналов Bot API **не перечисляет**,
  поэтому список каналов держим у аккаунта и наполняем через `getUpdates`/ручной ввод.
- **Гейт 50 МБ** на загрузку через облачный Bot API. Снимается только **локальным Bot API
  сервером** (`telegram-bot-api --local`, лимит → 2 ГБ), которому нужны разовые `api_id`/`api_hash`
  с my.telegram.org (это НЕ токен бота).
- **Отсюда прямая выгода переноса:** на вашем VPS такой сервер поднять естественно (один процесс на
  хост, обслуживает все токены), а на домашней машине — нет. У нас TG-постинг именно поэтому стоит
  на паузе.
- Мультиканал: один upload → полученный `file_id` переиспользуется для остальных каналов, байты
  второй раз не грузятся.
- Метрик у Bot API нет.

## 6. Байты: из R2 в площадку без диска

Все три площадки принимают тело потоком, все три требуют либо размер заранее, либо чанки. R2
отдаёт presigned GET, размер лежит в каталоге. Отсюда правило: **стримить, а не буферизовать**.
В pm2 стоит `max_memory_restart: 1G` — файл на 2 ГБ, прочитанный в память, положит процесс.

- VK: `pipe` из presigned GET в `multipart/form-data` на `upload_url`.
- YouTube: чанки `PUT` с `Content-Range` — читать из R2 диапазонами (`Range`) ровно теми же
  кусками. Наш опыт из другой задачи: presigned GET + `Range` работает и по нему даже `ffprobe`
  читает только `moov`.
- Telegram: `sendVideo` через локальный Bot API сервер — файл ему можно отдать и как локальный
  путь, если он на том же хосте.

Долгая загрузка не должна жить в HTTP-хендлере Next: очередь дренируется cron-роутом
(`POST /api/cron/post-queue`, как `storage-jobs`), одна задача за тик, с лизом и таймаутом.

## 7. Что делать с файлом после публикации

Локально это решала нода `copyFile`/`afterPost`: переложить в подпапку, удалить или оставить.
На сайте эквивалент — операции каталога, которые у вас уже есть: `/rename` (перенос внутри
проекта), `/trash`. Машина увидит результат обычной дельтой, ничего специального не нужно.

Значение по умолчанию — **оставить**. Удаление исходника после публикации должно быть явным
выбором пользователя: ошибка тут необратима.

### 7.1. Контракт `afterPost` — свойство ноды публикации

Согласовано 2026-09-07. Решение «что с файлом дальше» переезжает с Finder'а на **ноду
публикации**, и это правильное место: решение принимается ПО ИТОГУ публикации, а Finder к тому
моменту своё дело сделал. Галочка `deleteAfter` из Finder'а убирается — живых автопостингов на
момент переноса нет, поэтому совместимость держать не для кого, и сайт её больше не читает.

**Свойство ОДНО, а не два.** Отдельное поле «куда перенести» при выбранных «оставить» или
«удалить» висело бы пустым и бессмысленным, а условной видимости в редакторе нод нет. Поэтому
действия и токены пути живут в одном `autocomplete`, разделённые заголовками (`---текст`
рисуется как заголовок группы, значением не становится):

```jsonc
{
  "id": "afterPost",
  "controlType": "autocomplete",
  "controlProps": {
    "label": "After post",
    "tooltip": "Что сделать с исходником после успешной публикации.\nЛибо действие, либо путь: первый чип решает.\nПусто = оставить на месте.\nПуть можно с масками: VK_posted/$YYYY.$MM\n../Другой проект/IN — перенести в соседний проект (только на один уровень вверх).",
    "options": [
      "---Что сделать",
      "Keep",
      "Delete after",
      "---Или перенести в папку",
      "#pathPattern",
      "#folders",
      "#historyValue(afterPost)"
    ],
    "multiSelect": true,
    "allowDuplicates": true,
    "value": []
  },
  "outputType": "path"
}
```

**ПРАВИЛО, которое делает это однозначным: решает ПЕРВЫЙ чип.** Он либо известное действие —
тогда остальные чипы не значат ничего, — либо начало пути, и тогда весь список чипов и есть путь.
Без такого правила «Delete after» вперемешку с папкой означали бы что угодно, и разбирать это
пришлось бы гаданием.

Цена правила: папка, названная буквально «Keep» или «Delete after», будет принята за действие.
Это сказано в подсказке свойства; выдумывать разбор кавычек ради такого имени папки дороже, чем
папку переименовать.

Отличие от `targetPath` у `copyFile`, с которого списан компонент, одно: **без `Custom Folder...`**.
Абсолютный путь — папка на машине человека, а в облаке файл живёт внутри проекта, и вынести его
наружу некуда. Если такой путь всё же окажется в графе, сайт превратит «перенести» в «оставить»,
а не выдумает, куда деть файл.

Как это читает сайт ([routes.ts](../lib/posting/routes.ts), [scan.ts](../lib/posting/scan.ts)):

- действие нормализуется, а не сравнивается буквально: подпись может быть английской или
  русской. Незнакомый первый чип считается началом пути, а не ошибкой;
- **пусто = оставить.** Это же и значение по умолчанию, и самый частый случай;
- **маски в пути раскрываются при ПОСТАНОВКЕ задачи**, тем же контекстом, что и описание. Значит
  `VK_posted/$YYYY.$MM` разложится по тому месяцу, когда файл поставили в очередь, а не по тому,
  когда до него дошла очередь. Набор масок — подмножество (§11, пункт 7);
- путь, ставший пустым после раскрытия масок, тоже означает «оставить»;
- **`../` в НАЧАЛЕ пути уводит в соседний проект того же человека**: `../Другой проект/IN`.
  Ровно один уровень, не больше. Выше проектов лежат чужие папки и чужие люди, и «подняться на
  два» означало бы дать графу дотянуться туда, куда его автору доступа никто не давал; два и
  более `../` — это не «выше», а отказ, файл остаётся на месте. `..` в СЕРЕДИНЕ пути
  (`A/../B`) по-прежнему просто поднимается на уровень внутри пути, как в чип-навигации
  программы: два смысла у одного символа разводятся по позиции;
- проект-получатель ищется по имени **среди проектов того же владельца** (без учёта регистра) и
  запоминается у задачи по id: имя могут поменять, пока задача ждёт очереди. Чужой проект с таким
  же именем целью не станет никогда;
- перенос в СОСЕДНИЙ проект — это не переименование: у каждого проекта свой префикс ключей в R2,
  поэтому там копия объекта плюс удаление исходника, тем же путём, каким копирует между проектами
  кабинет. Сначала копия, потом удаление — обратный порядок дал бы файл, удалённый до того, как
  копия удалась;
- **неразрешимое назначение не отменяет публикацию.** Опечатка в пути к ней отношения не имеет:
  файл остаётся на месте, а причина («проект не найден») едет с задачей и видна в очереди
  замечанием рядом со статусом «опубликовано» — не красным, потому что публикация состоялась;
- папка-получатель создаётся, если её нет: человек указал её в графе, а не заводил руками;
- перенос идёт через `writeRename` — он ведёт журнал, иначе для машины перенос остался бы
  невидимым. Ключ в R2 при переносе не меняется, поэтому реестр опубликованного продолжает
  узнавать файл и после переезда.

**Список действий останется коротким.** Сайт исполняет ноду публикации, а не весь граф: `copyFile`
и всё, что за ним, — работа машины (§11, пункт 1). Здесь возможны только операции каталога:
оставить, удалить, перенести.

## 9. Переходный период — важно

Пока сайт не постит, постинг работает на машинах, и **два постинга по одному проекту включать
нельзя**: дедуп у нас файловый (`options/_post/*.jsonl`), у вас — в БД, друг о друге они не знают,
и один и тот же файл уедет дважды. На время перехода нужен явный переключатель «постинг этого
проекта делает сайт» — и мы на своей стороне глушим локальный раннер для таких проектов.

Проще всего сделать его флагом в `automation_settings` или полем проекта: главное, чтобы источник
истины был один и его видели обе стороны.

**Решено 2026-09-07: переключателя не будет — граница проходит по природе папки.**

Проверка показала, что предполагавшееся «программа постит только локальное» неверно:
`collectPostRoutes` (`src/PROCESSING/autoPost/scheduler.ts`) перебирает `mainFolderArr` и
фильтрует записи только по `mf.active`, а флаг `online` — тот, которым помечена папка клиента в
облачном зеркале, — не проверяет вовсе. Обработка про него знает
(`findAllFilesForProcess.ts`, автоотключение холодных проектов синхронизирует паузу в каталог
сайта), а постинг — нет. То есть проект в облачной папке сегодня постили бы обе стороны.

Правка делается **в программе**: постинг пропускает папки с `online: true`. После неё правило
становится структурным, а не настроечным — **облачные папки постит сайт, локальные постит
программа**, и совпасть они не могут по построению. Это лучше флага: флаг можно поставить
неправильно, а перепутать локальную папку с облачной нельзя — это разные записи в списке.

Из этого же следует, чего делать НЕ надо: заводить поле «постит сайт» у проекта, сводить два
реестра дедупа и придумывать, кто главный при расхождении. Пока файл лежит в зеркале, локального
реестра по нему просто не возникает.

### Чего пока нет — и почему это важно знать

1. **Сайт исполняет только публикацию, а не весь подграф.** Программа гонит от Finder'а всю
   цепочку: Poster → `copyFile` → что угодно дальше. Сайт исполняет Poster и на этом
   останавливается — остальные ноды это работа машины, у неё ffmpeg и локальные пути. Судьба
   файла после публикации решается свойством `afterPost` самой ноды публикации: оставить,
   удалить, перенести в папку (§7.1). Нода `copyFile` после постера на сайте **не отработает** —
   и не должна: для трёх операций каталога отдельная нода не нужна.
2. **Описание, приходящее СВЯЗЬЮ, не поддержано.** Снимается в
   [POSTING_NODES_PLAN.md](./POSTING_NODES_PLAN.md) §3.
   До тех пор правило «связь главнее поля» (§2) соблюдается
   единственно честным способом: такой маршрут **не исполняется**, и в отчёте по маршрутам
   написано почему. Вычислить значение связи может только исполнитель графа, а публиковать
   текстом из поля — заведомо публиковать не то.
3. **Папка-источник с абсолютным путём** (`CustomFolder...`) пропускается: в облаке такой папки
   нет вовсе.
4. **Клипы VK недоступны** — у Kate Mobile `shortVideo` скрыт (§5.1.1). Код клипов лежит готовый
   в программе и включается вместе со своим приложением VK.
5. **YouTube не подключается, Telegram не публикует** (§8, пункты 6–7).
6. **Таймзона одна на установку** — `POSTING_TIME_ZONE`, по умолчанию `Europe/Moscow`. Поля
   «таймзона проекта» на сайте нет; когда понадобится разный пояс у разных клиентов, оно
   появится у проекта.
7. **Маски в тексте поста — подмножество**: имя, id, проект, дата/время, `$random()`. Путевые
   маски (`$localFolder`, `$projectPathGD`) подставляются пустыми — путь машины на стене не
   нужен; незнакомые `$токены` остаются как есть, потому что в тексте доллар бывает просто
   долларом. Разбор — [masks.ts](../lib/posting/masks.ts).
